# 11. 自作エミュレータ t5emu（ESP32-P4 rev v1.x、案 B の初版）

- 日付: 2026-10-30
- 位置づけ: 08 の案 B（Rust で専用エミュレータを書く）の初版。M1（09）と M2（10）で実機の挙動を確かめたので、それを仕様にした。
- 結果: **実機に書き込むのと同じカーネルの ELF（`build/t5-kernel-esp32p4v1.elf`）を、無改造で最後まで実行し、selftest PASS になった。** 実行時間は約 0.36 秒（465 万命令、エミュレーション上の 251ms）。
- 使い方: `make test-p4emu`（終了コード 0 なら PASS）、`make test-emu`（エミュレータ自身の単体テスト）。

## 1. 構成（`emu/`）

ホスト用の単独クレートで、外部依存はない。

| ファイル | 内容 |
|---|---|
| `src/machine.rs` | HP コア。RV32IMAFC、M/U モード、CSR、トラップ（CLIC と直接モード）、P4 固有の lock-up、ROM のキャッシュ関数、`wfi` |
| `src/rvc.rs` | RV32C（c.flw/c.fsw などを含む）を 32 ビット命令に展開する |
| `src/pmp.rs` | PMP。16 エントリ、粒度 128B（G=5）、TOR/NAPOT、NA4 は選べない（WARL で OFF になる）、L ビット |
| `src/cache.rs` | L1 キャッシュの非一貫性のモデル（§2.2） |
| `src/periph.rs` | USB Serial/JTAG、SYSTIMER、割り込みマトリクス、v1.x の CLIC、LP_WDT（RWDT） |
| `src/bus.rs` | アドレスマップ。フラッシュ窓 0x4000_0000（2MiB）、L2MEM 0x4FF0_0000（768KiB）とその非キャッシュ別名 0x8FF0_0000、TCM、ROM、周辺 |
| `src/elf.rs` | ELF32 の PT_LOAD を読む |
| `src/main.rs` | CLI。`--mhz`、`--cache strict\|off`、`--max-ms`、`--seed`、`--trace-traps`、`--warn-unmodelled`、`--quiet` |

- ブートローダは模していない。PT_LOAD をそれぞれの仮想アドレスに置き、ELF のエントリから M モードで始める（ブートローダが渡す状態と同じく、mstatus=0、PMP はすべて OFF）。
- 時間は命令数で決まる。1 命令 = 1 サイクルで、CPU の周波数は既定で 40MHz。SYSTIMER（16MHz）はサイクル数から計算する。そのため**何度実行しても同じ結果になる**（命令数まで一致）。
  - `wfi` では、次にアラームが鳴る時刻まで時間を飛ばす。
  - 起こしてくれるものが何もない `wfi` は「停止」とみなす。カーネルが最後に入る待機ループがこれに当たる。
- L2MEM の初期値は、0 ではなく疑似乱数で埋める（`--seed`）。「メモリが 0 で始まる」ことに頼ったコードを見つけるため（判断）。
- 未実装の周辺レジスタは、書いた値をそのまま読み返すレジスタとして扱う。`--warn-unmodelled` を付けると、触ったアドレスを表示する。

### 終了コード
| コード | 意味 |
|---|---|
| 0 | カーネルが `selftest: PASS` を出して停止した |
| 1 | FAIL を出した、または結果を出さずに停止した |
| 2 | ハードウェアの水準の問題で止めた（lock-up、キャッシュ非一貫なフェッチ、RWDT の満了、未知の ROM 呼び出しなど） |
| 3 | 時間切れ（`--max-ms`、既定 10 秒） |

- 合否の判定は、当面コンソールの文字列で行う。構造化ログのサービス（ユーザー方針: OS はテキストログを持たず構造化ログだけを提供する）ができたら、`selftest.result` のようなイベントを解読して判定するように変える。

## 2. 実機の挙動をどう模したか

### 2.1 実機と ESP-IDF で確かめた事実をそのまま入れたもの
| 挙動 | 根拠 |
|---|---|
| misa = 0x4090_1125 | 実機（09） |
| CLIC モード（mtvec の mode=3）では、非ベクタの割り込みも例外も `mtvec & !63` に飛ぶ。mcause は [31] 割り込み、[29:28] mpp、[27] mpie、[23:16] mpil、[11:0] コード | 実機（10）、01 §4.1 |
| mcause.mpp/mpie は mstatus のフィールドの別名で、mret は mil を mpil から戻す | CLIC 仕様。カーネルの `run_user` はこれを前提にしている（10 §1.4） |
| mintstatus は 0x346（v1.x は非標準）、閾値は MMIO 0x2080_0008 の [31:24] | `riscv/include/riscv/csr_clic.h`、`soc/esp32p4/include/soc/clic_reg.h:61`（01 §0） |
| CLIC の制御ワード（ctl/attr/ie/ip）、NLBITS=3、48 本 | `clic_reg.h` |
| 割り込みマトリクス: ソース 53（SYSTIMER target0）のマップレジスタに CLIC 番号を書く | 10 §2.1 |
| SYSTIMER: 16MHz、スナップショット読み出し、アラームは `>=` で比較する（過去の時刻なら即座に発火） | 10 §2.1、`soc_caps.h:598` |
| MIE=0 でも、有効にした割り込みが保留になると `wfi` から戻る | 実機（10） |
| `mstatus.FS=Off` のときは、FP 命令（`flw`/`fsw` を含む）が不正命令になる | 実機（10） |
| RWDT: ブートローダが 9 秒で有効にしたまま渡す。設定レジスタへの書き込みは、WPROTECT に鍵があるときだけ効く | `boot/` の `CONFIG_BOOTLOADER_WDT_TIME_MS=9000`、`lp_wdt_reg.h`、kernel の `init` |
| USB Serial/JTAG: EP1 に書けば出力される（FIFO は常に空いている扱い） | 実機（09） |

### 2.2 L1 キャッシュの非一貫性（M1 で実機を止めた不具合）
- 各 64B の行について「D キャッシュに書いたがまだ書き戻していない（D_DIRTY）」と「I キャッシュが古い内容を持っている可能性がある（I_STALE）」の 2 つの状態を持つ。
  - データ側から書き込むと、両方が立つ。
  - `Cache_WriteBack_Addr(L1_DCACHE)` で D_DIRTY が消える。
  - `Cache_Invalidate_Addr(L1_ICACHE)` は、その時点で D_DIRTY が消えている行についてだけ I_STALE を消す。
  - `fence.i` は何もしない。
- I_STALE の行から命令をフェッチしたら、**実機が古いバイト列を実行する代わりに、そこでエミュレーションを止めて報告する**（`--cache strict`。既定）。`--cache off` にすると、一貫したメモリとして振る舞う。
- 非キャッシュの別名（0x8FF0_0000〜）への書き込みは、D キャッシュを通らない。ただし I キャッシュには古い内容が残りうる（推測）。

### 2.3 実機と照らし合わせて決めたもの
- **ミスアラインのロード/ストアはハードウェアが処理する。** そう判断した根拠は次の 2 つ。
  - TRM の例外コードの一覧に 4（ロードのミスアライン）がない（01 §1、105 行目）。
  - 実機では、PMP で禁止された領域へのミスアラインのストア（`fault/store-text`、tval=0x4ff4000a）が、6（ミスアライン）ではなく 7（アクセスフォールト）になった（09 のログ）。
  - エミュレータの最初の版はミスアラインで 6 を返していた。そのため、このテストだけ実機と食い違ったことから分かった。
  - 6 は AMO（と LR/SC）のミスアラインにだけ使う（推測）。周辺レジスタへのミスアラインアクセスは、アクセスフォールトにする（判断）。
  - PMP の境界をまたぐミスアラインアクセスについては、エントリ全体に収まらなければ失敗とした。これは RISC-V 仕様どおりの扱いで、実機では未確認。
- **lock-up**: トラップを処理している間（トラップに入ってから mret まで）に ecall/ebreak 以外の例外が起きたら、CPU が止まる（TRM §2.13.5、01 §0）。割り込みで入った場合も同じ扱いにした（推測）。

### 2.4 単純化しているもの（既知の限界）
- F 拡張の演算は、丸めモードによらずホストの最近接偶数丸めで計算する。フラグは NV と DZ（と変換の NX）しか立てない。整数への変換（`fcvt.w[u].s`）だけは丸めモードと飽和を正しく扱う。
- PMA、APM、Core1、L2 キャッシュ、PSRAM、フラッシュの MMU、DMA は模していない。
- タイミングは「1 命令 1 サイクル」。フラッシュの XIP やキャッシュミスの遅れはない。
  - 実機で spin が 100ms に回った回数は 6627、エミュレータでは 4355（40MHz の場合）。おおよその桁は合っている。
- 割り込みの閾値と現在のレベルは、M モードのときだけ効くとした（U モードでは M の割り込みは常に有効）。実機のカーネルは閾値に 0 を書くので、まだ差は出ない（判断）。

## 3. 検証

### 3.1 RVC の展開を llvm-mc と全数で突き合わせた
- `emu/scripts/gen-rvc-table.sh` で参照表を作る。手順は次のとおり。
  1. 16 ビットの符号化をすべて llvm-mc 18 で逆アセンブルする（`+c,+f`）。
  2. 逆アセンブルした結果を C なしで再アセンブルし、等価な 32 ビット命令を得る。
- `T5EMU_RVC_TABLE=… cargo test` で、合法な 38,583 通りすべてを比べた。llvm-mc が受け付けない符号化は、こちらでも不正命令になることも確かめた。
- 例外として扱ったもの（意味が同じであることを確認したうえで許容した）:
  - `mv`: 再アセンブルすると `addi rd, rs, 0` になる。仕様の展開は `add rd, x0, rs`。
  - HINT（rd=x0 など）: 何の効果もないことだけを確かめた。
  - `c.lui rd, 0`: 仕様では予約で、こちらは不正命令にした。llvm-mc はこれを受け付ける。
  - 全 0（`unimp`）。
- 最初に手で書いた期待値には誤りがあった。全数の照合に切り替えたのは、そのため。

### 3.2 カーネルに不具合を入れて、エミュレータが検出するか確かめた
| 入れた不具合 | エミュレータの報告 |
|---|---|
| `sync_code` を `fence.i` だけにした（M1 の実機の不具合そのもの） | `fetch from 0x4ff40000, which was written through the D-cache without Cache_WriteBack_Addr + Cache_Invalidate_Addr`（終了コード 2） |
| 書き戻しと無効化の順番を逆にした | 同上 |
| RWDT を止めなかった | `RWDT expired`（2） |
| WPROTECT の鍵を書かずに RWDT を止めようとした | `RWDT expired`（2） |
| `yield` の syscall の処理中に、カーネルが 0x4 を読むようにした | `CPU lock-up: exception 5 at pc=0x40007784 tval=0x00000004 while handling a trap`（2） |

- いずれも、元に戻すと PASS（終了コード 0）になる。
- これまでの QEMU virt や実機で見つけた不具合のうち、キャッシュと RWDT のものは、QEMU virt では再現できなかった種類である（08 §3.2）。

### 3.3 単体テスト（`make test-emu`）
- PMP: TOR の連鎖、境界をまたぐアクセス、M モードの扱い、粒度と WARL、NAPOT の最小 128B、L ビット。
- キャッシュモデル: 書き戻しと無効化の順序。
- RVC: §3.1。

## 4. 分かったこと（設計への影響）

- **P4 では、カーネルの panic 経路がほとんど役に立たない。**
  - プロセスから最初にトラップしてから後のカーネルは、mret するまでずっと「トラップ処理中」である。この間にカーネルが例外を起こすと、P4 は `kernel_trap`（panic の表示）に入らずに lock-up する。
  - QEMU virt では同じ不具合が `KERNEL PANIC` と表示されるので、気づきにくい。
  - 対策の候補（判断。M3 以降で検討する）:
    - (1) カーネルのコードを、例外を起こさないように書く（ユーザポインタはソフトウェアで検査する。今もそうしている）。
    - (2) lock-up から復帰できるよう、RWDT などのウォッチドッグを止めずに使い、リセット後に原因を回収する（構造化ログの保存と組み合わせる）。
    - (3) カーネル内の不具合は t5emu の lock-up 検出で早く見つける。
- **ミスアラインアクセス**: §2.3 のとおり。01 §9 の未確認事項の一部が解消した。PMP の境界をまたぐ場合は、まだ確認していない。

## 5. 次にやること
- 構造化ログのサービスと連携する。RTT の制御ブロックを RAM から直接読み、ログを解読して合否を判定する。
- 命令単位の適合性テスト: riscv-tests（rv32ui/um/ua/uf）を流せるようにする。今は「カーネルが動く」ことと RVC の全数照合だけで、F 拡張の細部などは検証が薄い。
- ブートローダからの起動（espflash の app image を読み、2 セグメントのマッピングを模す）。
- 実機で確かめていない挙動を、実機で確認して反映する。対象は、PMP の境界をまたぐミスアライン、U モードでの閾値の効き方、割り込みで入ったトラップ中の lock-up。
