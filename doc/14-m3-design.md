# 14. M3 の設計案: フラッシュ上のアプリ、署名、ハンドル

- 日付: 2026-10-30
- 状態: ユーザーの確認済み（2026-10-30）。M3a から実装する。
- 目標（07 §7）: T5A、`elf2t5a`、`apps` パーティションからのロード、Ed25519 による検証、ハンドル、`open`/`read`/`write`/`wait`。完了条件は「**書き込んだアプリを、再起動なしで起動・終了できる**」。
- 前提として決まっていること: T5A の考え方（04 §1・§3）、アプリストア方式 A（05 §5.2）、ハンドルと `wait`（04 §4）、構造化ログ（12）。
- フラッシュの読み書きの手段は、[research/m3-flash-access.md](research/m3-flash-access.md) の調査をもとに §5 で決めた（主要な数値は ESP-IDF のソースで確かめた）。
- 事実には出典を付け、推測には「（推測）」、設計判断には「（判断）」と書く。

## 0. 要約（判断）

M3 を 4 段に分けて、この順で進める。

| 段 | 内容 | 完了条件 |
|---|---|---|
| M3a | T5A v1（TLV と Ed25519 の署名）、`elf2t5a` による署名、カーネルでの検証。アプリは今までどおりカーネルに埋め込む | 署名を検証してから起動する。改ざんしたもの、鍵の違うもの、ABI の合わないものを拒否するテストが通る |
| M3b | アプリストア（`appmeta` A/B と `apps` の 64KiB エクステント）を、フラッシュから**読む**。ホストのツールでパーティションのイメージを作り、espflash で書く | カーネルにアプリを埋め込まずに、フラッシュのアプリを起動できる |
| M3c | 制御チャネル（RTT の down チャネル）とコマンド（一覧、起動、停止、プロセス一覧）。カーネルは自己試験の後も動き続ける | `t5log` から、再起動なしでアプリを起動・停止できる |
| M3d | **インストール**: 制御チャネルで T5A を送る → カーネルが検証してから `apps`/`appmeta` に書く → 起動。あわせてハンドル表と `open`/`read`/`write`/`wait`/`close`（最初のオブジェクトはタイマ） | **07 の完了条件**: ホストから送ったアプリを、再起動なしで書き込み、起動し、終了させられる |

### 0.1 その先の段取り（ユーザーと合意、2026-10-30）
| 段 | アプリを動かす場所 | 大きさ |
|---|---|---|
| M3 | SRAM（L2MEM のアプリプール）にコピーする | 小さい（今は 1 スロット 96KiB） |
| M4a | PSRAM にまるごとコピーする（PSRAM は L2 キャッシュの後ろにあるので、L2 も同期する） | 大きい（32MiB） |
| M4b | XIP: text はフラッシュのページを MMU で対応付けてそのまま実行し、data と bss は PSRAM のページにコピーする。両者を、リンクしたときの距離のとおりに窓の中で隣り合わせに並べる（静的 PIE は text と data の距離が固定なので） | 大きく、RAM の消費が少なく、起動が速い |

- `apps` のエクステント（64KiB）は MMU のページの境界と一致する。そのため、M3 の配置のまま M4b に使える。ヘッダが text の前にあるが、PIE なので text はページの途中から始まってよい。

## 1. T5A v1（イメージ形式）

### 1.1 構成
```
+------------------------------+ 0
| 固定ヘッダ（48 バイト）       |
+------------------------------+ header_size
| TLV 領域                      |   tlv_size バイト
+------------------------------+
| イメージ本体（text+rodata+data）| image_size バイト（4 バイト境界から）
+------------------------------+
| 再配置表（Reloc[]）           |   reloc_count × 8 バイト
+------------------------------+ signed_size（ここまでが署名の対象）
| フッタ: 署名 TLV              |
+------------------------------+ total_size
```
- 固定ヘッダ（すべて LE）: `magic "T5A1"`、`header_version`、`header_size`、`tlv_size`、`image_size`、`text_size`、`mem_size`、`stack_size`、`entry`、`reloc_count`、`signed_size`、`total_size`。
  - v0 の `abi_major/minor` は TLV に移す（04 §1）。
- **署名の対象は `[0, signed_size)`**、つまりヘッダ、TLV、本体、再配置表のすべて。フッタだけを除く。
  - 長さや配置は検証した後でしか使わない。検証の前に読むのは、`signed_size` と `total_size` の範囲の確認だけにする（判断）。
- v0（`T5A0`、署名なし）の読み込みは、M3a で削除する（ABI は 1.0 より前なので）。

### 1.2 TLV（型は u16、長さは u16、値は 4 バイト境界に詰める）
| 型 | 名前 | 値 | 必須 |
|---|---|---|---|
| 0x01 | `Name` | UTF-8、1〜32 バイト。`[a-z0-9_-]` | ○ |
| 0x02 | `Version` | u32 ×3（major、minor、patch） | ○ |
| 0x03 | `AbiVersion` | u16 ×2（major、minor）。major が一致し、minor ≤ カーネルのときだけ起動する | ○ |
| 0x04 | `BuildId` | 16 バイト（ELF の SHA-256 の先頭。ログの `proc.start` と t5log の ELF を結び付ける） | ○ |
| 0x05 | `Permissions` | `open` を許す名前の並び（NUL 区切り。例: `timer`） | — |
| 0x06 | `Flags` | bit0 = 起動時に自動で起動する | — |
| 0x07 | `SecureVersion` | u32。これより小さいものへのダウングレードを拒む（05 §5.2） | — |
| 0x80 | `Signature`（フッタ） | `key_id`（8 バイト。公開鍵の SHA-512 の先頭）+ Ed25519 の署名（64 バイト） | ○ |

- 名前、版、権限は、アプリの `Cargo.toml` の `[package.metadata.t5a]` から `elf2t5a` が作る（04 §6 の案のとおり）。
- 未知の TLV 型は無視する。ただし 0x40〜0x7F は「理解できなければ拒否する」範囲として予約する（判断。将来の互換性のため）。

### 1.3 鍵と署名（判断）
- **Ed25519**。検証には `ed25519-compact`（no_std、依存なし）を使う候補にする（https://docs.rs/ed25519-compact ）。大きさと速さは t5emu と実機で測る。遅すぎるときは P4 の SHA アクセラレータを検討する（05 §5.3）。
- **開発用の鍵**:
  - `make keys` で生成する。秘密鍵は `~/.config/tab5-os/dev-ed25519.key` に置き、リポジトリには入れない。
  - 公開鍵は `keys/dev-ed25519.pub`（コミットする）。カーネルの build.rs が読み込んで埋め込む。
  - 本番用の鍵と、2 段の鍵（ルート鍵 → 署名鍵）は後回しにする。
- カーネルは `key_id` で、埋め込んだ鍵を選ぶ（M3 では 1 本だけ）。
- 署名ツールは `elf2t5a --sign KEY`。`elf2t5a` が作ったイメージを、そのまま検証まで試せるようにする（`elf2t5a verify`）。

### 1.4 検証の手順（カーネル）
1. 固定ヘッダの範囲の確認（`signed_size + フッタ ≤ total_size ≤ 置き場所の大きさ`）。
2. フッタの `key_id` → 公開鍵 → `[0, signed_size)` の署名を検証する。**ここまで、他の欄は信用しない。**
3. TLV を解析する（`AbiVersion`、`Name`、必須 TLV の有無、予約範囲の型）。
4. 既存のローダ（04 §3）で、コピー、0 埋め、再配置、キャッシュの同期をする。
- 結果は `loader.verified { name, version, build_id }` か、`loader.rejected { name, reason }` のイベントで出す。

## 2. アプリストア（05 §5.2 の具体化）

### 2.1 パーティション（既存の `boot/partitions.csv`）
- `appmeta`（0x410000、64KiB）: 先頭の 4KiB セクタ 2 つを A/B に使う。
- `apps`（0x420000、8MiB）: 64KiB のエクステント 128 個。1 つのアプリは連続した n 個のエクステントに置く。

### 2.2 appmeta のセクタ（4KiB）
```
magic "T5AM" | version | seq (u32) | count | entries[count] | crc32（セクタ全体）
entry: name[32] | extent_first (u16) | extent_count (u16) | length (u32) | version[3] | secure_version
       | state (u8: New / PendingVerify / Valid / Invalid) | flags | sha256[32]（T5A 全体）
```
- 2 つのセクタのうち、CRC が合い、seq が大きいほうを有効とする。どちらも無効なら「空のストア」として扱う。
- M3 では 1 アプリにつき 1 版だけにする。旧版を残す A/B 版とロールバックは M5 に回す（07 §7）。

### 2.3 ホストのツール（M3b）
- `t5store build -o build/store/ APP.t5a...` で、`appmeta.bin` と `apps.bin` を作る。`make flash-apps` は espflash `write-bin` で 0x410000 と 0x420000 に書く。
  - これは実機への書き込みで、旧ファームが残っている領域を上書きする。実施の前に確認を取る。
- `t5store list` でパーティションのイメージを読み、中身を表示する（検証にも使う）。

## 3. 制御チャネルとコマンド（M3c）

- **経路**: RTT の down チャネル 0（ホスト → カーネル）を 1KiB に広げる。将来は USB CDC の受信も同じ形式で受ける。
- **形式**: 上りのログと同じく COBS フレーム。中身は `u8 command | u32 request_id | 引数（TLV）`。
  - 応答とその後の出来事は、すべて構造化ログのイベントで返す（例: `ctl.done { request_id, ok, error }`、`store.app { name, version, state, ... }`、`proc.start` / `proc.exit`）。応答用の別の経路は作らない（判断）。
- **コマンド（初版）**:

  | 番号 | 名前 | 引数 | 結果 |
  |---|---|---|---|
  | 1 | `list` | — | `store.app` を件数分 |
  | 2 | `run` | name, arg0, arg1 | `proc.start` → いずれ `proc.exit` |
  | 3 | `kill` | pid | `proc.killed` |
  | 4 | `ps` | — | `proc.info` を件数分 |
  | 5 | `install_begin` / 6 `install_data` / 7 `install_end` | 長さ、名前 / オフセット、データ / — | `store.installed` か `store.rejected`（M3d） |
  | 8 | `remove` | name | `store.removed`（M3d） |

- **ホスト側**: `t5log rtt` に、標準入力の 1 行を 1 コマンドとして送る対話モードを足す（例: `run hello`、`install build/apps/hello.t5a`）。`t5log ctl --probe ... run hello` のような単発の実行もできるようにする。
- **カーネルの常駐**: これまでは自己試験の後に止まっていた。M3c からは、自己試験の後（または自己試験なしのビルドでは、すぐに）**スケジューラを止めずに動かし続ける**。自動起動のアプリを起動し、空き時間に制御チャネルを読む。
  - プロセスは、アプリプールを固定長のスロットに分けて置く（今の 4 つのまま。可変長の割り当ては後回し）。
- **セキュリティの前提（判断）**: 制御チャネルはデバッグ用の接続（JTAG、USB）の上にある。そのため「物理的に接続できる人は管理者」とみなす。ただし、インストールは署名を必ず検証するので、デバッガ経由でも未署名のアプリは入らない。JTAG を使えばメモリを直接書き換えられるので、これは開発用の境界である。

## 4. ハンドルと syscall（M3d）

- 04 §4 のとおり。プロセスごとに 16 エントリのハンドル表を持つ（M3 では 16 で足りる。判断）。エントリは `{kind, object, rights}`。
- **syscall（ABI 0.4）**:

  | 番号 | 名前 | 引数 → 戻り値 |
  |---|---|---|
  | 0x080 | `close` | h → – |
  | 0x082 | `wait` | handles_ptr, n, timeout_ns_lo, timeout_ns_hi → (index, event, value) |
  | 0x100 | `open` | name_ptr, name_len, rights → h（Permissions TLV に名前があるものだけ） |
  | 0x101 | `read` | h, buf, len → len |
  | 0x102 | `write` | h, buf, len → len |
  | 0x103 | `ctl` | h, op, a, b → 値 |

- **最初のオブジェクト**: `timer`。`ctl(h, SET_PERIODIC, ns)` で周期を設定し、`wait` で満了イベントを受ける。デバイス（I2C、表示など）は M6 で足す。
- `sleep` は `wait` で置き換えられるが、ABI は追加だけにする方針なので残す。
- 試験: 2 つのアプリが周期の違うタイマを `wait` して、イベントの回数と間隔を確かめる。Permissions にない名前の `open` が拒否されることも確かめる。

## 5. フラッシュの読み書き（調査結果: [research/m3-flash-access.md](research/m3-flash-access.md)）

### 5.1 読む（M3b）: MMU で対応付けて、キャッシュ経由で読む（判断）
- フラッシュの MMU のエントリは 1024 個で、1 個が 64KiB のページを受け持つ。合わせてフラッシュ窓 0x4000_0000〜0x43FF_FFFF を覆う（`soc/esp32p4/include/soc/ext_mem_defs.h:57-96`）。
- エントリの書き方:
  1. `SPI_MEM_C_MMU_ITEM_INDEX_REG`（0x5008_C380）にエントリの番号（`(vaddr & 0x3FF_FFFF) >> 16`）を書く。
  2. `SPI_MEM_C_MMU_ITEM_CONTENT_REG`（0x5008_C37C）に `(paddr >> 16) | BIT(12)`（有効ビット）を書く（`spi_mem_c_reg.h:2630,2642`）。
- 使う場所: ブートローダはカーネル（ota_0、最大 2MiB）にエントリ 0〜31 を使い、ほかにエントリ 1023 も使う（調査結果 §1）。カーネルは、**フラッシュ全体の 16MiB を 0x4100_0000 + paddr に線形に対応付ける**（エントリ 256〜511）。その結果、`apps` は 0x4142_0000、`appmeta` は 0x4141_0000 から読める。
- 対応付けを変える手順は、ESP-IDF の P4 での手順に合わせる。
  1. 分岐予測を止める。
  2. L2 キャッシュを止める（ROM の `Cache_Suspend_L2_Cache` 0x4FC0_0508）。
  3. エントリを書く。
  4. L1 I（両コア）、L1 D、L2 を無効化する（`Cache_Invalidate_Addr` 0x4FC0_03E4）。
  5. L2 を再開する（`Cache_Resume_L2_Cache` 0x4FC0_050C）。
- L1 は止めない（L2MEM が L1 を通るため）。この手順は、起動時に一度だけ行う。
- 署名の検証は、この窓の上で直接行う（コピーしない）。

### 5.2 書く（M3d）: L2MEM に置いた関数で、L2 キャッシュを止めて ROM を呼ぶ（判断）
- P4 には SPI0 と SPI1 の自動中断（auto suspend）がない（ESP-IDF の文書では「S3/C2/C3/C6/H2 のみ。P4 は将来」。`docs/en/api-reference/peripherals/spi_flash/spi_flash_optional_feature.rst:32-37`）。そのため、ROM の `esp_rom_spiflash_erase_sector`（0x4FC0_014C）や `esp_rom_spiflash_write`（0x4FC0_0154）を呼んでいる間は、フラッシュからの命令の取得とデータの読み出しを完全に止める必要がある。
- 手順（1 回の単位は、4KiB の消去か 256B の書き込み）。
  1. 割り込みを止めたまま（カーネルはもともと MIE=0）、分岐予測を止めて L2 を止める。
  2. ROM を呼ぶ。
  3. 書いた範囲の窓を無効化して、L2 を再開する。
  4. 単位ごとに RWDT に餌をやり、スケジューラに戻る余地を作る。
- **この関数、その呼び出し元のスタック、書く元のバッファは、すべて L2MEM に置く。** そのためにカーネルに `.ram_text` セクション（L2MEM、実行可能）を作る。ビルドのときに objdump で、そこからフラッシュ上の関数や定数（memcpy、パニック、ジャンプ表）を参照していないことを確かめる。
- ota_0/ota_1（カーネル）と、それより前の領域への書き込みは、API で拒否する。書けるのは `appmeta` と `apps` だけにする。
- 注意:
  - 1 回の消去のあいだは割り込みが止まる。フラッシュの品種によって数十〜数百 ms（推測）。プリエンプションが遅れることは許容する。
  - ROM のデータ領域は v1 では 0x4FF3_FFxx にある（`esp32p4.rom.ld:67-68,168-169`）。アプリプール（0x4FF4_0000〜）とカーネル RAM（〜0x4FF2_9000）は、これと重ならない。

### 5.3 t5emu
- M3b: フラッシュの MMU のレジスタ（エントリの書き込み、無効化）と、フラッシュ全体（16MiB）を模す。
- M3d: ROM の消去と書き込みを模す。**L2 を止めずに呼んだとき、またはフラッシュの窓から命令を取得している最中に呼んだときは、エラーで止める**。実機なら固まる誤りを検出するため。

### 5.4 実機で確かめること（M3b、M3d の中で行う）
- MMU のエントリのダンプ（ブートローダが使っている範囲）。線形の窓で読んだ内容と、`espflash read-flash` で読んだ内容が一致すること。
- フラッシュの JEDEC ID。4KiB の消去にかかる時間。割り込みを止めている時間。
- L2MEM の関数から Suspend/Resume を呼んで、正しく戻ってくること。
- 予備のセクタで、消去 → 書き込み → 無効化 → 読み出しが一周できること。

## 7. 確認したいこと
1. M3 を、上の 4 段（M3a → M3b → M3c → M3d）に分けて進めてよいか。
2. 制御チャネルを RTT の down チャネルにし、応答をすべて構造化ログのイベントで返す方針でよいか。
3. 開発用の鍵の置き場所（秘密鍵は `~/.config/tab5-os/`、公開鍵はリポジトリ）でよいか。
4. M3b で `appmeta`（0x410000）と `apps`（0x420000）の領域に書き込む許可（旧ファームの領域を上書きする）。その時点で改めて確認する。
