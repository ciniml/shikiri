# 15. M4b: アプリの text をフラッシュから直接実行する（XIP）

- 日付: 2026-10-30
- 状態: **実装し、実機で確認した（§6）**
- 前提: M3（T5A v1、アプリストア、フラッシュの MMU）、M4a（PSRAM、アプリを PSRAM にコピーして実行。doc/research/m4-psram-and-clock.md §9）
- 事実には出典を、推測には（推測）、設計判断には（判断）を付ける。

## 1. 制約: MMU の窓と対象は固定
- P4 の外部メモリの MMU は 2 つある。フラッシュの MMU は 0x4000_0000〜0x43FF_FFFF の窓を、PSRAM の MMU は 0x4800_0000〜0x4BFF_FFFF の窓を受け持つ。どちらの窓がどちらのメモリを指すかは固定で、フラッシュの窓のエントリが PSRAM のページを指すことはできない。エントリの形式も、フラッシュは有効ビットが bit12、PSRAM は bit11 と bit10（ACCESS_PSRAM）で別になっている [soc/esp32p4/include/soc/ext_mem_defs.h:57-96; hal/esp32p4/include/hal/mmu_ll.h:73-85]。
- 静的 PIE は、text から data を pc 相対（`auipc`）で参照する。そのため、**text と data の距離はリンクしたときのまま** でなければならない。
- 14 §0.1 では「text と data を窓の中で隣り合わせに並べる」と書いたが、上の制約によりできない。

## 2. 方針（判断）: data を text のちょうど 128MiB 上にリンクする
- 2 つの窓は、ちょうど 0x0800_0000（128MiB）離れている。アプリの data（.dynamic、.got、.data、.bss）を、**text のちょうど 0x0800_0000 上** にリンクする（`user/rt/t5app-xip.ld`）。text を窓のオフセット O に置けば、data は PSRAM の窓の同じオフセット O + (data の位置) に来る。
- **仮想アドレスの割り当て**（スロット k = 0〜3、各 8MiB）:

  | 範囲 | MMU | 中身 |
  |---|---|---|
  | 0x4000_0000〜0x401F_FFFF | フラッシュ 0〜31 | カーネル（ブートローダが設定） |
  | 0x4100_0000〜0x41FF_FFFF | フラッシュ 256〜511 | フラッシュ全体の線形マップ（M3b。署名の検証、ストアの読み出し） |
  | **0x4200_0000 + k × 8MiB** | フラッシュ 512〜1023 | **スロット k の XIP の text**。起動のたびに、そのアプリのエクステントを対応付ける |
  | 0x4800_0000〜0x49FF_FFFF | PSRAM 0〜511 | PSRAM 全体の線形マップ（M4a。コピー方式のスロット k は 0x4800_0000 + k × 8MiB） |
  | **0x4A00_0000〜0x4BFF_FFFF** | PSRAM 512〜1023 | **PSRAM 全体の 2 つ目の線形マップ**（起動時に固定）。スロット k の XIP の data は 0x4A00_0000 + k × 8MiB から |

  - XIP のスロット k の data は、コピー方式のスロット k と同じ物理ページ（物理 k × 8MiB〜）を、別の仮想アドレスから使う。1 つのスロットを使うのは、一度に 1 つのプロセスだけ。
  - **キャッシュの別名（エイリアス）**: 同じ物理ページを 2 つの仮想アドレスから使うので、スロットを読み込むときに、もう一方の別名の範囲を書き戻して無効化する（判断。キャッシュが仮想アドレスで引かれているかは確かめていないが、どちらでも安全な側に倒す）。
- **PMP**: text（R-X）と data + stack（RW-）が離れるので、TOR を 2 組使う（エントリ 1〜4）。text の先頭は、フラッシュ上の T5A の中の image の位置になる。PMP の粒度（128B）に合わせるため、elf2t5a は **image の先頭が 128B 境界に来るように TLV を詰め物で埋める**（エクステントは 64KiB 境界なので、仮想アドレスも 128B 境界になる）。

## 3. T5A の変更（判断）
- 新しい TLV `XIP_DATA`（0x40、**must understand**）: 値は u32 で、data のリンクアドレス（今は 0x0800_0000 だけを受け付ける）。この TLV を理解しないカーネルは、イメージを拒否する（14 §1.2 の規則）。
- image の中身は今までどおり「text（`text_size` バイト）の後に data の初期値」。data の初期値は、リンクアドレス `XIP_DATA` に置く。
- `mem_size` は「data の先頭からの、data + bss の大きさ」にする。再配置のオフセットは data の範囲（`XIP_DATA` 〜 `XIP_DATA + mem_size`）だけを許す。加数（addend）はリンクアドレスのどこを指してもよい。実行時のアドレスは、どれも「text の実行時の先頭 + リンクアドレス」になる。
- 詰め物の TLV `PAD`（0x08、理解しなくてよい）。
- XIP の TLV のないイメージは、今までどおりコピーして実行する。XIP のイメージをコピーして実行することはできない（data が窓の外に出るため）。

## 4. カーネルの変更
1. 起動時: PSRAM の MMU エントリ 512〜1023 を、物理 0〜32MiB に対応付ける（2 つ目の別名）。
2. ローダ（`load_xip`）:
   - フラッシュの線形マップの上で、署名を検証する。
   - スロット k のフラッシュの MMU エントリ（128 個）に、アプリのエクステントを対応付け、残りを無効にする。これは RAM 上の関数で、L2 を止めて行う（`map_flash_linear` と同じ手順）。そのあと、スロットの範囲を L1 I/D と L2 で無効化する。
   - data の初期値を `Vt + XIP_DATA` に書き、bss とスタックを 0 で埋め、再配置を当てる。そのあと、L1 D と L2 を書き戻す。もう一方の別名（0x4800_0000 + k × 8MiB）は、書き戻してから無効化する。
3. `Region` を `{ text: Range, data: Range }` にし、PMP の TOR を 2 組にする。
4. インストール: **動いている XIP プロセスが使っているエクステント** も「使用中」とみなす（`remove` の後に上書きされると、動いている text が変わってしまうため）。
5. t5emu: すでにフラッシュの MMU は 1024 エントリを模している。PSRAM の 2 つ目の別名も、PSRAM の MMU の 1024 エントリで扱える。L2 を止めずにフラッシュの MMU を書き換えたら、止めるようにする。

## 5. 試験
- `xipcheck`（新しいアプリ、XIP でリンク）: 512KiB の定数表（rodata）を持ち、合計を計算して、期待値と比べる。さらに、自分の pc がフラッシュのスロットの範囲にあること、data が PSRAM の範囲にあることを確かめる。
- `hello-xip`: hello を XIP でリンクしたもの。自己試験で、コピー方式と同じ結果になることを確かめる。
- 実機: 起動の自己試験に XIP の 2 件を足す。`install` した XIP アプリが動き、動いている間に `remove` → `install` しても、動いているアプリのエクステントが上書きされないこと。

## 6. 実装の記録（2026-10-30）

### 6.1 実装したもの
- `abi/src/t5a.rs`: TLV `XIP_DATA`（0x40）と `PAD`（0x08）、`XIP_DELTA` = 0x0800_0000。XIP のイメージは、image の位置が 128B 境界でなければ拒否する。
- `tools/elf2t5a`: 書き込み可能なセグメントが 0x0800_0000 から始まる ELF を XIP とみなす。text の後に data の初期値を詰めて image にし、`XIP_DATA` と詰め物の TLV を付ける。再配置は data の範囲だけを許す。
- `user/rt/t5app-xip.ld`（data を 0x0800_0000 に置く）。Makefile は、`XIP_APPS`（hello、xipcheck、spin）を `RUSTFLAGS` で XIP 用のリンカスクリプトに替えて、別の target ディレクトリに作る。`hello-xip.t5a`、`xipcheck.t5a`（ストアのイメージに入れる）、`spin-xip.t5a`（制御チャネルで入れる試験用）。
- カーネル:
  - ローダの入口を 1 つにした（`loader::load(bytes, &Slot)`）。XIP なら、フラッシュの線形の窓での位置からフラッシュのオフセットを求め、`Platform::map_xip` でスロットにページを対応付ける。data の初期値、bss、スタック、再配置は PSRAM の 2 つ目の別名の側に書く。
  - `map_flash_linear` を一般化して `map_flash_pages(first_entry, count, first_page, valid)` にした（`.ram_text`、384B）。起動時の線形マップと XIP のスロットの両方で使う。
  - PSRAM の MMU のエントリ 512〜1023 に、物理 0〜32MiB の 2 つ目の別名を作る。`Platform::retire_alias` で、使う前にもう一方の別名を書き戻して無効化する。
  - `pmp::Region` を `{ text, data }` にし、TOR を 2 組使う。ユーザのポインタの検査も、text と data を別々に見る。
  - インストール: 動いている XIP プロセスのエクステントを `install_begin` に渡し、空きの探索から外す（`store.install_begin` の `busy`）。
  - 自己試験 M4b: `hello`（コピー）、`hello-xip`、`xipcheck` を同時に動かす。ストアに XIP のアプリがないとき、または XIP のない環境（QEMU）では飛ばす。
- t5emu: 変更は不要だった（フラッシュの MMU の 1024 エントリと、PSRAM の MMU の 1024 エントリを、すでに模していた）。`make test-p4emu` に、XIP のアプリを動かしたまま `remove` → `install` する試験を足した（エクステントが上書きされると、t5emu では text が消えて `spin.done` が出ない）。

### 6.2 実機（Tab5）で確かめたこと（[logs/m4b-xip-tab5-20261030.txt](logs/m4b-xip-tab5-20261030.txt)）
- `hello-xip`、`xipcheck`、`spin-xip` を制御チャネルでインストールした（xipcheck は 138KB。消去 35 回、書き込み 557 回で 2.96 秒）。
- `spin-xip` を 2 秒動かしている間に `remove spin-xip` → `install greeter` を行った。greeter は、空いたはずのエクステント 11 ではなく 12 に入った（`busy=1`）。spin-xip は最後まで動き、0 で終わった（FP レジスタの不一致 0）。
- `xipcheck`: pc 0x4280_008A（フラッシュの窓のスロット 1）、表 0x4280_156C（フラッシュから直接読んだ）、data 0x4A80_00E8（PSRAM の 2 つ目の別名）。合計が期待値と一致した（`ok=true`）。
- リセットの後、**自己試験 24 件がすべて通った**（`hello-xip` と `xipcheck` を含む）。
- 署名の検証の時間は、イメージの大きさにほぼ比例する。7KB で 89ms、138KB で 475ms（SHA-512 に約 2.9ms/KB。CPU 90MHz、カーネルはフラッシュから XIP）。512KiB の表を持つ版は t5emu で 3 秒かかったので、試験用の表は 128KiB にした。

### 6.3 残っていること
- 大きなアプリの起動のたびに、全体の署名を検証している。インストールのときにだけ検証し、起動のときは省く（あるいはページごとのハッシュを持つ）方式を、M5（更新）で考える。M4c で CPU を 360MHz にし、138KB で 127ms になった（research/m4-psram-and-clock.md §10）。
- スロットは固定の 8MiB × 4。text も data も、スロットに収まらないアプリは動かせない。
- 同じアプリを 2 つのスロットで動かすと、text は同じフラッシュのページを 2 つの仮想アドレスから読む（読むだけなので問題はないと考えている。推測）。
