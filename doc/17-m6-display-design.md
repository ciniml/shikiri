# 17. M6 の設計: 表示とタッチ

M6 の目標（doc/07 §6）: **アプリが画面に描画する**。I2C → IO エクスパンダ → MIPI-DSI 表示 → アプリへのフレームバッファの提供、とタッチ入力。

調査は 2 つのノートにまとめた。この文書はそれをもとにした設計で、レジスタの値や出典はノートを参照する。
- [research/m6-dsi.md](research/m6-dsi.md): SoC 側（LDO VO3、クロック、DSI ホスト、D-PHY、DSI ブリッジ、DW-GDMA、キャッシュ）。§7 に順序つきのレジスタ操作の一覧。
- [research/m6-panel-touch.md](research/m6-panel-touch.md): ボード側（I2C1、IO エクスパンダ、パネルの判別、3 種類のパネルの初期化表とタイミング、バックライト、タッチ）。§7 に立ち上げの順序。

## 1. 段階

一度に全部を入れると、画面が出ないときにどこが悪いのか分からない。実機で 1 段ずつ確かめる。

| 段階 | 内容 | 実機で確かめること |
|---|---|---|
| M6a | I2C1 のドライバ（ポーリング）、IO エクスパンダ #1 でリセットを解除、パネルの判別、タッチの読み出し | `display.panel kind=st7123` などのイベント。画面を触ると `touch.point` が出る（カーネルが自己試験のあとでしばらく読む） |
| M6b | LDO VO3、DSI ホストと D-PHY、パネルの初期化、DW-GDMA でフレームバッファを送り続ける、バックライト | カーネルが描いた試験の絵（色の帯と枠）が出る。`display.frames` で 1 秒あたりのフレーム数（約 60） |
| M6c | アプリへの提供: `display` と `touch` のオブジェクト | 試験アプリ `paint` が、触ったところに描く |

M6a は I2C の読み書きと IO エクスパンダへの書き込みだけで、フラッシュには書かない。M6b はカーネルの更新（`make flash-kernel-p4`）だけで試せる。

## 2. 安全の約束（M6 の全体）
- **LDO VO1（フラッシュの 3.3V）には触れない。** VO3 は `EXT_LDO_P0_0P2A`（0x5011_51C0）と `_ANA`（0x5011_51C4）の 2 語だけを書く（m6-dsi.md §1）。PSRAM の VO2 のコード（`psram.rs`）を、チャネルを引数に取る形に一般化する。
- **IO エクスパンダ #2（0x44）は書かない。** bit4 のトグルは電源断になる（doc/06 §1.3）。#1（0x43）だけを書き、スピーカのアンプ（bit1）は切ったままにする。
- **DW-GDMA はソフトウェアリセットをまたいで動き続ける**（m6-dsi.md、IDF も再起動の前に全チャネルを止める）。カーネルのリセットの経路（`reboot`、kupdate のロールバック、`pending_verify` のパニック）すべてで、先に DMA を止める。`Platform::reset` の中で行う。
- 表示の初期化に失敗しても、カーネルは止まらずに表示なしで続ける（`display.failed` を出す）。自己試験の合否には、M6 の間は含めない（パネルを外した状態や、判別できないロットでも、更新とロールバックが働くように）。

## 3. メモリ
- フレームバッファは 720×1280×2 バイト = 1,843,200 バイト（1.76 MiB）。**PSRAM の末尾 4 MiB** を表示用に取り、アプリのプールは 28 MiB にする（スロットは 4 つのまま、1 つ 7 MiB）。4 MiB にするのは、あとで二重バッファ（2 枚で 3.5 MiB）にできるようにするため。
- DW-GDMA のリンクリストの項目（64 バイト）は、内部 SRAM のキャッシュしない別名（+0x4000_0000）に置く（m6-dsi.md §5、IDF と同じ）。
- 描いたあとは、L1 D と L2 をフレームバッファの範囲で書き戻す（ROM `Cache_WriteBack_Addr`）。アプリはキャッシュの操作ができないので、書き戻しは `ctl` の `FLUSH` でカーネルが行う。

## 4. 表示の更新の仕組み
- IDF と同じく、DW-GDMA の 1 チャネルが 1 フレームを送り終えると止まり、完了の割り込みで次のフレームを始める。カーネルに 2 つ目の割り込み（CLIC）を足す。割り込みの中では、チャネルを再び動かし、フレームの数を数えるだけにする。
- v1 の DSI ブリッジには VSYNC の割り込みがないので、DMA の完了をフレームの区切りとして使う（m6-dsi.md §6）。アプリには `wait` のイベント `display::FRAME` として渡す（描くタイミングを合わせたいアプリのため）。
- DMA の自動再読み込み（リンクリストを自分に戻す）で割り込みなしに回せるかは、M6b が動いたあとで試す（m6-dsi.md の未解決事項）。
- 画素のクロックは PLL_F240M ÷ 3 = 80MHz、レーンは 2 本で 1040Mbps（M5GFX の値）。PSRAM 用の MPLL（400MHz）とは別の系統なので、ぶつからない。ST7121 だけはレーンの速度が違う（900 か 965Mbps。未確定）ので、ST7121 は M6 では判別だけして、表示は後回しにする（手元の個体が ST7121 でなければ）。

## 5. パネルの判別（M6a）
m6-panel-touch.md §3 のとおり I2C で行う。
1. エクスパンダ #1 で LCD とタッチのリセットを解除する（GPIO23 を High にして待つ手順も含む）。
2. 0x55 の 16 ビットのレジスタ 0x0000 を読む（10ms おきに最大 600ms）。1 なら ST7121、3 なら ST7123。
3. 0x55 が答えなければ、0x14 がアドレスに ACK するかを見る。ACK すれば ILI9881C ＋ GT911。
4. どれでもなければ `display.unknown` を出して、表示は初期化しない。

DSI での ID の読み出し（ILI9881C: page1 の 00/01 = 98 81、ST7123: F4 = 71 23）は、M6b で確かめとして行う。

## 6. アプリへの API（M6c、ABI 0.7）
| 名前（Permissions） | 権利 | 操作 |
|---|---|---|
| `display` | CTL、WAIT | `ctl(MAP)` → フレームバッファの先頭アドレス（a1）。呼んだプロセスにだけ、その範囲の RW の PMP 領域を足す。`ctl(INFO)` → 幅・高さ・画素の形式（RGB565）。`ctl(FLUSH, y0 \| y1 << 16)` → その行の範囲をキャッシュから書き戻す。`wait` で `FRAME`（値 = フレームの数） |
| `touch` | READ、WAIT | `wait` で `TOUCH`（値 = 点の数、0 は指が離れた）。`read` で点の配列（各点 `u16 x, u16 y, u16 id, u16 size`、最大 5 点） |

- `display` を開けるのは同時に 1 プロセスだけ（2 つ目は `Busy`）。閉じるかプロセスが終われば、PMP の領域も外れる。
- PMP: 今は 1 プロセスあたり TOR の対を 2 つ（テキスト、データ）使う（`pmp.rs`）。3 つ目の対をフレームバッファに使う（エントリ 5〜6）。
- タッチは、カーネルが割り込みを使わずに、スケジューラの見回り（今の `POLL_MS`）で 16ms ごとに読む。INT（GPIO23）の割り込みは、電力が問題になってから考える。`touch` を開いたプロセスがいなければ読まない。
- 座標はパネルの向き（縦長、720×1280）のまま渡す。回転はアプリ側で行う。
- **画面の向き**（2026-10-31、利用者の確認）: 試験の絵は正しく出たが、**キーボードを付けると画面の向きが 180 度逆になる**（Tab5 をキーボードに差すと、パネルの本来の上下と逆向きに置かれる）。そこで、カーネルは「今の向き」（0/90/180/270）を 1 つ持ち、`display` の `ctl(INFO)` で返し、タッチの座標はその向きに変換して渡す（アプリは向きどおりに描けばよい）。フレームバッファの並びはパネルのまま（回転はアプリが描くときに行う。パネルの走査方向を MADCTL で変えられるかは未確認）。向きの決め方は、まず制御コマンド `rotate 0|90|180|270` で手で決め、次に IMU（BMI270、0x68）の重力の向きで自動にする。キーボードを付けた状態の `i2cscan` は付けないときと同じ 9 個（0x10、0x14、0x32、0x36、0x40、0x41、0x43、0x44、0x68）で、キーボードは内部の I2C には現れない（2026-10-31、実機）。
- `shm_map`（doc/07 の予定の 0x140 番）は作らず、`display` の `ctl(MAP)` で代える。共有メモリを一般のプロセス間でも使うようになったら、そのとき `shm_map` として切り出す。

## 7. 試験
- **QEMU（virt）**: 表示とタッチはない。`display` と `touch` は `NoDevice`。M6c の自己試験は飛ばす。
- **t5emu**: I2C1 に、0x55 で ST7123 として答える最小のモデルを足す。DSI ホストは状態のビット（コマンドの完了、PLL のロック、レーンの停止状態）だけを返し、DW-GDMA は一定の時間ごとに完了の割り込みを上げる。これで、初期化の手順（ポーリングの順序と時間切れ）と、割り込みでの再起動、アプリの API を試す。画素そのものは確かめない。
- **実機**: 段階ごとに、画面を見て確かめる（M6b は試験の絵、M6c は `paint`）。

## 8. 未解決のまま進めること
- 手元の Tab5 のパネルがどれか（M6a で分かる）。
- VO3 の eFuse の補正値と、ブートローダが VO3 をすでに入れているか（M6b の最初に読んで記録する）。
- ST7123 の SLPOUT と DISPON の順序（M5GFX と esp-bsp で違う）。M5GFX の順で始め、映らなければ入れ替える。
- PSRAM の帯域: 表示に約 120MB/s 使う（80MHz × 2 バイト × 有効画素の割合）。PSRAM の実測は書き込み 76MB/s、読み出し 66MB/s（CPU からの値。M4c）。DMA からの読み出しがこれより速いかは分からない。足りなければ、画素のクロックを下げる（フレーム数が減る）か、内部 SRAM に一部を置くことを考える（推測。M6b で `display.underrun` を数えて判断する）。
- IO エクスパンダ #2 を書かないと、充電が止まったままかもしれない（m6-panel-touch.md の未解決事項）。M6a で充電の状態（#2 の入力）を読んで記録する。

## 9. M6a の実装の記録（2026-10-31）
- カーネル: `platform/esp32p4v1/i2c.rs`（I2C1、ポーリング、100kHz）、`platform/esp32p4v1/tab5.rs`（エクスパンダ #1、GPIO23、判別、タッチの読み出し）。`Platform::board_init` を `clock_init` のあとに呼び、`board.ready panel=…` を出す。制御コマンド `touch SECONDS`（16ms ごとに読み、点が現れたか動いたら `touch.point`、離れたら `touch.up`）と `i2cscan`。
- t5emu: I2C1 と、エクスパンダ 2 つ、ST7123 のタッチ（固定の 1 点を返す）のモデル。**エクスパンダ #2 へのレジスタの書き込みがあれば失敗にする**。`test-p4emu` に、判別・`i2cscan`・`touch` の回を足した。
- 実機: **手元の Tab5 は初期ロット（ILI9881C ＋ GT911、0x14）**。エクスパンダ #1/#2 の 0x01 は 0xA0（電源投入後に一度読まれて bit1 が消えた値）。`i2cscan` で答えたのは 0x10（ES8388）、0x14（GT911）、0x32（RX8130）、0x36（カメラ）、0x40（ES7210）、0x41（INA226）、0x43、0x44、0x68（BMI270）。判別は 1 回目で決まり、エクスパンダの解除から判別まで約 115ms。
- **見つけた問題: NACK のあとのバスクリアで GT911 が応答しなくなる。** 最初の実装は、NACK でも FSM リセットとバスクリア（SCL を 9 回）をしていた。`i2cscan`（約 100 回の NACK）や、判別のあとの 0x5D などへの問い合わせのあと、GT911 は 0x14 に答えなくなり、次のリセットまで戻らなかった。最初は INT を Low にする手順（M5GFX の `wakeup()`）が原因に見えたが、間に入れた問い合わせの NACK のほうが原因だった。ESP-IDF は NACK では、バスが空くのを待つだけで、リセットもバスクリアもしない（`esp_driver_i2c/i2c_master.c:591-604`）。同じにしたら、`i2cscan` のあとも、`wakeup()` のあとも、GT911 は答え続けた。バスクリアは、時間切れなどのバスの異常のときだけにした。
- エクスパンダ #2 の入力（0x0F）は 0 だった（CHG_STAT は Low）。充電が止まっているかどうかは、まだ判断していない（§8）。
- タッチ（実機、利用者が画面に触れて確認）: `touch 15` で 750 回読み、エラー 0。なぞると 20ms ごとに `touch.point` が続き、指を離すと `touch.up`。座標は x 251〜428、y 301〜1002 で、パネルの縦長の範囲（720×1280）に収まった。
- **t5log の修正**: このときの `touch 15` の `ctl.done` が届かず、t5log は 30 秒後に「答えがない」で終わった。カーネルは、読む人がいない間に RTT の上りバッファが一杯になると新しいフレームを捨てる（`log.dropped sink=rtt count=12`）。t5log がつないですぐコマンドを送ったので、その答えが捨てられた。t5log は、上りのチャネルを一度読み切ってから（読んで 0 バイトになってから）コマンドを送るようにした。

## 10. M6b の実装の記録（2026-10-31）
- カーネル: `platform/esp32p4v1/display.rs`。m6-dsi.md §7 の順（VO3 → DSI ホストと D-PHY → 80ms → DW-GDMA → ブリッジとタイミング → ILI9881C の初期化表 → 試験の絵 → DMA 開始 → 映像モード → バックライト）。フレームバッファは PSRAM の末尾 4MiB の先頭（0x49C0_0000）。アプリのプールは 28MiB（スロット 7MiB）。
- フレームごとの再開: DW-GDMA の割り込み（ソース 24 → CPU 線 2）を CLIC で有効にし、プロセスの実行中なら `Platform::handle_irq` で、カーネルの中ではスケジューラのループの先頭（`display_service`）で、`DMA_TFR_DONE` を見て次のフレームを始める。カーネルが長く止まる処理（自己試験のイメージの検証など）の間は再開が遅れ、フレーム数が下がる（自己試験中は約 34fps）。
- `Platform::reset` は、ソフトウェアリセットの前に DMA のチャネルを止める（abort）。
- 制御コマンド `display`: フレーム数、アンダーラン、fps を出す。
- t5emu: DSI ホスト（PHY のロック、空の FIFO）と DW-GDMA（1 フレームの時間で完了し、割り込みを上げる）のモデル。タッチのモデルは手元の実機と同じ GT911（0x14）にした。`test-p4emu` の M6 の回で `display.ready` と `display.stats` を確かめる。
- 実機の結果（[logs/m6b-display-tab5-20261031.txt](logs/m6b-display-tab5-20261031.txt)）:
  - VO3: eFuse の補正（K=21、Vos=4、C=34）で探索すると dref=9、mul=6 で 2474mV（較正なしなら 2500mV）。起動時の P0_0P2A は 0x4020_0000 系で、XPD は 0（ブートローダは VO3 を入れていない）。
  - D-PHY はロックし、レーンは stop 状態になった。`display.id` は 0x98、0x81（ILI9881C の page 1 の ID）。DSI の読み出しも動いた。
  - 初期化から表示開始まで 257ms。自己試験の後の `display` で、1.13 秒に 72 フレーム = **約 64fps**（計算値 64.3Hz）、アンダーラン 0。
- **ちらつき（利用者の報告）と、その対策**: 最初の実装は IDF と同じく、1 個の LLI でフレームごとに DMA が止まり、割り込みかスケジューラのループで再開していた。フレームの開始の間隔を測ると、カーネルが 20ms 以上自分の処理をしている間（自己試験のイメージの検証は 1 個 23ms、138KiB の xipcheck は 127ms）と、プローブがつながる瞬間に、間隔が 20〜180ms に延びていた（自己試験中に 11 回、つなぐたびに 0〜2 回。何もつながない 30 秒は 0 回で 64.3fps）。再開が垂直帰線（約 0.5ms）に間に合わないとフレームが抜け、画面がちらつく。
  - DW-GDMA の「リロード」モード（CFG0 の種別 1）は、最初のブロックのあと BLOCK_TFR_DONE を出さずに止まった（DST_TRANSCOMP だけ立つ）。
  - LLI を自分に向けると、DMA は使った LLI の VALID を 0 に書き戻し、次に読んだときに無効として止まった（INTSTATUS の bit13 `SHADOWREG_OR_LLI_INVALID_ERR`）。
  - **採用: 16 個の LLI の輪**。各 LLI は 1 フレーム分で、次の LLI を指し、LAST は立てず、`IOC_BLKTFR`（CTL の bit58）でフレームごとに割り込みを出す。`service` は、割り込み（またはスケジューラのループ）で、VALID が 0 になった LLI を立て直す。CPU の締め切りは 0.5ms から 15 フレーム（約 230ms）に延びた。それでも間に合わず無効な LLI で止まったら、チャネルを止めて輪の先頭から始め直す（`restarts` で数える）。
  - 結果: 自己試験と xipcheck の実行を含めて `restarts=0`、アンダーラン 0。`frames` は割り込みの回数なので、カーネルが忙しい間に重なったフレームは 1 回に数えられ、実際より少なく出る（下限）。
- `psram_init` の前に、前の起動から動いている DMA があれば止める（`display.dma_was_running`）。プローブのリセットのあとでは見られなかった（プローブのリセットで DMA も止まるらしい。推測）。
- 未解決: `t5log rtt --reset` で、前の起動のログの再生と今回の起動の境目のフレームが壊れることがある（`undecodable frame`。3 回に 2 回）。境目の `log.prev_end` が壊れると、t5log は今回の起動の行も `prev#` と表示する。表示と関係があるかは未確認。

## 11. M6c の実装の記録（2026-10-31）
- ABI 0.7: `t5_abi::display`（`INFO`、`MAP`、`FLUSH`、`ORIENTATION`、wait の `FRAME`）と `t5_abi::touch`（`read` で 1 点 8 バイト × 最大 5、wait の `CHANGED`）。制御コマンド `rotate 0|90|180|270`。
- カーネル: `screen.rs`（向き、タッチの状態、display の持ち主）。`display` を開けるのは 1 つだけ（2 つ目は `Busy`）。`ctl(MAP)` で、そのプロセスの PMP にフレームバッファの RW の領域（エントリ 5〜6 の TOR）を足す。ハンドルを閉じるかプロセスが終わると外れる。`touch` を開いているプロセスがいる間だけ、カーネルは 16ms ごとにタッチを読み、向きに合わせた座標にして渡す。
- `t5-rt`: `Display`（`open` で開いて写像し、`put`/`rect`/`fill` はユーザから見た座標で描く。向きの変換はタッチの逆）、`Touch`、`rgb`。
- アプリ `paint`（`--permit display --permit touch`）: モード 0 は、上端（ユーザから見た上）に青い帯と左上の白い四角を描き、指の下に四角を描く。モード 1 は自己試験（2 つ目の open が `Busy`、写像したフレームバッファに書ける、`FLUSH` の範囲の検査、`FRAME` が 3 つ来る、`touch` が読める、`touch` への `write` は `Denied`）。
- 自己試験 M6c: `paint` の自己試験と、`display` を開いていない `fault` がフレームバッファに書くと store access fault になること。表示がない（QEMU）か `paint` がストアにないときは飛ばす。
- t5emu: `test-p4emu` で、`rotate 180` のあと `run paint 0 1` が `paint.done` まで動くことを確かめる。
