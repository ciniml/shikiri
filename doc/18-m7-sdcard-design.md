# 18. M7 の設計: microSD とファイル

M7 の目標: **アプリがファイルを読み書きできる**。microSD のカードをカーネルがセクタ単位で扱い、FAT は U モードのサービスが扱う。

調査: [research/m7-sdcard.md](research/m7-sdcard.md)（ピン、電源、SDMMC ホスト、クロック、コマンド、IDMAC、キャッシュ、ファイルシステムの候補）。レジスタの値と出典はそちら。

## 1. 前提（調査から）
- ピンは CLK=GPIO43、CMD=GPIO44、D0〜D3=GPIO39〜42 の 4 ビット。IO_MUX の機能 0 に固定（GPIO マトリクスを通らない）。外付けのプルアップがある。
- **カードの電源は SOC_3.3V に直結で、切り替えられない**。VO1（フラッシュ）にも IO エクスパンダ #2 にも関係しない。M5Stack の BSP が入れている LDO VO4 は、Tab5 の回路図では使われていないので触らない。
- カードの抜き差しの検出はない（Detect は未接続）。
- 電源を切れないので、カードを 1.8V に切り替える CMD11 は**決して送らない**（戻すには電源を切るしかない）。3.3V の Default Speed（25MHz）と High Speed（50MHz）だけを使う。
- SDMMC のクロック源は PLL_F160M（SPLL 系）で、PSRAM の MPLL とは独立。

## 2. 段階
| 段階 | 内容 | 実機で確かめること |
|---|---|---|
| M7a | SDMMC ホストの初期化、カードの初期化（400kHz、1 ビット）、**セクタ 0 の読み出し**（まず FIFO のポーリング、だめなら IDMAC）。制御コマンド `sdinfo`（CID/CSD/容量）と `sdread LBA`（16 進のダンプをイベントで） | カードの種類と容量が出る。セクタ 0 の末尾が 0x55AA で、パーティション表が読める |
| M7b | 4 ビット、20→40MHz、IDMAC での複数セクタの読み書き。カーネルのオブジェクト `sd`（セクタ単位） | 速度の測定。**書き込みは試験用の領域だけ**（§4） |
| M7c | U モードのファイルサービス `fs`（`embedded-sdmmc` 0.10、FAT16/32）。ほかのアプリはチャネル `chan:fs` で open/read/write/list を頼む | アプリがファイルを作って読み戻す |

## 3. カーネルの `sd` オブジェクト（M7b、ABI 0.8）
- `open("sd")`（Permissions に `sd`）。持てるのは同時に 1 つ（ファイルサービスだけに許す想定）。
- `ctl(INFO)` → セクタ数（下位 32 ビット。SDXC の 2TB まで足りる）。`ctl(SEEK, lba)`。
- `read`/`write` は 512 バイトの倍数で、今の位置から読み書きし、位置を進める。1 回に最大 4KiB（カーネルの中の、64 バイト境界にそろえたバッファを通す。キャッシュの書き戻しと無効化はカーネルが行う）。
- 待たせ方: まずはカーネルが転送の終わりをその場で待つ（4KiB を 40MHz・4 ビットで約 0.2ms＋カードの遅延）。カードの書き込みの busy が長いとき（数十〜数百 ms）は、プロセスを待ち状態にして、スケジューラのループで終わりを見る（`wait` と同じ形）。

## 4. 安全の約束
- **カードの中身は利用者のもの**。M7a は読むだけ。M7b の書き込みの試験は、利用者が試験に使ってよいと言ったカードか、カードの上の決めた場所（たとえば FAT の中の試験用のファイルの領域、または最後のパーティションの外の未使用の末尾）だけにする。どちらにするかは実装の前に利用者に確認する。
- VO1、VO4、IO エクスパンダ #2 には触れない。
- カードがない・応答しないときは、`sd.absent` を出して先へ進む（自己試験の合否に入れない）。

## 5. ファイルサービス（M7c）
- `embedded-sdmmc`: no_std、alloc なし、FAT16/32。作れるファイル名は 8.3 だけ（長い名前は読めるが作れない）。exFAT は読めない（32GB を超えるカードは FAT32 に初期化し直す必要がある）。`fatfs` は no_std に古い nightly の `core_io` が要るので使わない。
- サービスは `sd` を開き、`embedded-sdmmc` の `BlockDevice` を `sd` の read/write で実装する。ほかのアプリとの間は `chan:fs`。メッセージ 256 バイトの中に、要求（op、ハンドル、長さ、名前）とデータ（最大約 240 バイト）を入れる。大きいデータは遅い（後で共有メモリにする）。
- 自動起動（flags の autostart）で起動しておく。

## 6. 試験
- t5emu: SDMMC ホストとカードの最小のモデル（コマンドへの応答、512 バイトのセクタを持つ小さいディスクイメージ。`--sd FILE` で与える）。カーネルの初期化の手順とセクタの読み書き、ファイルサービスを試す。
- QEMU（virt）: `sd` は `NoDevice`。
- 実機: §2 の各段階。

## 7. 未解決のまま進めること
調査の §9 のとおり。とくに、FIFO のポーリングで読めるか（IDF は常に DMA）、カード検出の入力を「挿入」に固定する設定でコマンドが通るか、136 ビットの応答の語順、40MHz が安定するか。

## 8. M7a の実装の記録（2026-10-31）
- カーネル: `platform/esp32p4v1/sd.rs`。m7-sdcard.md §8 の 2〜17（クロックとリセット、ホストのリセット、IO、カード検出の入力を「挿入」に固定、400kHz、CMD0/8、ACMD41、CMD2/3/9/7）。カードは最初の `sdinfo` で初期化する（起動の時間を延ばさない）。制御コマンド `sdinfo`（カードの情報とセクタ 0 のパーティション表）、`sdread LBA`（1 セクタを 32 バイトずつイベントで）。
- 実機: カードは SanDisk の SDHC（`mid=3`、名前 `SK32G`、CSD v2、62,333,952 セクタ = 約 30GB）。ACMD41 は 19 回目（約 0.2 秒）で準備完了、CCS = 1（セクタ単位のアドレス）。
- **FIFO を CPU で読めない**: 最初は調査のとおり FIFO（+0x200）をポーリングで読んだが、何回読んでも同じ語（セクタの先頭 4 バイト `FA B8 00 10`）が返り、STATUS の fifo_count は 128 語のまま減らなかった。+0x200〜0x3FF の連続したアドレスで読んでも同じ。ESP-IDF も CPU で FIFO を読むことはない（常に IDMAC）。そこで **データは最初から IDMAC で受ける** ようにした（内部 SRAM の 64 バイト境界のバッファと記述子。記述子は非キャッシュの別名から書き、読んだあとバッファのキャッシュを無効化する）。
- 結果: セクタ 0 は MBR（署名 0x55AA）。パーティション 0 は FAT32（0x0C、開始 16384、512MiB）、1 は Linux（0x83、約 29.9GB）。1 ビット・400kHz で 1 セクタ約 11ms。
- 利用者の了解: このカードは自由に使ってよい（中身を消してよい）。

## 9. M7b（ドライバの部分）の記録（2026-10-31）
- 初期化の続き（m7-sdcard.md §4 の 9〜14）: ACMD51 で SCR を読み、4 ビットに対応していれば ACMD6 で 4 ビットにして D3 を SD の機能に戻す → 20MHz（1 段目 ÷8、2 段目なし）→ CMD6（mode 1、group 1 = High Speed）が通れば 40MHz（÷4）。速度を変える前と後でセクタ 0 を読み比べる。
- 読み書き: CMD17/18（1 セクタ / 複数）、CMD24/25。複数は auto-stop（ホストが CMD12 を出す）。1 回は最大 4KiB（8 セクタ。内部 SRAM の受け渡し用のバッファ）。書き込みのあとは STATUS の data_busy が落ちるのを待ち、CMD13 で tran かつ READY_FOR_DATA を待つ。
- 制御コマンド `sdtest`: 試験用のセクタ 8192〜8199（MBR と最初のパーティション（16384〜）の間の空き）を読んで保存し、模様を書いて読み比べ、FAT のパーティションの先頭から 256KiB を読む時間と、試験用のセクタに 256KiB を書く時間を測り、最後に元の中身を書き戻して読み比べる。
- 実機: SCR は SD 3.0（`scr_spec=2`）、4 ビットと High Speed に切り替わり 40MHz。ACMD41 は 2 回目で準備完了（カードは前の起動から電源が入ったまま）。セクタ 0 の読み出しは 11ms から 0.43ms に。`sdtest`: 模様の読み比べ一致、元に戻せた。**読み 5.4MB/s、書き 3.3MB/s**（4KiB ずつ。転送ごとにコマンドを出し、書き込みは毎回カードの完了を待つので、大きいまとまりならもっと速いはず。推測）。

## 10. M7c の記録（2026-10-31）
- カーネル: `sd` オブジェクト（ABI 0.10。権限 `sd`、開けるのは 1 つだけ）。`ctl(SECTORS)`、`ctl(SEEK, lba)`、`read`/`write` は 512 バイトの倍数で最大 4KiB（`sd::MAX_IO`）。`read`/`write` のカーネルのバッファを 256 バイトから 4KiB にした（チャネルは 256 バイトを超えるメッセージを自分で断る）。
- ファイルサービス `fs`（`--permit sd --permit shm --permit listen:fs`、スタック 32KiB）: `embedded-sdmmc` 0.10 の `VolumeManager`（同時に開くファイル 8、ディレクトリ 4）で最初のパーティションを扱う。`BlockDevice` は `sd` の SEEK と read/write（4KiB ずつ）。クライアント 4 人まで、各 64KiB の共有メモリを渡す。プロトコルは `t5_abi::fs`（要求 12 バイト＋パス、返事 12 バイト。OPEN/READ/WRITE/SEEK/CLOSE/LIST/DELETE/MKDIR）。クライアントが去ったら、その人が開いたままのファイルを閉じる。
- `t5-rt` の `Files`（`connect`、`open`、`read`、`write`、`seek`、`close`、`list`、`delete`、`mkdir`）。試験アプリ `fstest`（`--permit svc:fs`）。
- **時計がない**ので、ファイルの日時は固定（2026-10-31 12:00）。RTC（RX8130、I2C の 0x32）を読めるようになったら直す。
- 実機（利用者が `fs` と `fstest` をインストールして実行）: FAT32 のルートの 53 項目（Raspberry Pi の boot パーティション。長い名前は `BCM271~1.DTB` のように 8.3 で見える）を列挙。`T5OS/TEST.BIN`（102,400 バイト）を書いて読み比べ一致、`DEL.TXT` の作成と削除、`T5OS` の列挙が正しかった。**書き 1.1 秒（約 90KB/s）、読み 0.1 秒（約 1MB/s）**。書きが遅いのは、`embedded-sdmmc` がブロックごとに書き、FAT やディレクトリも都度書き直すためと考えている（推測）。
- 残り: t5emu の SD のモデル（自動の試験で M7 を通すため）、書き込みの速さ、RTC。
