# 23. N3: リンク間の転送、経路表、ICMP のエラー、待ち受けの指定

[research/net-stack.md](research/net-stack.md) §3.3 と §4 の段階 N3。`net`（U モードのネットワークサービス）が、自分あてでないパケットをリンクの間で転送する。あわせて、ソケットの待ち受けを「すべてのリンク」「アドレス指定」「リンク指定」で選べるようにした。

利用者の判断（2026-11-01）: 待ち受けは「アドレスを指定しなければすべてのリンク」「アドレスやリンクを指定して限る」の両方が要る。

## 1. 区切りと状態
| 内容 | 状態 |
|---|---|
| `net` をリンクのデバイス（`link.rs`）、転送（`fwd.rs`）、試験用 LAN（`testlan.rs`）、本体（`main.rs`）に分けた | 済み |
| 転送面、経路表（最長一致）、ARP の表、TTL、ICMP の Time Exceeded と Destination Unreachable | t5emu で確認（§6） |
| 待ち受け（TCP_LISTEN、UDP_BIND）のアドレスとリンクの指定、すべてのリンクでの待ち受け | 実機で Wi-Fi 側の待ち受けを確認（§6） |
| 実機での転送（PC → Tab5 → 試験用 LAN） | 未。PC に経路を足す必要がある（root、§6.3） |

## 2. リンクとインタフェース
smoltcp の `Interface` は種類ごとに 1 つ。番号は `fwd::IFACE0`、`WLAN`、`TEST`。

| インタフェース | リンク | アドレス | デバイス |
|---|---|---|---|
| 0（`Medium::Ip`） | ループバック、ホストリンク（`netdev:host`） | 127.0.0.1/8、10.55.0.2/24 | `link::Links` |
| 1（Ethernet） | Wi-Fi（`netdev:wlan0`） | DHCP | `link::EthNic`（`Port::Dev`） |
| 2（Ethernet） | 試験用 LAN `test0`（`run net 1` のときだけ） | 192.168.50.1/24 | `link::EthNic`（`Port::Test`） |

- **受信の振り分け**: デバイスの `receive()` が 1 フレームずつ見る。自分あてでない IPv4 は、smoltcp に渡さずに転送の受信箱（`fwd::inbox`、8 フレーム）に入れる。
  - 「自分あて」とは、宛先がそのリンクのアドレス、255.255.255.255、そのサブネットのブロードキャスト、マルチキャスト、127/8 のどれかであること。リンクにまだアドレスがない間（DHCP の途中）は、すべて自分あてとする。DHCP の OFFER は、配るアドレスあてに来るため。
  - Ethernet では、自分の MAC あてのフレームだけを転送の対象にする。
- **ARP**: Ethernet のデバイスは、通る ARP の送信元（IP と MAC）を ARP の表（32 項目、寿命 300 秒）に覚える。smoltcp にもそのまま渡す。smoltcp は自分の近隣の表を外に見せないので、転送用にはこの表を別に持つ（判断）。

## 3. 転送（`fwd.rs`）
`Stack::poll` は、各インタフェースの処理、試験用 LAN の相手の処理、`Stack::forward` を、何も動かなくなるまで（最大 8 回）繰り返す。転送したパケットには、ARP や相手の応答のためにもう 1 回りが要るため。

- **経路表**: 各リンクのアドレスとプレフィックスから作る直結の経路と、Wi-Fi の DHCP で得た既定の経路のうち、プレフィックスが最長のものを使う。127/8 は経路を持たない。設定ファイルからの静的な経路はまだない（§7）。
- **処理**: IPv4 のヘッダを確かめ、TTL が 1 以下なら ICMP Time Exceeded を返す。経路がなければ ICMP Destination Unreachable（code 0、network unreachable）を返す。それ以外は TTL を 1 減らし、ヘッダのチェックサムを計算し直して、出口のリンクへ送る。
  - ホストリンクには IP パケットのまま書く。
  - Ethernet のリンクでは、次の段の MAC を ARP の表で引いて、ヘッダを付ける。表になければ、ARP の要求を出し、パケットを最大 4 個、1 秒まで待たせる。
- **ICMP のエラー**: 入ってきたリンクの自分のアドレスから、元のパケットの送信元へ送る。中身は元の IP ヘッダと、その後の 8 バイト（RFC 792）。ICMP のエラーへのエラーと、送信元がブロードキャストやマルチキャストのものには返さない。1 秒に 10 個まで。
- **記録**: 30 秒ごとに、数が変わっていれば `net.fwd`（forwarded、no_route、ttl_expired、no_arp、dropped、icmp_sent、icmp_limited）を出す。
- 断片化はしない。MTU は全リンク 1500 にそろえる（research §3.3 のとおり）。

## 4. 試験用 LAN（`testlan.rs`、`run net 1`）
2 本目の本物のネットワークがない所（t5emu、ホストリンクしかない Tab5）で転送を確かめるための、`net` の中のリンク。

- `net` の側は `test0`（192.168.50.1/24、MAC 02:74:35:00:00:01）。
- 相手は `net` の中の別の smoltcp（192.168.50.2/24、MAC 02:74:35:00:00:02、既定の経路は 192.168.50.1）。2 つの間は、向きごとに 8 フレームのリングでつなぐ。
- 相手は ping に答え（smoltcp の `auto-icmp-echo-reply`）、TCP の 7777 番で受け取ったものを送り返す。
- カーネルに仮想の Ethernet の対を置く案は、カーネルの RAM（内部 SRAM）に余裕がないのでやめた（判断）。転送の処理はすべて `net` の中にあるので、試験の対象は変わらない。
- `run net` の引数: 第 1 引数が 256 未満ならフラグ（bit0 = 試験用 LAN）。256 以上なら、従来どおり Wi-Fi の静的なアドレスとルータ（doc/22 §7）。

## 5. 待ち受けの指定（`abi/src/net.rs`）
`TCP_LISTEN` と `UDP_BIND` は、`a` にローカルのアドレス（0 = 指定なし）、`b` に `port | link << 16` をとる。

| 指定 | 待ち受ける所 |
|---|---|
| アドレス 0、`link::ANY` | すべてのインタフェース（インタフェースごとに smoltcp のソケットを 1 つずつ） |
| アドレスあり | そのアドレスを持つリンクのインタフェースで、そのアドレスだけ（ない場合は `NO_ADDRESS`） |
| `link::LO` / `HOST` | インタフェース 0 で、127.0.0.1 / 10.55.0.2 だけ |
| `link::WLAN0` / `TEST0` | そのインタフェース（アドレスは問わない。DHCP で変わるため） |

- すべてのリンクで待ち受けた TCP は、どれかに接続が来たら、そのソケットが接続になり、ほかのリンクの待ち受けは閉じる。これまでどおり、待ち受けのソケットがそのまま接続になる（accept はない）。
- すべてのリンクで bind した UDP は、受信はどのリンクからも受け取る。送信は宛先の経路のリンクのソケットから出す。
- 接続（`TCP_CONNECT`）、`PING`、`UDP_SEND` の出口は、経路表で決める（以前は「127/8 と 10.55.0.0/24 以外は Wi-Fi」と決め打ちだった）。
- ソケットのバッファは、クライアントのソケット（8 個）ではなく、smoltcp のソケットごとのプール（16 個）にした。すべてのリンクで待ち受けると、インタフェースの数だけ使う。`net` のスタックは 64 KiB にした（`Stack` が転送の待ちのバッファを持つため）。
- `t5-rt` に `Net::tcp_listen_at(addr, link, port)` と `udp_bind_at` を足した。`tcp_listen(port)` と `udp_bind(port)` は「すべてのリンク」になった。

## 6. 結果
### 6.1 t5emu（`make test-p4emu`）
t5emu の PC 役（`hostpeer`）に、相手のアドレス（`--host-peer-target`）と始める合図のイベント（`--host-peer-start`）を足した。相手が 10.55.0.2 以外なら、10.55.0.2 を既定の経路として Tab5 を通る。`run net 1` で試験用 LAN の相手（192.168.50.2）を相手にした結果:

```
t5emu: host peer: ping [4.0, 2.0, 2.0] ms, TCP echo in 65 ms, ICMP errors [11, 3]
```
- 192.168.50.2 への ping 3 回と、TCP の echo（16 KiB が一致）が、Tab5 の転送を通って成功した。
- TTL 1 の ping に、10.55.0.2 から Time Exceeded（11）が返った。
- 経路のない 192.168.99.1 への ping に、10.55.0.2 から Destination Unreachable（3）が返った。
- 従来のホストリンクの試験（10.55.0.2 の echo）も通る。

### 6.2 実機（2026-11-01、AP「iotap」）
- `run net 1`: host、wlan0、test0 の 3 つのリンクが立つ。DHCP、DNS、外への HTTP は以前どおり動く（退行なし）。
- Tab5 から試験用 LAN の相手への ping（`nettest 3 192.168.50.2`）: 4/4、往復 0.48〜0.63 ms。
- **Wi-Fi 側での待ち受け**: `nettest 1`（TCP の echo、すべてのリンクで待ち受け）に、LAN の PC（有線、192.168.2.14）から Tab5 の Wi-Fi のアドレス（192.168.2.112）の 7777 番へつなぎ、200,000 バイトを送った。全部一致して戻った（0.20 秒）。

### 6.3 実機での転送（未）
PC から 192.168.50.0/24 への経路が要る。PC で次を実行（root が要る）してから、`t5log hostlink` を動かして ping する:
```
sudo ip route add 192.168.50.0/24 via 10.55.0.2 dev t5
```
Wi-Fi 側の機器から 10.55.0.0/24 への戻りの経路はないので、ホストリンクと Wi-Fi の間の転送は N5（NAT）を待つ。

## 7. まだ
- 別のリンクにある自分のアドレスあて（例: ホストリンクから Wi-Fi のアドレスへ）は、転送の対象になり、自分には届かない。research §3.3 の「転送面が自分の別のリンクのアドレスあてを見つけて、その Interface へ回す」は未実装。
- 静的な経路を設定から読む。経路を見る・変える制御コマンド（`svc:netctl`）。
- ARP の待ちが溢れたとき、相手が答えないときに ICMP Host Unreachable を返す。
- フィルタと conntrack（N4）、NAT と DHCP サーバ（N5）。
