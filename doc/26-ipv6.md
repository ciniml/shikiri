## 2. アドレスと経路（`user/apps/net/src/main.rs`）
smoltcp の機能に `proto-ipv6`、`proto-ipv6-slaac`、`multicast` を足した。1 インタフェースあたりの上限も上げた（アドレス 8、SLAAC のプレフィックス 2、経路 4、近隣の表 16）。

| インタフェース | IPv6 のアドレス |
|---|---|
| 0（ホストリンク） | `::1/128`、`fd55::2/64`（PC は `fd55::1`、判断） |
| Wi-Fi | リンクローカル（MAC からの EUI-64）、SLAAC（RA のプレフィックス + EUI-64） |
| 試験用 LAN | リンクローカル、`fd50::1/64`（相手は `fd50::2/64`、既定の経路は `fd50::1`） |

- **SLAAC**: smoltcp が、RA を受けてアドレスと既定の経路をインタフェースに足す。`net` は、IPv4 のアドレスを付け直すとき（DHCP、`sync_addrs`）に IPv6 のアドレスを残すようにした。以前は表を全部消していた。SLAAC のアドレスが付いたか変わったら `net.ipv6` を出す。
- **出口の選び方**（`Stack::route6`）:

  | 宛先 | 出口 |
  |---|---|
  | `::1`、`fd55::/64` | インタフェース 0 |
  | `fd50::/64` | 試験用 LAN |
  | それ以外 | Wi-Fi（その先の経路は RA から） |
- **転送しない**: `link::transit` は IPv6 を転送の対象にしない。どのリンクの IPv6 も、受けたインタフェースの smoltcp に渡る。
- **デバイス**: Ethernet の IPv6（0x86DD）のフレームも、フィルタの `in` と `out` を通す。ループバックの判定に `::1` を足した。

## 3. フィルタ（V2、`filter.rs`、`rules.rs`）
- アドレスを u128 で持つ（IPv4 は下位 32 ビット）。パケットにも規則にも、種類（4 か 6）を持たせる。
- IPv6 では、拡張ヘッダ（hop-by-hop、routing、fragment、destination options）を飛ばして、トランスポートを見る。
- ICMPv6 の echo（128、129）は、IPv4 と同じく識別子で接続を追う。ICMPv6 のエラー（1〜4）は、引用されたパケットの接続に当たれば `related` にする。
- **近隣探索と MLD**（ICMPv6 の 130〜137、143）は、規則によらず通す。止めると IPv6 自体が動かないため（DHCP と同じ扱い）。
- IPv6 には `reject` がない（ICMPv6 のエラーをまだ作らない）。`drop` になる。
- `net.drop` の saddr と daddr は、バイト列（4 か 16 バイト）にした。
- 規則の書き方: `from`/`to` に IPv6 のアドレス（例 `fd55::/64`、`2001:db8::/32`）を書ける。アドレスを書いた規則は、その種類のパケットにだけ当たる。種類の違う `from` と `to` は書けない。プロトコルに `icmp6` を足した。`masquerade` は IPv4 だけ。

## 4. アプリとの取り決め（V3、`abi/src/net.rs`、`t5-rt`）
- **要求**: 2 バイト目（これまで 0）を種類にした。`FAMILY_V6`（6）なら、12 バイトの要求の後に IPv6 のアドレス（16 バイト）を付け、`a` の代わりに使う（`REQUEST_SIZE_V6` = 28）。それ以外は従来どおり IPv4。
  - TCP_LISTEN と UDP_BIND で、`::`（未指定）の IPv6 の要求を「すべて」にした。`link::LO` / `HOST` は、種類に合わせて `::1` / `fd55::2` になる。
  - RESOLVE を IPv6 の要求で送ると、AAAA を引く。
- **返事**: IPv6 のアドレスを返すとき（UDP_RECV の送信元、RESOLVE_RESULT の答え）は、12 バイトの返事の後に 16 バイトを付ける（`REPLY_SIZE_V6`）。クライアントは返事の長さで見分ける。
- **`t5-rt`**: `core::net::IpAddr` を受ける API を足した。従来の u32 の API はそのまま。
  - `tcp_connect_ip`、`tcp_listen_ip`
  - `ping_ip`、`resolve6`
  - `udp_send_ip`、`udp_recv_ip`
- **nettest**:

  | mode | 動作 |
  |---|---|
  | 5 | one.one.one.one の AAAA を引き、ping6 を 4 回、IPv6 で HTTP の GET |
  | 6 | `::1` で UDP の往復 20 回と、TCP 64 KiB（FNV で比べる） |
  | 7 | 試験用 LAN の相手（`fd50::2`）へ ping6 |

## 5. 結果
### 5.1 t5emu（`make test-p4emu` に 2 つ足した）
t5emu の PC 役に `fd55::1/64` を持たせた。相手（`--host-peer-target`）には IPv6 も書ける。
- PC 役 → `fd55::2`: ping6 を 3 回（1〜2 ms）。nettest 1 の echo に IPv6 で 16 KiB を送り、一致（74 ms）。
- `run net 1` で `nettest 6`: UDP の往復 20 回（164 ms）、TCP 64 KiB が一致（601 ms）。
- `nettest 7`: `fd50::2` に 4/4（3〜5 ms）。

### 5.2 実機（2026-11-01、iotap。RA で 2001:db8:0:1::/64 が来る）
- SLAAC: `net` の起動から約 4.4 秒で、Wi-Fi に `2001:db8:0:1:e6b3:23ff:fe9a:1f24` が付いた（`net.ipv6`）。IPv4 の DHCP（約 11 秒）より早い。
- LAN の PC（有線）から ping6 を 10 回: 10/10、平均 5.3 ms（最初の起動直後は、近隣探索の間に最大 1.1 秒）。
- LAN の PC から IPv6 で TCP の echo（`nettest 1`、すべてのリンクで待ち受け）に 200,000 バイト: 一致、0.19 秒。
- `nettest 5`: AAAA を 27 ms で解決（`2606:4700:4700::1111`）。ping6 は 3/4、約 8 ms（最初の 1 回はルータの近隣探索の間に失われた）。IPv6 で HTTP の応答 358 バイト（`403 Forbidden`、CDN の応答）。
- 守りの規則（`run netctl 2`）: LAN の PC からの ping6 は 0/5。Tab5 から始める IPv6（ping6 4/4、HTTP）は通る。統計では、established の規則に 10 回、`in` の規定で捨てたものが 8 回。

## 6. V4（IPv6 の転送）について
下流（試験用 LAN、将来の USB）の機器に IPv6 で外へ出てもらうには、下流に使うプレフィックスが要る。次のどれかを選ぶ必要がある（利用者の判断）:
1. 上流のルータから DHCPv6-PD で下流用のプレフィックスをもらう。smoltcp に DHCPv6 はないので自作になる。ルータが PD に対応している必要がある。
2. 近隣探索の代理（NDP proxy）で、上流の /64 を下流にも広げる。上流のルータには何も要らない。広く使われている方法だが、/64 を 2 つのリンクで分け合う。
3. 下流は ULA にして、出るときにプレフィックスを変換する（NPTv6、RFC 6296）。IPv4 の NAT に近く、上流に依存しない。

## 7. まだ
- IPv6 の ICMPv6 のエラー（Time Exceeded、Destination Unreachable、`reject`）。
- DHCPv6（ステートフル）、RDNSS（RA で DNS サーバを受ける）。DNS サーバは今は IPv4 の DHCP で得たものだけ。
- プライバシー拡張（一時アドレス）。今は MAC から作るアドレスなので、外から機器を追える。
