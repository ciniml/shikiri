# 27. IPv6 の転送と NDP proxy（V4）

doc/26 §6 の V4。利用者の判断（2026-11-01）: 下流へのプレフィックスは方式 2（NDP proxy。上流の /64 を下流にも広げる）にする。

## 1. 区切りと状態
| 内容 | 状態 |
|---|---|
| IPv6 の転送（ホップ数、フィルタの forward、近隣の表、NS で次の段を探す） | t5emu で確認（PC → Tab5 → 試験用 LAN、§4.1） |
| NDP proxy（下流への RA、上流と下流での代理 NA） | 実機で確認（§4.2） |
| ICMPv6 のエラー（Time Exceeded など） | 未。ホップ数が尽きたら黙って捨てる |

## 2. 転送（`user/apps/net/src/fwd6.rs`）
- **受信の振り分け**: デバイスは、IPv6 の宛先が全体向けかユニークローカルのユニキャストで、Tab5 のどのアドレスでもなければ、転送の受信箱に入れる（`fwd6::transit`）。Tab5 のアドレスの一覧は、毎回の poll で全インタフェースから作り直す（SLAAC で変わるため）。
- **出口**（`Stack::route6_fwd`）:

  | 宛先 | 出口 | 次の段 |
  |---|---|---|
  | NDP proxy の /64 で、下流で見たことのある機器 | 下流 | 宛先 |
  | NDP proxy の /64 で、それ以外 | 上流（ただし上流から来たものは捨てる。行き来を防ぐ） | 宛先 |
  | `fd50::/64` | 試験用 LAN | 宛先 |
  | `fd55::/64` | ホストリンク | 宛先 |
  | それ以外 | Wi-Fi | RA で知った上流のルータ（`net.ra`） |
- **処理**: フィルタの `forward`（IPv6 の規則がそのまま効く）を通し、hop limit が 1 以下なら捨て、1 減らして送る。IPv6 のヘッダにはチェックサムがない。
- **近隣の表**（32 項目、寿命 300 秒）:
  - 次の 3 つから覚える。
    - Ethernet で受けたすべての IPv6 のフレームの送信元
    - NA の target
    - 重複検出（DAD）の NS の target（送信元 `::` で、送った機器が使おうとしているアドレス）
  - 表にない次の段は、Tab5 から NS（送信元は出口のリンクのリンクローカル、宛先は要請ノードのマルチキャスト）を出して探す。その間、パケットを最大 4 個、1 秒まで待たせる。
- 統計: 30 秒ごとに、数が変わっていれば `net.fwd6`（forwarded、no_route、hop_limit、no_neighbor、proxied、ra_sent）を出す。

## 3. NDP proxy
規則の文字列に `ndp-proxy on UP to DOWN` と書く（例 `ndp-proxy on wlan0 to test0`。`netctl 6` に入れた）。UP の SLAAC の /64（Tab5 の全体向けアドレスのもの）を、DOWN に広げる。

- **下流への RA**: 10 秒ごとと、RS を受けたときに出す。中身は次のとおり。
  - ルータの寿命 1800 秒、送信元リンク層アドレス、MTU 1500
  - プレフィックス情報: /64、A=1（SLAAC でアドレスを作る）、L=0（リンク上ではない）、有効 3600 秒、推奨 1800 秒

  初めて広げたときに `net.ndp_proxy` を出す。
- **上流での代理 NA**: UP で、下流で見たことのある機器のアドレスを探す NS に、Tab5 の UP の MAC で答える（R=1、DAD への答え以外は S=1、O=0。RFC 4389 §4.1.3）。上流のルータと LAN の機器は、そのアドレスあてを Tab5 に送るようになる。
- **下流での代理 NA**: DOWN で、/64 のうち下流の機器でないアドレスを探す NS にも、Tab5 の DOWN の MAC で答える。
  - 必要な理由: L=0 を広告しても、smoltcp は SLAAC で作ったアドレスの /64 を「リンク上」と扱い、上流の機器を直接 NS で探す（§4.2 で分かった）。ほかの実装でもありうる。
  - DAD（送信元 `::`）には答えない。答えると、聞いた機器が自分のアドレスを捨てるため。
- **NA の送信元**: 代理 NA の IPv6 の送信元は、target のアドレスそのものにした。smoltcp 0.14 は、NA の MAC を target ではなく IPv6 の送信元のアドレスに結び付けて覚えるため（§4.2）。Linux は target で判断するので、どちらでも動く。
- **試験用 LAN の相手**: smoltcp の SLAAC を有効にした。上流のプレフィックスのアドレスができたら、`http://[2606:4700:4700::1111]/` を一度取る（`net.peer_slaac`、`net.peer_http v6=true`）。
  - 相手の IPv6 の既定の経路は、Tab5 のリンクローカルにした（以前は `fd50::1`）。smoltcp は近隣を探している間のパケットを捨てる。一方、Tab5 の NS にはリンクローカルの MAC が載っているので、そちらを経路にしておけば最初の返事から通る（t5emu で分かった）。

## 4. 結果
### 4.1 t5emu（`make test-p4emu` に足した）
`run net 1` で、PC 役（`fd55::1`、IPv6 の既定の経路は `fd55::2`）から試験用 LAN の相手（`fd50::2`）へ:
```
t5emu: host peer: ping [8.0, 2.0, 3.0] ms, TCP echo in 102 ms, ICMP errors []
```
ping6 3 回と、TCP の echo 16 KiB が、Tab5 の IPv6 の転送を通って一致した。

### 4.2 実機（2026-11-01、iotap。上流の /64 は 2001:db8:0:1::/64）
`run net 3`、`run netctl 6`（NAT、DHCP サーバ、`ndp-proxy on wlan0 to test0`）で:
```
net.ndp_proxy up=wlan0 down=test0 prefix=20010db800000001
net.peer_slaac addr=2001:db8:0:1:74:35ff:fe00:2
net.peer_http v6=true status=HTTP/1.1 301 Moved Permanently ms=22
```
- 下流の相手が、Tab5 の RA から上流の /64 のアドレスを作り、Tab5 を通って IPv6 で Cloudflare の Web に届いた（応答まで 20〜117 ms）。
- LAN の PC（有線）から、相手のアドレスへの ping6: 9/10、平均 2.4 ms（最初の 1 回は近隣探索の間に失われた）。PC の近隣の表では、相手のアドレスは Tab5 の MAC（`router` 印つき）になっている。
- そこまでに直した 2 つ:
  - 相手が上流の機器を直接 NS で探す件（下流での代理 NA を足した）
  - smoltcp が NA を送信元で覚える件（代理 NA の送信元を target にした）
- 一度、`net` の起動から 1 分以上、Wi-Fi に SLAAC のアドレスが付かないことがあった（RA が来なかった）。次の起動では数秒で付いた。上流のルータの RA の間隔によると考える（未調査）。上流のルータを覚えたときは `net.ra` を出すようにした。
- その後、4 分間 RA が 1 つも来ないこともあった。smoltcp の SLAAC は起動時に RS を 3 回出すだけなので、Wi-Fi に全体向けのアドレスがない間は、Tab5 から 10 秒ごとに RS を出すようにした（`Stack::solicit`、`net.rs_sent`）。直後の起動ではすぐに付いたが、RS が効いたのかどうかはまだ確かめていない。

## 5. まだ
→ ICMPv6 のエラー、下流への RDNSS、プレフィックスが変わったときの扱いは doc/46。
- ICMPv6 のエラー（Time Exceeded、Destination Unreachable、Packet Too Big）を作る。
- 上流から下流へ DAD を中継する（RFC 4389 の完全な形）。今は下流の機器のアドレスの重複を上流で確かめない。EUI-64 のアドレスなら実際には重ならない。
- 下流に RDNSS（DNS サーバ）を広告する。
- 上流の /64 が変わったときの、下流の古いアドレスの扱い（今は新しいプレフィックスで RA を出すだけ）。
- ホストリンク（`fd55::/64`、ULA）から IPv6 で外へ出る（NPTv6）。
