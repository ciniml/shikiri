## 2. S1: カーネル（`kernel/src/smp.rs`、`arch/riscv32/mod.rs`、リンカスクリプト）
- **入口**: `_start` は `mhartid` を見る。0 でない hart（QEMU はすべての hart をここから始める）は、`SECONDARY_GO` が 0 でなくなるまで待ち、`_start_secondary` へ進む。P4 の Core1 は、ROM から直接 `_start_secondary` に来る。
- **`_start_secondary`**: MIE=0、mscratch=0、gp=0 にし、Core1 用のスタック（`.stack1`。P4 は RAM_HI に 64 KiB、QEMU は 32 KiB）に切り替えて、`smp::kmain_secondary` を呼ぶ。
- **`kmain_secondary`**:
  - プラットフォームの初期化（P4 は Core1 の CLIC のしきい値）、トラップのベクタ、PMP の初期化をする。
  - `smp.core_up`（hart、mtvec、sp）を出し、`CORE_UP` を立てる。
  - その後は `park` で待つ。`park` は RAM（`.ram_text`）の WFI のループで、Core1 に割り込みは何も回していないので眠り続ける。RAM に置くのは、Core0 のフラッシュの操作でキャッシュが止まっても読めるようにするため（doc/14 §5）。
- **Core0**（`kmain` の PMP の初期化の直後、`smp::start`）: プラットフォームの `start_secondary` で Core1 を起動し、`CORE_UP` を最大 100 ms 待って `smp.started`（cores）を出す。S1 では、Core0 が待っている間に Core1 がログを書くので、両コアが同時にカーネルの状態に触ることはない。
- **P4 の起動**（`esp32p4v1.rs`）: SOC_CLK_CTRL0 の CORE1_CPU_CLK_EN を立て、HP_RST_EN0 の RST_EN_CORE1_GLOBAL を下ろし、ROM の `ets_set_appcpu_boot_addr(_start_secondary)` を呼ぶ（doc/32 §1）。
- **QEMU**: `start_secondary` は `SECONDARY_GO` を立てるだけ。`-smp 1` では待ちが 100 ms で切れ、`cores=1` で続く。`make test-virt` を `-smp 2` にした。

## 3. S1: t5emu（`emu/src/machine.rs`、`periph.rs`）
- `Machine` は、動いていないほうのコア（`Core`: `Cpu`、CLIC、待ちの印）を持つ。1 度に 1 コアを `QUANTUM`（1024 命令）ずつ進め、状態と CLIC を入れ替える。時刻（`bus.cycles`）は両コアで共有する。両方が忙しいと、エミュレータの時刻あたりの仕事は半分になる（判断。正しさの試験が目的）。
- **WFI**: 2 コアのときは、起こすものがなければ「待ち」の印を付けて、もう一方に番を渡す。待っているコアは、起こすものが来るまで飛ばす。両方とも待っていれば、どちらかが起きられる最初の時刻まで時計を飛ばす。
- **割り込み**: Core1 の割り込みマトリクス（0x500D_6800）を足した。振り分けは、動いているコアのマトリクスで、そのコアの CLIC に入れる。
- **`mhartid`**: コアの番号を返す。
- **LR/SC**: 書き込み（AMO を含む）は、もう一方のコアの同じワードの予約を消す。
- **Core1 の起動**: ROM の `ets_set_appcpu_boot_addr` は、Core1 のクロックが入り、リセットが解けていれば、a0 から Core1 を始める。
- まだ: コア間の割り込み（HP_SYSTEM の `CPU_INT_FROM_CPU_n`）、コアごとの命令キャッシュ（今は 1 つの模型を共有）。

## 5. S2: 大きな鍵とスケジューラ（`kernel/src/smp.rs`、`sched.rs`）
- **鍵**（`smp::lock`、`unlock`）: 1 つのチケットロック（`NEXT` を `amoadd` で取り、`SERVING` が自分の番になるまで待つ）。
  - コアはカーネルのコードを動かす間ずっと鍵を持ち、手放すのはプロセスを動かす間（U モード）と眠る間だけ。カーネルは割り込みを止めたまま（MIE=0）なので、割り込みとの行き違いはない。
  - 最初は compare-and-swap の鍵にしたが、Core1 が鍵を取れなかった。Core0 は、プロセスのシステムコール（`time_ns` など）で数命令後にまた鍵を取るので、Core1 が割り込めない。チケットロックは順番に渡すので、こうならない。
  - 鍵を待つ処理と眠る処理（`smp::idle`）は RAM（`.ram_text`）に置き、その間は `WAITING` を立てる。
- **フラッシュと MMU の操作**（`map_xip`、`map_flash`、`flash_erase`、`flash_write`）: キャッシュを止める前に `smp::quiesce` を呼び、もう一方のコアが RAM の中（鍵を待っているか眠っている）にいることを確かめる（100 ms まで。過ぎたら `smp.quiesce_timeout`）。鍵はこちらが持っているので、もう一方のコアは RAM から出られない。
  - もう一方のコアがプロセスを動かしている最中（U モード）は、`quiesce` は待つ。プロセスは長くて 1 スライス（10 ms）で戻ってくる。そのプロセスの XIP のテキストやデータ（PSRAM）を読むので、RAM にいることを待つ必要がある。
  - 本来の形（コア間の割り込みで止める）は S3。
- **スケジューラ**:
  - Core0 が動かすスケジューラ（`sched::run`）を `ACTIVE` で公開し、Core1（`sched::run_secondary`）も同じ表からプロセスを選ぶ。
  - 表は生のポインタで渡し、借用は鍵を持つ間だけにする（`run_user` や眠りをまたがない）。
  - `on_core`: プロセスごとに、動かしているコア。もう一方のコアが動かしているプロセスは選ばない、起こさない、片付けない（`reap`、`free_slot`）。
  - `kill` されたプロセスをもう一方のコアが動かしている場合は、そのコアが戻ってきたときに終わらせる（ログ、ハンドルを閉じる）。
  - `run` は抜ける前に、もう一方のコアがプロセスを返すまで待ってから `ACTIVE` を消す（自己試験は、ケースごとにスケジューラを作り直すため）。
- **Core0 だけがすること**: デバイス（Wi-Fi の受信、ホストリンク、表示）、制御コマンド（`poll`）、ウォッチドッグ。デバイスの割り込みも Core0 にだけ回す。
- **Core1**: Ready のプロセスがあれば 1 スライス動かす。なければ眠る。眠るのは、10 ms か、待っているプロセスの最初の起床時刻の早いほうまで。
  - 後者がないと、Core1 で動いたプロセスがタイマを待ち始めても、Core0 はそれより前に決めた時刻まで眠っているので、起床が最大 10 ms 遅れる（`timers` の試験が失敗した）。
  - コア間の割り込みがないので、Core0 で Ready になったプロセスに Core1 が気づくのは、Core1 が次に起きたとき（最大 10 ms）。Core0 が空いていれば Core0 が動かす（S3 で直す）。
- **タイマ**: コアごとに SYSTIMER の比較器を使う（Core0 は TARGET0、Core1 は TARGET1）。Core1 の比較器は、Core1 の割り込みマトリクスで Core1 の CLIC の同じ線に回す（`init_secondary`）。SYSTIMER_CONF は両コアで共有なので、鍵を持っているときだけ書く。QEMU は hart ごとの `mtimecmp`。
- **FPU**: レジスタはコアごと。スライスの終わりに、持ち主のプロセスのレジスタを（書かれていれば）保存して手放す。プロセスは次のスライスでどちらのコアでも動ける。以前の遅延保存（持ち主が替わるまで保存しない）はやめた。
- **CPU の計測**: 待ちの時間をコアごとに数える。`kernel.cpu` に `cores`、`idle0_pm`、`idle1_pm`、`slices0`、`slices1` を足した。`idle_pm`、`procs_pm`、`kernel_pm` は、全コアに対する千分率。プロセスの `cpu_pm` は 1 コアに対する千分率（2 コアで 2 つ回すと、それぞれ約 1000）。

## 6. S2: 試験の変更
- `spin` を 2 つ回す自己試験（M2）は、2 コアだとそれぞれが別のコアで動き、横取りされない（`spin` は「横取りされなかった」で exit 2）。`spin` を 3 つにした。
- `echo` の利用者（mode 3、5）は、サービスがまだ `listen` していなければ、1 ms おきに最大 1 秒、接続し直す。1 コアでは、表の順でサーバが先に動いていたが、2 コアでは同時に始まる。
- `sched.done`（デバッグ）: 自己試験のスケジューラが終わるとき、コアごとのスライスの数と横取りの数を出す。

## 7. S2: t5emu の直し（`emu/src/machine.rs`）
- **待っているコアが起きなかった**: 1 コアが忙しく、もう一方が WFI で待っているとき、エミュレータは待っているほうに番を回さなかった。そのため、そのコアのタイマが来ても起きなかった。`QUANTUM` ごとに必ず番を渡すようにした（待っているほうは、起こすものがなければすぐ返す）。
- **`pause`**（Zihintpause。FENCE の述語が W、後続が 0。実機ではただの fence）: 鍵を待つループで使う。t5emu はこれでもう一方のコアに番を渡す。鍵を持っているほうが進まないと待ちが終わらないため。これがないと、Core1 が鍵を待つ間エミュレータの時間を食い、試験の時間が倍になった。

## 8. S2: 実機で見つかったこと
- **Core1 が上がらなかった**（`smp.started cores=1`）:
  - 原因（推定）: 再起動（ROM の software reset）の前に Core1 を止めていなかった。ROM の中の Core1 の入口（`ets_set_appcpu_boot_addr` で渡した番地）が前のカーネルのまま残り、Core1 は新しいカーネルが読み込まれる前にその番地へ入ったと考える。Core0 が .bss を 0 にするので `CORE_UP` も消える。S1 で上がったのは、その前のカーネルが Core1 を一度も起動していなかったから。
  - 対処1: `reset` で、ESP-IDF の `esp_restart_noos`（`system_internal.c:113-146`）と同じく、Core1 をリセットのままにして、入口を 0 にしてから再起動する。
  - 対処2: `start_secondary` で、入口を 0 にし、Core1 を一度リセットしてから放し、入口を渡す。パニックなどで止めずに再起動した場合にも、Core1 は ROM から入り直す。
  - 対処3: Core0 が 100 ms 待ってあきらめた後に Core1 が来た場合、Core1 は加わらずに RAM で眠り続ける（`CORE_UP` の compare-and-swap で決める）。数えていないコアが動くと、`quiesce` が待たないため。
- **Core1 のタイマ割り込みがすぐまた来た**:
  - 症状: `spin` を 2 つ動かすと、1 つが 12% しか動かず、カーネルの時間が 46%。Core1 は非常に短いスライスを繰り返した。t5emu では起きない。
  - 原因（推定）: SYSTIMER の割り込みを消して（INT_CLR）から、それがコアの CLIC の保留ビットに届くまでに少し時間がかかる。Core1 はスライスの終わりからすぐ次のプロセスを U モードで動かすので、残っている保留ビットで、すぐにまたトラップする。Core0 は、その間にデバイスの仕事などをするので、表に出なかった。
  - 対処: `clear_alarm` で、このコアの CLIC のタイマの線の保留ビット（IP）が落ちるまで待つ（256 回まで）。あわせて、アラームの時刻より前のタイマ割り込みは「にせ」として数え（`kernel.cpu` の `spurious0`、`spurious1`）、スライスを終わらせない。対処の後は、にせの割り込みは 0。
  - 待つ対処だけで直ったのか、時刻の判定も効いているのかは、分けて確かめていない。

## 10. S3: コア間の割り込み（`kernel/src/smp.rs`、`sched.rs`、`platform/*`）
- **割り込みの源**:
  - P4: HP_SYSTEM の `CPU_INT_FROM_CPU_n`（0x500E_5010 + 4n）に 1 を書くと、源 `FROM_CPU_INTRn` が立ち、0 を書くまで立ったまま（`hp_system_reg.h:37-60`、`crosscore_int_ll.h`）。ESP-IDF と同じく n は宛先のコアの番号にし、源 79 を Core0 の、源 80 を Core1 の割り込みマトリクスで CPU の線 5（CLIC の 21）に回す（`interrupts.h:100-101`）。
  - QEMU: CLINT の hart ごとの `msip`（0x0200_0000 + 4 × hart）。マシンのソフトウェア割り込み（mcause 3、`mie.MSIE`）。
  - プラットフォームの `IPI_IRQ`、`ipi_send(hart)`、`ipi_clear()`。消すときは、タイマと同じく CLIC の保留ビットが落ちるまで待つ（§8）。
- **起こす**（`smp::kick`、`sched::kick_if_ready`）:
  - `idle` は、眠る前に `ASLEEP` を立て、起きて鍵を取った後に消す。どちらも鍵を持っている間なので、鍵を持つコアからは正確に見える。
  - コアがプロセスを始めるときと、システムコールを処理した後に、もう一方のコアが眠っていれば、待っているプロセスを起こしてみて（`wake`）、どのコアも動かしていない Ready のプロセスがあれば割り込みを送る。システムコール（チャネルへの書き込み、終了など）で、別のプロセスの待ちが終わることがあるため。
  - 割り込みは消すまで立ったままなので、眠る直前に送られても WFI はすぐ戻り、失われない。起きたコアは、仕事を探す前に割り込みを消す（`idle` の終わり）。
  - Core1 が仕事のないときに眠る上限を 10 ms から 1000 ms にした。
- **止める**（`smp::quiesce`）: フラッシュと MMU の操作の前、もう一方のコアが RAM の中にいなければ（`WAITING`）、割り込みを送る。プロセスを動かしていたコアはトラップでカーネルに戻り、鍵を待つ（RAM）。鍵はこちらが持っているので、そこから出ない。以前はプロセスのスライスが終わるのを待っていた（最大 10 ms）。
  - 割り込みを受けたコアは、鍵を取った後、割り込みを消して同じプロセスを続ける（`ipis0`、`ipis1` で数える）。
- **命令の取り込み**（`smp::code_changed`、`sync_fetch`）:
  - P4 の命令キャッシュはコアごと（doc/32 §1）だが、ROM の `Cache_Invalidate_Addr` に渡している `CACHE_MAP_L1_ICACHE_MASK`（`CACHE_MAP_L1_ICACHE_0 | CACHE_MAP_L1_ICACHE_1`、`rom/cache.h:228-233`、`cache_ll.h:486-490`）は両コアの命令キャッシュを指すので、`sync_code` と `map_flash_pages` は、もとから両方を無効にしている。
  - 残るのはコアのパイプラインに先に取り込まれた命令で、これは `fence.i` が要る（各コアが自分で実行する）。ローダがアプリを読み込むたびに世代を進め、各コアはプロセスを U モードで動かす前に、世代が変わっていれば `fence.i` を実行する。
- **計測**: `kernel.cpu` と `sched.done` に `kicks0`、`kicks1`（送った数）と `ipis0`、`ipis1`（プロセスを動かしている最中に受けた数）を足した。
- **t5emu**: `CPU_INT_FROM_CPU_0〜3` を持ち、立っている源を、動いているコアの割り込みマトリクスで振り分ける（`periph.rs`）。待っているコアは、番が回ってきたときに保留を見て起きる。
- **試験**: `make test-p4emu` に、両コアをプロセスでふさいだまま、インストール、XIP のアプリの対応付けと実行、削除をする試験を足した。t5emu は、L2 を止めている間のフラッシュや PSRAM への読み出しで止まる。
  - 最初は普通の `spin` を使ったが、`spin` は回るたびに `time_ns` を呼ぶので、Core1 はほとんどいつも鍵を待っていて、割り込みが使われなかった（`ipis1=0`）。
  - そこで `spin` に、システムコールをしない回り方（`id` に 0x100）を足した。時刻を読まず、`duration_ms` × 100,000 回まわる。これで `ipis1=14`、2 つの `spin` は `fp_mismatches=0` で終わり、フラッシュの違反も `smp.quiesce_timeout` もない。
- QEMU（`make test-virt`）と t5emu（`make test-p4emu`）の試験一式が通る。

## 11. S3 の実機の結果（2026-11-01）
- kupdate で入れた（ota_seq=12、slot 1）。`cores=2`、Wi-Fi、自動起動は以前どおり。
- **両コアをふさいだままのインストール**: 新しい `spin` をストアに入れ（実機のストアの `spin` は古く、システムコールをしない回り方がなかった。最初の試みはそのため `ipis1=0` だった）、`spin 257 3000` と `spin 258 3000` を動かしたまま、`greeter` のインストールと実行、`spin-xip` のインストール（XIP の対応付け）と実行、両方の削除をした。
  - すべて成功。`ipis1=12`、2 つの `spin` は `fp_mismatches=0`、`proc.fault` も `smp.quiesce_timeout` もない。
  - `spin-xip` の exit 2 は「横取りされなかった」で、空いているコアで 1 つだけ動いたため（期待どおり）。
- **両コアをふさいだままの kupdate**: `spin 257 20000` と `spin 258 20000` を動かしたまま `kupdate build/kupdate/good.t5k`（157,852 B、消去 39、書き込み 617）。
  - 検証と `kupdate.ready` まで通り（`ipis1=163`）、再起動後に新しいカーネル（slot 0、ota_seq=13）が自己試験を通して確定した。S3 の完了の条件を満たした。
- **気づいたこと**（未解決）:
  - 両コアが U モードで回っている間、t5log の RTT の書き込み（コマンドを送る側）が何度も失敗した（「Error communicating with the probe」、kupdate の間に 3,591 回）。t5log がやり直すので結果は正しいが、書き込みに 48 秒かかった（以前の記録では 98 KB で約 1.8 秒）。読み出し（ログ）は失敗していない。原因は調べていない。
  - プロセスの時間（`cpu_ms`）には、トラップの後に鍵を待った時間が入る。もう一方のコアがフラッシュを書いている間に待つと、短い窓の `cpu_pm` が 1000 を超えることがある。鍵の待ちはフラッシュのコードを呼べない場所（RAM）で始まるので、時刻を読めない。そのままにした。
- **直したこと**: Core1 が最大 1 秒眠るようになり、短い窓の `idle1_pm` が 1000 を大きく超えた（`ps` を続けて送ったとき 5478）。眠りの時間を起きたときにまとめて足していたため。眠り始めた時刻をスケジューラに置き（`asleep_since`）、`ps` は眠っている最中のコアの時間をその時点までで区切って足すようにした（`settle_idle`）。
