# 34. `net` の CPU を減らす

利用者の指示（2026-11-01）:「net の CPU 使用率の削減に進みましょう」。doc/33 §12 の時点で、Wi-Fi の TCP echo（16 MiB）は 9.9 Mbps、`net` は 1 コアの約 58% を使っていた。

## 1. 結果
| 版 | 片道 | `net` の CPU（16 MiB の echo 1 回） |
|---|---|---|
| 1 コア（doc/31 §4） | 8.9 Mbps | — |
| SMP S4（doc/33 §12） | 9.9 Mbps | 約 9.8 秒 |
| **この文書の後** | **11.0〜11.1 Mbps** | **約 7.4 秒（約 24% 減）** |

- 測り方は doc/33 §12.1 と同じ（守りの規則を外して測り、戻す）。表の値はプロファイラを止めて測った。
- 起動時、Wi-Fi の接続を待つ間に `net` が約 7 秒の CPU を使っていたのも直した（§5）。起動から 46 秒の `net` の CPU は 8.7 秒 → 1.7 秒。

## 2. 道具: プロファイラ（`kernel/src/prof.rs`、`tools/prof.py`）
- **制御コマンド**: `prof start PID US`（そのプロセスを US µs ごとに標本化）、`prof stop`（まとめを記録）、`prof dump K`（標本の K 番目の 512 個を記録）。t5log と t5emu の `--cmd` で使える。
- **標本**: プロセスが動いている間、アラームをスライスの終わりと次の標本の時刻の早いほうにする。標本の時刻に来たタイマ割り込みで、プロセスの PC を記録する（8,192 個まで。P4 は RAM_HI の .bss に 32 KiB）。
  - カーネルは割り込みを止めて動くので、システムコールの最中に来た標本は、U モードに戻った直後（命令を 1 つも実行する前）に取られる。その標本には印（ビット 0）を付け、カーネルの時間として数える（PC はシステムコールの直後なので、呼んだ関数が分かる）。
  - プロセスが動いていない間に時刻が来た標本は、次に動くときに取らずに先へ送る。最初はこれをしておらず、`wait` から戻った直後の標本がカーネルの時間に見えた。
  - 次の標本の時刻はプロファイラが持つ。最初は U モードに戻るたびに「今 + 間隔」にしていたので、数 µs ごとにシステムコールをする `net` は一度も標本化されなかった（t5emu では遅いので起きなかった）。
- **システムコール**: 番号ごとに回数と、カーネルが処理にかけたサイクル（`mcycle`）を数える。トラップの出入りと鍵の待ちは含まない。
- **ホスト**: `tools/prof.py LOG ELF` が、ELF の関数（`nm`）ごとに標本をまとめる。PC から引くのはテキストの先頭（`prof.summary` の `text`）。
- **記録の溢れ**: `prof dump` を一度に多く送ると、RTT の記録が溢れる（`log.dropped`）。t5log を分けて 2 つずつ送る。
- **t5emu**: ホスト役（`--host-peer`）が終わった後も、残りのコマンドを（待ちを飛ばして）送るようにした。プロファイラの結果を読むため。

|---|---|---|

| `READ` | 134,280 | 524 M |

標本（8,192 個）: カーネル 68%（`netdev` への書き込み 26%、`time_ns` 20%、読み出し 18%）、U モード 32%（`memcpy` 7%、`memset` 6%、チェックサム 3%）。

## 4. 直したこと
| 何 | どこ | 効果 |
|---|---|---|
| **時刻をまとめて読む**: 時刻はシステムコール。smoltcp の `poll` のたび、パケットごと（フィルタ、NAT、近隣の表）に読んでいた。poll の 1 巡の始めと `wait` の後にだけ読み（`tick`）、ほかは `clock_ns()` を使う | `user/apps/net/src/main.rs` ほか | `TIME` 300k → 93k 回 |
| **フレームの置き場**: `receive` のたび（ほとんどは何も来ていない）に 1.5 KB を 0 で埋め、トークンで値渡ししていた。送信と転送の置き場も毎回 0 で埋めていた。静的な置き場にした（受信は機器の種類ごと、送信は 1 つ） | `link.rs`、`fwd.rs`、`testlan.rs` | `memset` 6% → 2% |
| **SDIO の書き込みを待たない**: C6 へのフレームの書き込み（CMD53）は、コマンドが受け付けられて DMA が始まったら戻る。終わりは、次にホストを使う前、SDIO の割り込み、Core0 の回り目（`wlan::poll`）で確かめる（`finish_write`）。SD カードの書き込みは今までどおり終わるまで待つ | `kernel/src/platform/esp32p4v1/sd.rs`、`sdio.rs` | `WRITE` の中のサイクル 979 M → 189〜265 M |
| **空の読み出しをしない**: `READ` が、読んだ後にまだ並んでいるフレームの数を返す（a2）。`net` は、0 になったら次の `wait` まで読まない | `kernel/src/process.rs`、`handle.rs`、`user/rt`、`link.rs` | `READ` 135k → 81k 回、中のサイクル 558 M → 123 M |
| **I/O の置き場**: `READ`/`WRITE` のたびに、カーネルのスタックの 4 KiB を 0 で埋めていた。静的な 1 つにした（鍵の中だけで使う） | `kernel/src/process.rs` | — |
| **もう一方のコアを確かめる間隔**: SYSTIMER の読み出し（約 2 µs）をやめ、コアのサイクル数で 1 ms ごとにする | `kernel/src/sched.rs` | システムコール 1 回あたり約 2 µs |

### 4.1 SDIO の書き込みを待たないときに起きたこと
- 最初の版では、ホストの IDMAC の割り込み（TI）が許可されていたため、待たずに戻った書き込みの DMA が終わると、SDIO の割り込みが立ちっぱなしになった。Core0 はトラップと U モードへの復帰を繰り返し、プロセスは進まず、RTT も答えなくなった。自己試験は Wi-Fi を使わないので通り、そのカーネルは確定していた（ota_seq=23）。プローブがつながっているとウォッチドッグが止まるので、そのまま止まり、プローブを外すとウォッチドッグで再起動を繰り返した。
  - 戻し方: 再起動の直後、自己試験の後で C6 を初期化する前に、`wifi` と `net` を `kill` し、その間に直したカーネルを kupdate で入れた。
- IDINTEN を 0 にする案は、IDSTS の印も立たなくなり（DMA が終わったか分からず、SD も SDIO も時間切れ）、だめだった。IDINTEN は元のまま、SDIO の割り込みで `finish_write` を呼ぶようにした（TI が消える）。カードの割り込みは、RINTSTS に印があるときだけ扱う。
- t5emu は C6 を模していないので、この部分は実機でしか試せない。

## 5. 起動時の空回り（smoltcp の SLAAC）
- 症状: 起動から Wi-Fi のアドレスが付くまで（約 5〜30 秒）、`net` が回り続けた（31 秒で `wait` 138k 回、`TIME` 415k 回）。元の `net` でも起きていた（起動から 41 秒で CPU 9.6 秒）。
- 調べ方: `poll_delay` が 0 のまま 1,000 回続いたら、インタフェースごとの値を記録する（`net.busy_poll`）。`wlan0` が 0 を返し続けていた。
- 原因: smoltcp 0.14.0 の `Slaac::poll_at`。ルータ要請（RS）を送り切ると、`rs_required` が偽になって `rs_sent` が呼ばれず、`retry_rs_at` が過去のまま返る。ルータ広告（RA）が来るまで `poll_delay` が 0 になる。上流の main も同じ（2026-11-01）。
- 対処: smoltcp を `third_party/smoltcp-0.14.0` に置き、送り切った後は時刻を返さないように 1 行直した（`user/Cargo.toml` の `[patch.crates-io]`、`third_party/README.md`）。
- 結果: 起動から 46 秒の `net` の CPU は 1.7 秒。IPv6（SLAAC）と DHCP は以前どおり付く。

## 7. 次の候補（未着手）
- **システムコールの往復の費用**: `TIME` の中身は 2.2 µs だが、`net` から見ると 1 回約 9 µs かかっている（標本の数から）。残りはトラップの出入り、鍵の取得、Core0 が SDIO の仕事で鍵を持っている間の待ち。カーネルの入口の経路（フラッシュから読むコード）や、鍵を持つ時間を短くすることが考えられる。時刻だけなら、システムコールにしない方法（共有の読み取り専用のページなど）もある。
- **`memcpy`**: フレームはカーネルのキュー → カーネルの I/O 置き場 → `net` の置き場 → smoltcp のソケット → `nettest` の共有メモリ、と何度も写す。
- **チェックサム**: smoltcp の `checksum::data` は 16 ビットずつ。32 ビットずつにすれば速くなる見込み。
- Core0 のカーネルの時間（全体の 13%）の内訳。
