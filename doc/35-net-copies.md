# 35. `net` の経路のコピーを減らす（ゼロコピーの検討）

利用者の指示（2026-11-01）:「ゼロコピーを目指したいけど可能ですかね？」。doc/34 §13 の後、`memcpy` はまだ `net` の U モードの約 11%。

## 1. 今のコピー（Wi-Fi の TCP echo、1 バイトあたり）
§2 の前は、CPU のコピーが 14 回あった（DMA を除く）。

| 向き | 場所 | コピー |
|---|---|---|
| 受信 | カーネル | SDIO の DMA の bounce → `stream` → `wlan` の受信の待ち行列 → カーネルの I/O 置き場 → `net` のフレーム |
| 受信 | `net` | フレーム → smoltcp の TCP の受信リング → 共有メモリ（アプリ） |
| 送信 | `net` | 共有メモリ → smoltcp の TCP の送信リング → フレーム |
| 送信 | カーネル | フレーム → I/O 置き場 → `wlan` の送信の待ち行列（Core1 のとき） → `l.tx`（SDIO の頭をつける） → bounce |

- カーネルの 8 回は、原理的には 0 にできる（§4）。
- `net` の 4 回のうち、フレーム → 受信リング（並べ直し）と送信リング → フレーム（再送のために持つ）は TCP に要る。残りの 2 回（リングと共有メモリの間）は、アプリが smoltcp のリングを直に読み書きすれば消えるが、smoltcp のリングの位置は外に出ていないので、smoltcp に手を入れることになる（判断: 今はやらない）。
- つまり smoltcp を使う限り、端から端までのゼロコピーにはならない。カーネルのゼロコピーと、`net` の 2〜4 回が現実的な目標。

## 2. Z0: ABI を変えずに減らす（実装済み）
- `READ`/`WRITE` は、カーネルの I/O 置き場（4 KiB）を通さず、呼び手のメモリへ直に読み書きする（`process.rs`）。範囲はそのプロセスの text と data だけで（共有メモリは入らない）、呼び出しの間ほかから触られない。
- SDIO の送信は、頭（12 バイト）、フレーム、ブロックの残りの 0 を、DMA の bounce に直に集める（`sd.rs` の `Data::WriteParts`）。`l.tx`（2 KiB）がなくなった。
- SDIO の受信は、DMA が置いた bounce の上でパケットに分け、そのまま渡す（`Data::ReadWith`）。読み出しが途中で切ったパケットだけを `stream` に残す。
- カーネルのコピーは、受信 4 → 2、送信 4 → 2（Core0 からの送信は 1）。カーネルの RAM も 6 KiB 減った。

## 3. 空の `READ` を減らす（`net`）
- `net` は `wait` のたびに全部のリンク（ホストと Wi-Fi）に「フレームがあるかもしれない」と印をつけ、読んでいた。起こしたのがアプリの要求でも読むので、ほとんどが空の `READ` だった。
- `wait` は水準で知らせる（フレームが残っていれば次の `wait` がすぐ戻る）ので、起こしたリンクだけに印をつける。
- `READ` 82,308 → 46,660 回（echo 1 回、プロファイラの数）、その中のカーネルのサイクル 125 M → 64 M。

## 4. 結果と見立て
| 版 | 片道（3 回） | `net` の CPU（1 回） |
|---|---|---|
| doc/34 §13 | 12.9〜13.1 Mbps | 6.0〜6.1 秒 |
| §2 の後 | 12.5〜13.1 Mbps | 6.2〜6.3 秒 |
| §3 の後 | 12.4〜12.6 Mbps | 6.1〜6.2 秒 |

- どれもばらつき（doc/34 §11.3）の中で、はっきりした差は出なかった。
- カーネルのコピーは内蔵 RAM の 1.5 KB で 1 回約 3 µs、多くは Core0 の仕事で、`net` の時間にはあまり入らない。
- `READ` が減った分、`WRITE` の標本が増えた（4.3% → 13.1%、1 回平均 5.0 k → 5.4 k サイクル）。前のフレームの SDIO の DMA（1.5 KB で約 80 µs）が終わるのを待つ時間が、`WRITE` に寄った（推測）。`net` が Core0 で動いているときの送信は、バスの速さで待つ。
- 見立て: いまの `net` の時間は、コピーより、システムコールの数（echo 1 回で約 15 万回）と SDIO のバスを待つ時間で決まっている。

## 5. Z1/Z2: 共有のフレーム置き場（`netdev` の輪）
利用者の指示（2026-11-01）:「すすめて」（§4 の後の Z1/Z2）。

### 5.1 形（ABI 小版 13）
- `ctl(netdev:wlan0, MAP_RING)`: 輪を呼び手に写し、番地を返す。置き場は、PSRAM があるとき空いている L2MEM のアプリ用の池（0x4FF8_0000〜、`ring::SIZE` = 49,408 バイト）。PMP の 9/10 番を RW- で与え、ハンドルを閉じると外す。`KICK`: 送信の輪に足したフレームを送らせる。
- 配置（`t5_abi::netdev::ring`）: 受信と送信に 16 枠ずつ（1 枠 1,536 バイト）、長さの表、4 つの数（受信: カーネルが `RX_HEAD`、プロセスが `RX_TAIL`、送信: プロセスが `TX_HEAD`、カーネルが `TX_TAIL`）。数は回りっぱなしで、枠は数 % 16。
- 守り:
  - カーネルは自分の数を自分のメモリに持ち、輪の上の数と長さは一度だけ読んで確かめる。でたらめを書いたプロセスは自分のフレームを失うだけ。
  - 受信の輪に入るのはステーションのフレームだけ。カーネルが DMA の bounce から 1 回写す。C6 の制御の応答（`wifi` サービス宛て）は共有の置き場に入らない（判断: DMA を直に輪へ向けない）。
  - 送信の SDIO の頭はカーネルが自分のメモリで作り、フレームと一緒に bounce へ集める。`net` は C6 への制御の命令を作れない。
- `net`（`link.rs`）: 受信は輪の枠をそのまま smoltcp に渡し（NAT も枠の上で書き換える）、使い終えたら返す。送信は smoltcp に枠へ直にフレームを作らせる。4 フレームごと、またはその回の終わり（`wait` の前）に `KICK`。輪がいっぱいなら `KICK` してから `yield` で少し待つ。

### 5.2 コピーとシステムコール
- カーネルのコピー: 受信 1（bounce → 輪）、送信 1（輪 → bounce）。`net` のフレームの置き場とのコピーはなくなった（`net` の中は smoltcp のリングとの 2 回と、共有メモリとの 2 回が残る）。
- Wi-Fi のフレームの `READ` はなくなり、`WRITE` は 4 フレームに 1 回の `KICK` になった。

### 5.3 最初の版の失敗: 輪があふれる
- 最初は `KICK` をその回の終わりにだけ出していた。smoltcp は 1 回の `poll` で TCP の窓（約 22 フレーム）まで送るので、16 枠の輪が埋まる。`net` が Core1 にいると `KICK` は Core0 に頼むだけで、枠はすぐ空かず、`sleep_ms(1)` で待っていた。echo は 4 回のうち 3 回が 6.0〜6.7 Mbps に落ちた。
- 4 フレームごとに `KICK` し、満杯のときは `yield` で待つようにして直った。

### 5.4 結果（16 MiB の echo）
| 版 | 片道 | `net` の CPU（1 回） |
|---|---|---|
| §3 の後 | 12.4〜12.6 Mbps | 6.1〜6.2 秒 |
| **§5 の後** | **12.3〜13.8 Mbps**（20 回以上） | **5.7〜5.8 秒** |

- doc/34 の始め（S4、9.8 秒）からは約 41% 減。

### 5.5 測っている途中で見つけたこと
- 起動の後しばらくの echo で、`net` が「ecall from M-mode」で止まることがあった。輪とは関係がなく（輪を写す前にも起きた）、プロセスが M モードで動いていた。doc/36 に分けて書く。
