# 36. プロセスが M モードで動いていた（デバッガの停止が引き金）

doc/35 §5 の測定中（2026-11-01）に見つけた。利用者の指示（同日）:「M-mode problem は安全性に関わるので追いかけましょう」。

## 1. 起きたこと
- 起動してしばらくの Wi-Fi の echo で、`net` が `proc.fault: 104 killed by ecall from M-mode` で止まる。
- `mcause` は 0x3800000B: 例外 11（M モードからの `ecall`）、`mpp`（ビット 29:28）= 3。止まった番地は `net` の text の中（`t5_rt` の `ecall`）。
- `net` は、直前の `mret` から次の `ecall` まで M モードで動いていた。その間 PMP は効かない（ロックしていないエントリは M モードに効かない）。

## 2. 切り分け
| 試したこと | 結果 |
|---|---|
| コアごとに最後の 8 回のトラップを記録 | 毎回、Core0 の `net` のチャネルの `READ`（U モードから）の後の `mret` で M モードになる。間に割り込みはない。`mret` の直前の `mstatus.MPP` は U |
| `mret` の前に `mstatus`/`mcause` を読み直す | 変わらない（約 1 割の起動で起きる） |
| 1 コア（Core1 を起こさない） | 20 回の起動の 3 回目で起きた。SMP とは関係がない |
| この作業の前のカーネルと `net`（9bbf70b） | 2 回目の起動で起きた。前からある |
| **起きた時刻** | どれも `t5log`（probe）がつながっている最中か、その終わり |
| probe を外したまま 16 MiB の echo を 30 回 × 2 起動（10 分以上） | 一度も起きない |
| echo の最中に `t5log rtt --cmd ps --until-done` を 30 回ほどつなぎ直す | 4 回の起動のうち 2〜3 回で起きる |
| 同じ回数つなぐが、`t5log` を `timeout` で殺して終わらせる | 3 回の起動で 0 回 |
| 1 回の接続で `ps` を 40 回 | 3 回の起動で 0 回 |
| `spin`（ほぼずっと U モード）を回しながら `t5log` をつなぐ | 起きない |

## 3. 原因
- **引き金はデバッガがハートを止めて再開すること**。`t5log`（probe-rs をライブラリとして使う）は、次の 3 か所で止めていた（probe-rs dd49092）:
  1. `Session::core` で `Core` を作るとき。`misa` を読み（`read_hart_isa`）、`dcsr` の ebreak のビットを書く（`ensure_debug_on_sw_breakpoint`）。どちらもハートを止める。
  2. 8 ビットと 16 ビットのメモリアクセス。Tab5（P4 v1.x）では LP SRAM でもプログラムバッファ経由になり（実機で確かめた: A8/A16 → ProgramBuffer、A32 → SystemBus）、1 回ごとに止める。RTT の下りのチャネルへの書き込みは、端を `write_8` で書く。
  3. **`Session` の `Drop`**。ハードウェアのブレークポイントを消し（`clear_all_hw_breakpoints`）、各コアの `Core` を作って `debug_core_stop` を呼ぶ。両方のコアを止める。`t5log` が普通に終わるたびに起きていた。§2 の「`timeout` で殺すと起きない」はこれで説明できる。
- 止めて再開したときに、なぜプロセスが M モードになるのかは確かめていない（推測）: 停止がカーネルの実行中に来て、カーネルがプロセスへ `mret` するところで取られると、`dcsr.prv` が M のまま `dpc` がプロセスの番地になる。P4 は例外の処理中（`mexstatus.EXPT_VLD`、`mret` まで）を内部で持っており（doc/01 §5.2）、その間の停止要求の扱いが関係している可能性がある。`spin` で起きないのは、停止がカーネルの中に来ないため。`net` は時間の 4〜5 割をカーネルで使う。

## 4. 安全性の評価
- デバッガがないときには起きない（§2）。アプリが自分で起こせる道は見つかっていない。
- デバッガはもともと何でもできるので、これ自体は権限の分離の穴ではない（判断）。ただし開発中にデバッガでハートを止めると、プロセスが M モードで動きうる。`t5log status`（止めるのが目的）や probe-rs の CLI を使った後のふるまいは信用しない。

## 5. 対策
- **`t5log rtt` はハートを止めない**（`tools/t5log/src/rtt.rs`）:
  - probe-rs の `Core` を作らず、`Session::get_riscv_interface` のメモリの読み書きで RTT を読む。`--reset` のときだけ `Core` を作る（リセットするので構わない）。
  - メモリアクセスは 32 ビットだけ（`Words`）。8/16 ビットは語の読み出しと読み・変更・書き込みにする。
  - `Session` は捨てずに `std::mem::forget` する（probe はプロセスの終わりで閉じる）。
  - 効果: echo の最中に 53 回つなぎ直して 4 回の起動で 0 回（直す前は 2〜3 回）。
- **カーネルは検出して止める**（`trap.rs`、`sched.rs`）: `mret` の前に `mstatus`/`mcause` の MPP が U であることを確かめる。プロセスからのトラップの直後に `mstatus.MPP` を見て、M なら `proc.mmode`（pid、戻した番地、トラップの番地、`mcause`）を記録してそのプロセスを止める。

## 6. 残っていること
- 止めて再開したときに M モードになる仕組み（§3 の推測）は、確かめていない。Espressif に問い合わせるなら、再現の手順は §2 の表のとおり。
- ~~echo の最中に `t5log` を 1 秒に 1 回ほどつなぎ直すと、echo の TCP が止まることがある~~ → 解決（2026-11-02）。止まったのは試験のスクリプト（`echo.py`）だった:
  - ホストの側では、送ったものはすべて受け取りが返っていて、送りの待ち行列は空だった。止めていたのは Python の側。
  - Python 3.5 からは、ソケットの時間切れ（30 秒）が `sendall` の呼び出し全体にかかる。64 MiB は約 41 秒かかるので、つなぎ直しがなくても時間切れになる。
  - 64 KiB ずつ送るように直した。その後は、約 40 回つなぎ直しても 64 MiB の echo が 4 回とも正しく通った（11.99〜13.06 Mbps）。
  - ついでに分かったこと: 試験のたびに `run nettest 1` を出していたので、`nettest` が 4 つ同じポート 7777 で待ち受けていた。`net` が同じポートの 2 つ目の待ち受けを断るようにした（doc/20 §1 の追記）。
