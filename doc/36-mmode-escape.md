# 36. プロセスが M モードで動いていた（未解決）

doc/35 §5 の測定中（2026-11-01）に見つけた。原因は分かっていない。

## 1. 起きたこと
- 起動してしばらくの Wi-Fi の echo で、`net`（pid 104）が `proc.fault: 104 killed by ecall from M-mode` で止まる。
- `mcause` は 0x3800000B: 例外 11（M モードからの `ecall`）、`mpp`（ビット 29:28）= 3。ハードウェアは、`net` の `ecall` を M モードで実行したと見ている。止まった番地は `net` の text の中（`t5_rt` の `wait_raw` や `Channel::send` の `ecall`）。
- つまり `net` は、直前の `mret` から次の `ecall` まで M モードで動いていた。その間、PMP は効いていない（ロックしていないエントリは M モードに効かない）。権限の分離が破れる、深刻な不具合。

## 2. 分かったこと
- 輪（doc/35 §5）とは関係がない。輪を写す前（起動 4 秒、最後のシステムコールは `OPEN`）にも起きた。
- コアごとに最後の 8 回のトラップを記録した版で、2 回とも同じ流れだった（Core0、`net`）:
  1. `net` が自分の要求のチャネルを `READ`（`Handle::read`、0x2e9e6）。U モードから（`mcause` 0x08000008、トラップ直後の `mstatus.MPP` = U）。
  2. カーネルが結果を書いて `run_user` で戻す。`mret` の直前に読み直した `mstatus.MPP` は U だった。
  3. `net` は 0x2e9ea から M モードで動き、要求を処理して、返事の `Channel::send` の `ecall`（0x2ea62）でトラップ。
  - その間に割り込みのトラップはない。
- カーネルの中で `mstatus` を書くのは `run_user` だけ（と FPU の FS）。カーネルが動く間は MIE=0 で、カーネルの中のトラップは `kernel_trap` で止まる。ソフトウェアの道筋では、MPP=U のまま `mret` して M モードになる経路が見つからない。
- デバッガ（`t5log` の RTT）: Tab5（v1.x）の probe-rs は、L2MEM をプログラムバッファで読むときにコアを止める（doc/13 §3.3）。`t5log` は LP SRAM（システムバス、止めない）しか読まない。`spin` を両コアで回しながら、`t5log` を 20 回つなぎ直しても、50 秒つないだままでも、起きなかった。
- ESP32-P4 の公開の errata（v1.4）に、CPU のコアの項目はない。

## 3. 頻度と回避の試み
| カーネル | 起動の回数 | 起きた回数 |
|---|---|---|
| 確かめなし（doc/35 §5 の最初の版） | 約 6 | 2 |
| `mret` の前に `mstatus` を読み直す | 約 7 | 2 |
| `mstatus` と `mcause` を読み直す | 12 | 0 |
| `mstatus` だけに戻す（A/B） | 16 | 2 |
| `mstatus` と `mcause`（今の版） | 6 | 1 |

- 読み直しは効かない。全体で約 1 割の起動で起きる。
- 起きる場所は毎回同じ: Core0 の `net` の、チャネルの `READ` の後の `mret`（戻す番地 0x2e9ea）。起動 4 秒の 1 回だけが `OPEN` の後。ランダムなタイミングの不具合なら場所はばらつくはずで、何かの条件がある（推測）。

## 4. 今のカーネルの対策
- `run_user`: `mret` の前に `mstatus` と `mcause` を読み直し、MPP が U でなければ panic（`trap.rs`）。
- `run_slice`: プロセスからのトラップの直後に `mstatus.MPP` を見て、M なら `proc.mmode`（pid、戻した番地、トラップの番地、`mcause`）を記録してプロセスを止める（`sched.rs`）。M モードで動いた後に気づくだけで、その間のことは防げない。

## 5. 次に調べること
- 1 コア（Core1 を使わない）で起きるか。
- doc/35 §2 の「`READ` は呼び手のメモリへ直に写す」を戻して起きるか（毎回、チャネルの `READ` の後なので）。
- デバッガを一度もつながない起動で起きるか（今はリセットに probe を使う）。
- `mret` の前に `fence` や、`mcause` の読み直しのほかの待ちを入れて頻度が変わるか。
- Espressif に問い合わせる材料（再現の手順、`mcause` の値）を揃える。
