# 37. Wi-Fi の送信でバスを待たない（Core0）

利用者の指示（2026-11-02）:「すすめて」（doc/35 §6 の最初の候補）。

## 1. 前の形
- SDIO の書き込みは、DMA の終わりを待たずに戻る（doc/34）。ただし、次のコマンドを出す前に前の DMA の終わりを待つ（`sd::finish_write`）。
- `KICK` を Core0 で受けると、`flush_tx` が輪のフレームを全部続けて送っていた。2 つ目からは前のフレームの DMA（1.5 KB で約 80 µs）を待つので、その時間は `KICK` を呼んだ `net` の時間になる。
- 測ると（16 MiB の echo、プロファイラ）、`KICK`（`ctl`、259 番）は 8,770 回で 313 M サイクル（1 回約 36 k サイクル ≒ 99 µs）。`net` の標本の 18.8% がここだった。

## 2. 変えたこと
- `flush_tx` は、バスが空いている間だけ送る。前の書き込みの DMA がまだ動いていれば（`sd::write_busy`: IDSTS の TI と RINTSTS の DTO を読むだけで、待たない）、そこで戻る。
- 次のフレームは、DMA の終わりの割り込み（SDIO のホストの割り込み、TI。もとから Core0 に来て `finish_write` をしていた）で送る。スケジューラは、Core0 で装置の割り込みを処理した後に `flush_tx` を呼ぶ。
  - フレームは 1 つずつ、割り込みで続けて出る。`net` はその間も動き続ける。
- `WlanDev::write`（輪のない経路）も、Core0 ではまず待ち行列に入れてから `flush_tx` を呼ぶ。前は、`flush_tx` が待ち行列を送り切るのを待ってから、自分のフレームを送っていた。
- 割り込みが来なかったときも、フレームは残らない。`wlan::pending` は送るフレームがある間は真なので、Core0 は眠らずにスケジューラの回り目で送る。

## 3. 結果（16 MiB の echo、3 回）
| 版 | 片道 | `net` の CPU（1 回） | `KICK` のサイクル |
|---|---|---|---|
| doc/35 §5 | 12.3〜13.8 Mbps | 5.7〜5.8 秒 | 313 M（1 回 36 k） |
| **この版** | **12.8〜13.0 Mbps** | **5.4 秒** | **123 M（1 回 14 k）** |

- `net` の標本の中の `ctl` は 18.8% → 8.8%。
- 残りの 14 k サイクル（約 39 µs）は、フレームを出す仕事そのもの:
  - CMD53 を出して応答を待つ
  - bounce へ写す
  - 時々、C6 の空き数を読む（CMD53）
- 速さは変わらない。SDIO のバスとエアの速さで決まっていると見立てる（doc/34 §11.3 のばらつきの中）。

## 4. この先
- フレームを出す仕事も Core0 の割り込みに回せば、`KICK` はほぼ 0 になる。そうすると、その時間は Core0 の割り込みに移る。`net` が Core0 にいるときは、得にならない（判断: 今はやらない）。
- 輪を `netdev:host` にも（doc/35 §6）。
