# 43. PSRAM の転送が遅い理由とキャッシュの設定

利用者の指示（2026-11-03）:「すすめて。」doc/42 §4 の残り（CPU から PSRAM への転送が、書き込みで約 59 MB/s しか出ない理由）を調べた。doc/42 の報告で、PPA より先にこちらを勧めていた。

## 1. 計測の道具: `membench`
- カーネルのコマンド `membench [pause]`（`t5_abi::ctl` の `MEMBENCH` = 27）を足した。`kernel/src/platform/esp32p4v1/membench.rs`。
- 空いているプロセスのスロット（3 MiB）のうち 2 MiB を使う。1 回の試験は 1 MiB で、L2 キャッシュ（128 KiB）の 8 倍。
- カーネルの中で、割り込みを止めて動く。もう一方のコアは、自分のプロセスを動かし続ける。
  - 割り込みが止まっている間は、表示の DMA のリング（16 フレーム）が補充されず、途中で DMA が止まる。最初の版の数字はこれで乱れていた。今は、試験の合間に `display::service()` を呼ぶ。
- 試験の一覧:

  | 名前 | 内容 |
  |---|---|
  | `write32`、`write32+wb` | 4 バイトずつ書く。`+wb` はキャッシュの書き戻しまでを含む |
  | `write16+wb` | 2 バイトずつ（画素の `fill` にあたる） |
  | `read32` | 4 バイトずつ読む（先にキャッシュを空にする） |
  | `memcpy+wb`、`memmove+wb` | 1 MiB の複写と、40960 バイト（文字 1 行）ずらす複写 |
  | `cells_by_row+wb`、`cells_by_col+wb` | 270° の `term` と同じ形（1 マスは 1440 バイトおきの 64 バイト × 16）で 22 x 80 マスを、行の順または列の順に書く |
  | `uc_write32`、`uc_read32` | キャッシュを通さない窓（0x8800_0000）で 128 KiB |
  | `l1_read32`、`l1_write32` | L1 に収まる 16 KiB を 64 回（CPU 側の上限） |

- `pause` を付けると、表示の DMA を止めて（`display::pause`/`resume`）同じ試験をもう一度行う。
- 自動先読み（§4）の設定を試験ごとに変え、終わったら起動時の値に戻す。

## 2. 最初の結果: ミスの待ち時間が上限を決めていた
CPU 360 MHz、PSRAM 200 MHz、L2 128 KiB / 64 バイトのライン（ブートローダの設定のまま）、自動先読みなし。

| 試験 | 表示の DMA あり | 表示の DMA なし |
|---|---|---|
| `write32+wb` | 60 MB/s | 83 MB/s |
| `read32` | 76 MB/s | 96 MB/s |
| `memcpy+wb` | 41 MB/s | 56 MB/s |
| `memmove+wb` | 53 MB/s | 71 MB/s |
| `uc_write32` | 24 MB/s | 34 MB/s |
| `uc_read32` | 8 MB/s | 11 MB/s |
| `l1_read32` / `l1_write32` | 287 / 338 MB/s | 同じ |

読み取り:
- キャッシュを通さない 4 バイトの読み出しは 1 回約 360 ns。PSRAM の 1 回の取引（コマンド、アドレス、待ちのサイクル、データ）の待ち時間がこの程度ある。
- キャッシュ越しの読み出し 96 MB/s は、64 バイトのラインを 1 本約 670 ns で取ることにあたる。ミスは 1 本ずつ待たれ、重ならない。帯域でなく、待ち時間が上限を決めている。PSRAM の線の上のピーク（16 本 DDR、200 MHz で 800 MB/s）には遠い。
- 書き込みは、ラインを読んでから書き戻す（write-allocate）。このため、線の上では 2 倍を運ぶ。
- 表示の DMA は、1.84 MB のフレームを約 64 fps で読む（DPI 80 MHz、htotal 940、vtotal 1324）。これは約 118 MB/s で、CPU の転送を 25〜30% 下げる。
- L1 に当たるときの上限は約 290〜340 MB/s で、CPU の命令の速さで決まる。

## 3. 変更 1: L2 のラインを 128 バイトに
- ブートローダは、L2 を 128 KiB、64 バイトのラインにしている（`boot/sdkconfig` の `CONFIG_CACHE_L2_CACHE_LINE_64B`）。ESP-IDF のアプリは、起動時に `cache_hal_init` で L2 の設定をし直す（`esp_system/port/cpu_start.c:467-487`、`hal/cache_hal.c:58-77`）。128 KiB で 128 バイトのラインも、ESP-IDF の設定の選択肢にある（`esp_system/port/soc/esp32p4/Kconfig.cache:23-36`）。
- カーネルの `Platform::init` の最後で、同じことをする（`esp32p4v1.rs` の `set_l2_line`）:
  - RAM の中から、分岐予測を止め、L1 D を書き戻し、ROM の `Cache_Set_L2_Cache_Mode(CACHE_SIZE_128K, 8, CACHE_LINE_SIZE_128B)` と `Cache_Invalidate_All(L2)` を呼ぶ（ROM の番地は `esp32p4.rom.ld:180-194`、値は `rom/cache.h:97-110`）。
  - PSRAM を上げる前なので、L2 にはフラッシュのきれいなラインしかない。
  - ESP-IDF は 8 をそのまま渡している（`cache_hal.c:76`）ので、同じにした。
- 確認:
  - `CACHE_L2_CACHE_BLOCKSIZE_CONF`（0x3FF1_027C）が 8 から 16（bit4 = 128 バイト）に変わった。
  - ROM の `Cache_Get_L2_Cache_Line_Size` は 128 を返す。どちらも `membench.cache` に出る。
- ラインが大きいと、64 バイトにそろえた範囲を書き戻さずに無効にしたとき、隣の汚れたデータまで消えうる。PSRAM の範囲を無効にするところは、`retire_alias`（先に書き戻す）と、起動時の `map` だけだった。SD のバウンスバッファは L2MEM で、L2 を通らない。ラインの大きさに頼るところはなかった。

## 4. 変更 2: キャッシュの自動先読み（autoload）
- L1 D と L2 には、区間（4 つまで）を決めると、その中でミスしたときに続きのラインも読む機能がある（`cache_reg.h` の `CACHE_L1_DCACHE_AUTOLOAD_CTRL_REG` 0x134 以降、`CACHE_L2_CACHE_AUTOLOAD_CTRL_REG` 0x2B4 以降）。
  - リセットのときは切れている。ESP-IDF も ROM の設定を引き継ぐだけ（`cache_hal.c:49-54`）。
  - 起こる条件は、ミス（0）、ヒット（1）、両方（2）から選ぶ。
- 結果（128 バイトのライン、表示の DMA あり）:

  | 試験 | なし | L2 | L1 | L1+L2（ミス） | L1+L2（ミスとヒット） |
  |---|---|---|---|---|---|
  | `write32+wb` | 73 | 90 | 94 | 92 | 87 |
  | `read32` | 112 | 181 | 139 | 190 | 208 |
  | `memcpy+wb` | 64 | 84 | 70 | 75 | 62 |
  | `memmove+wb` | 81 | 105 | 89 | 102 | 108 |
  | `cells_by_row+wb`（ms） | 39 | 70 | 43 | 67 | 73 |
  | `cells_by_col+wb`（ms） | 23 | 22 | 23 | 22 | 21 |

  単位は MB/s（`cells_*` だけ ms）。

- 先読みは続けて読み書きするときに効く。その一方で、`cells_by_row` のように 1440 バイトおきに 64 バイトずつ書くと、要らないラインを読むので遅くなる（39 → 67 ms）。
- 決めたこと:
  - L1 D と L2 の両方で、ミスのときだけ先読みする。ヒットでも先読みする設定との差は小さい。投機的な読み出しが少ないほうを選んだ。
  - 区間は PSRAM の 2 つの線形の窓（`WINDOW` と `ALIAS`）。
  - ただし範囲は、フレームバッファより下（アプリ、共有メモリ）に限る。90° と 270° で描くと、フレームバッファは飛び飛びに書かれることが多い（`psram::autoload`。起動時は全体、`display_init` でフレームバッファの手前までにする）。
- `membench` は試験の後に、起動時の値（区間 0 と制御のレジスタ）を戻す。

## 5. 変更 3: `term` はフレームバッファの順に描く
- 270° では、文字の 1 列（16 画素の幅）が、フレームバッファの 16 行のひとつながりになる。
- `cells_by_col` は、どの設定でも `cells_by_row` より速い（64 バイトのラインでも 30 ms 対 36 ms、128 バイトでは 22 ms 対 39 ms）。1 つの列を描き終えるまで、その 16 行のラインがキャッシュに残るため。
- `Term::draw` は、`steps` がユーザーの y で ±1 になる向き（90° と 270°）のとき、列ごとにマスを描く。0° と 180° は行ごとに描く。

## 6. 実機での結果（ota_seq 64 以降のカーネル、`run term 1`）

| 何を | doc/42 の後 | 今 |
|---|---|---|
| 画面全体（1660 マス）を描く | 60 ms | **35 ms** |
| ベンチ（100 行、行ごとにスクロール） | 33.2 ms/行 | **28.6 ms/行** |
| `wrong_cells` | 0 | 0 |

- `membench` の数字（表示の DMA あり、128 バイトのラインと自動先読みあり）は、64 バイト・先読みなしと比べて次のとおり。
  - 書き込み: 60 → 92 MB/s
  - 読み出し: 76 → 190 MB/s
  - 複写: 41 → 75 MB/s
  - ずらす複写: 53 → 102 MB/s
- 途中の版（先読みをフレームバッファにもかけ、行の順に描いていた）では、全画面の描き直しが 94 ms に悪化した。§4 と §5 はその対策。

## 7. 残り
- 書き込みは、まだラインを読んでから書く。全部を上書きするライン（`fill` など）は、DMA（AXI GDMA の mem2mem、2D-DMA、PPA の塗りつぶし）でキャッシュを通さずに書けば、読み出しが要らない。doc/42 の候補 B（PPA）とあわせて検討する。
- 表示の DMA（約 118 MB/s）は、リフレッシュを 60 fps に下げても数 % しか変わらない。
- L2 を 256 KiB にする（SRAM が 128 KiB 減る）のは試していない。
