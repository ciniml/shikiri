# 44. PPA と 2D-DMA による描画（塗りつぶしと矩形のコピー）

利用者の指示（2026-11-03）:「すすめて」。doc/43 §7 の次の候補として、CPU を通さない描画のハードウェア（PPA と 2D-DMA）を使えるようにした。

## 1. 調べたこと
- レジスタの手順は、ESP-IDF 6.0 のドライバ（`esp_driver_ppa`、`esp_hw_support/dma/dma2d.c`、`hal`、`soc`）から、FreeRTOS とドライバの層を外した形でまとめた。出典は行番号つきで `doc/research/ppa-dma2d-registers.md` にある。
- 使うのは次の 3 つ（チップの rev v1.x、TX 3 本、RX 2 本）:

  | 操作 | 仕組み | チャネル |
  |---|---|---|
  | 塗りつぶし | PPA のブレンドエンジンの FILL（固定の画素を出力） | RX1（peri_sel 2） |
  | A8 の文字を固定色で重ねる | PPA の BLEND（背景 RGB565、前景 A8） | TX2 背景（peri_sel 2）、TX1 前景（3）、RX1 出力（2） |
  | 矩形のコピー | 2D-DMA の M2M（PPA を通さない） | TX1 → RX1（peri_sel 4 と 3、`in_mem_trans_en`） |

- 記述子（24 バイト）は L2MEM の静的な領域に置き、キャッシュを通らない別名（+0x4000_0000）で書く。表示の DMA のリストと同じ方法。
- DMA2D には、PSRAM の窓のアドレス（0x48xx_xxxx）をそのまま渡す。DMA はキャッシュを通らないので、カーネルが前後でキャッシュを書き戻し、無効にする（§4）。

## 2. 実機で見つけたこと
1. **`BLEND_TRANS_MODE` の update ビットは、別の書き込みで立てる**:
   - モードと update（bit3）を 1 回で書くと（塗りつぶしなら 0x0D）、エンジンは前の操作のモードで動いた。
     - リセット後の最初の塗りつぶしは終わらない（RX は記述子を取ったまま、PPA は何も出さない）。
     - 塗りつぶしの後の最初のブレンドは、出力が書かれなかった。
     - 同じ種類が続くときだけ正しく動くので、「最初の 1 回だけ失敗する」ように見えた。
   - ESP-IDF はビットフィールドを 1 つずつ書くので、update は必ず別の書き込みになる（`ppa_ll.h:614-635`）。
   - モード（0x05 または 0x01）を書いてから、update を加えた値（0x0D または 0x09）を書くようにして直った。
   - 調べている途中で、`PPA_REG_CONF.clk_en` と、ブレンドのときの `BLEND_TX_SIZE` も試した。update の件を直した後で外して試すと、どちらも要らなかった。どちらも ESP-IDF は書いていない。
2. **重なるコピーは、転送先がメモリの前にあれば正しい**:
   - 同じ画像の中で全体を 32 画素左へずらすコピー（`copy_scroll_left`）は、全画素が正しかった。
   - DMA は読む位置が書く位置より先に進むので、転送先が後ろ（下や右）にあると、まだ読んでいない元を上書きする（推測。試していない）。
   - 転送先が後ろ（行が下、または同じ行で右）で重なるコピーは、カーネルが **ずらす量以下の幅（高さ）の断片に分け、遠い端から順に** 行う。
     - 断片は、記述子のリスト（TX と RX、`next` でつなぎ、最後だけ suc_eof）にして、1 回の操作で行う。断片は最大 32 個で、それを超えると断る（`Invalid`）。
     - 各断片の転送先は、自分の元とも、まだ読んでいない断片の元とも重ならない。DMA が先の断片を先に読んでも問題ない。
     - 実機の `ppabench`: 32 画素右へ（32 列の断片 21 個）、64 行下へ（64 行の断片 20 個）。どちらも全画素が正しかった。

## 3. 速さ（実機、`ppabench`、720 x 1280 の RGB565、PSRAM）
カーネルのコマンド `ppabench`（`t5_abi::ctl` の `PPA_BENCH` = 28）は、空いたスロットに画像を置いて各操作を行い、全画素（文字はマスの両端と中央）を CPU で確かめる。結果はどれも誤りが 0 だった。

| 操作 | 時間 | 参考: CPU（doc/43 の後） |
|---|---|---|
| 全画面の塗りつぶし（1.84 MB） | 5.1 ms（360 MB/s） | 約 20 ms |
| 画面の半分のコピー（0.92 MB） | 6.8 ms | 約 12 ms（memcpy 75 MB/s） |
| 全画面を 32 画素左へずらすコピー（重なりあり） | 13.4 ms | 約 17 ms（memmove 102 MB/s） |
| 同じく右へ（32 列の断片 21 個） | 23.0 ms | 約 17 ms |
| 64 行下へ（64 行の断片 20 個） | 13.0 ms | |
| 32 x 16 のマスの塗りつぶし 1760 回 | 12.0 ms（1 回 6.8 µs） | |
| 32 x 16 の A8 の文字 1760 回 | 40.9 ms（1 回 23 µs） | `term` の全画面の描き直し 35 ms |

- 小さい操作は、チャネルのリセットと設定の手間が大きい。
- 文字を重ねる操作（ブレンド）は、CPU より速くならなかった。このため、アプリに出すのは塗りつぶしとコピーだけにした（判断）。ブレンドは `ppabench` の中だけで使う。

## 4. アプリからの使い方（ABI 小版 17）
- ディスプレイのハンドルに `write` で要求を書く（`t5_abi::display::op`）。値はリトルエンディアンの u16 で、座標はフレームバッファの画素（パネルの向き）。
  - `FILL, x, y, w, h, rgb565`
  - `COPY, src_x, src_y, dst_x, dst_y, w, h`
- カーネルは要求を受けると、次のことをしてすぐに返る。ハードウェアは、呼んだプロセスが動いている間に働く。
  1. 枠を確かめる。重なるコピーの向きも確かめ、だめなら `Invalid` を返す。
  2. 読む行をキャッシュから書き戻す。書く行は、書き戻してから無効にする。キャッシュに残った古い行が、後で結果の上に書き戻されないようにするため。
  3. 操作を始める。
- 一度に 1 つだけ。動いている間の `write` は `Busy` を返す。
- 終わると、RX1 の SUC_EOF の割り込み（interrupt source 105 を CLIC の 22、CPU の線 6 へ。線 5 は他方のコアからの IPI なので使えない）でカーネルが後始末をする。`wait` はイベント `display::DONE` を返す。失敗したとき（200 ms のタイムアウト、DMA のエラー）は `display::FAILED` を返し、カーネルはチャネルとエンジンをリセットして `ppa.failed` を記録する。割り込みを取りこぼしても、スケジューラのループが同じ確認をする。
- 終わるまでは、その行に触れてはいけない（ABI の約束）。
- `t5_rt::Display`:
  - `start_fill`、`start_copy`: ユーザーの座標の矩形を、フレームバッファの矩形に直して要求する。
  - `wait_done`: `DONE` で `Ok`、`FAILED` で `Err(Fail)` を返す。
- 使うのはプロセス自身のフレームバッファだけで、プロセスのメモリは DMA に渡さない。このため、途中でプロセスが終わっても、ほかのメモリは壊れない。

## 5. `term` での使い方
- 上へのスクロール（270° でフレームバッファの左へのコピー）に `start_copy` を使う。
- 下へのスクロールは、270° ではフレームバッファの右へのコピーになる。これは 32 列の断片に分かれ、CPU より遅い（23 ms）。このため、これまでどおり CPU でずらす。
- カーネルが断ったときも CPU でずらす。
- ハードウェアのコピーが失敗したときは、フレームバッファがどこまで動いたかわからない。このため、全部のマスを描き直す（`SHOWN` を `STALE` にする）。
- 起動時の画面の塗りつぶしに `start_fill` を使う。
- 結果（実機、`run term 1`）:

  | 何を | doc/43 の後 | 今 |
  |---|---|---|
  | ベンチ（100 行、行ごとにスクロール） | 28.6 ms/行 | **18.0〜19.1 ms/行**（2 回） |
  | 画面全体（1660 マス）を描く | 35 ms | 36 ms（文字は CPU のまま） |
  | `wrong_cells` | 0 | 0 |

## 6. t5emu
- `emu/src/dma2d.rs` に、カーネルが使う範囲の働きを足した。
  - 塗りつぶしとブレンドは `BLEND_TRANS_MODE` の update で、コピーは RX1 の開始で、その場で全部を行う。メモリに直接書き、キャッシュは通らない。
  - その後 RX1 の `IN_INT_RAW` に SUC_EOF を立て、ENA が立っていれば source 105 の割り込みを出す。
  - チャネルの `STATE` は、常に reset_avail を返す。
  - コピーは、TX と RX の記述子のリストを `next` でたどり、断片ごとに順に行う。
- `make test-p4emu` の `term` の試験（`run term 1`、全マスの画素の確認）は、エミュレータの 2D のハードウェアを通る。

## 7. 残り
- 文字の描画は CPU のまま。ブレンドを速くするには、行ごとにまとめて 1 回にする（CPU が A8 の行の画像を作る）などが要る。効果は未確認。
- 細い断片（1 行に 64 バイト）は遅い。右へのコピーは、いったん別の場所（使っていない画面の外など）へ写してから戻す 2 回のコピーにすれば、速くなるかもしれない（未確認）。
- 要求は 1 つずつ。複数の要求を記述子のリストでまとめれば、小さい操作の手間を減らせる。
