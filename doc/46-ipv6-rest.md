## 1. ICMPv6 のエラー（RFC 4443、`fwd6.rs`）
- 転送の途中で捨てるとき、送り元に返す:

  | 場合 | 返すもの |
  |---|---|
  | 経路がない | Destination Unreachable、code 0（no route） |
  | フィルタの `reject`（FORWARD） | Destination Unreachable、code 1（administratively prohibited） |
  | フィルタの `reject`（IN、自分あての IPv6） | 同じ（`fwd::rejects` の待ち行列から、IP の版で分ける） |
  | ホップ数が尽きた | Time Exceeded、code 0 |
  | 出ていくリンクの MTU（1500）より大きい | Packet Too Big（MTU 1500） |
  | 次の段が近隣探索に 1 秒答えない | Destination Unreachable、code 3（address unreachable） |

- フィルタは、これまで IPv6 の `reject` を `drop` に変えていた。今は IPv4 と同じく、OUT 以外では `reject` のまま返す。
- 返さないもの（§2.4 (e)）:
  - ICMPv6 のエラーへのエラー。
  - 送り元が未指定またはマルチキャストのもの。
  - 宛先がマルチキャストのもの（Packet Too Big は除く）。
- 1 秒に 10 通まで（IPv4 と同じ。超えた分は `icmp_limited` に数える）。
- 元のパケットは、エラー全体が 1280 バイトに収まるところまで引用する。
- 送り元のアドレスは、入ってきたリンクの自分のアドレスから選ぶ。
  - 優先する順: 宛先と同じ /64 のもの、グローバルなもの、リンクローカル。
  - ループバックは選ばない。最初の版は、ホストリンクで `::1` を選び、PC が受け取らなかった。
- `net.fwd6` の統計に `icmp_sent` と `icmp_limited` を足した。送るたびに Debug の `net.icmp6_error`（kind、code、link）を出す。
- t5emu の試験:
  - IPv6 の転送の試験（PC fd55::1 → Tab5 → 試験用 LAN の fd50::2）の後に、PC 役（`emu/src/hostpeer.rs`）が 2 つを送る。
    - ホップ数 1 の ping を fd50::2 へ。
    - 経路のない 2001:db8::1 への ping。
  - Tab5（fd55::2）から ICMPv6 の type 3 と type 1 が返るのを確かめた（`ICMP errors [3, 1]`）。IPv4 の試験と同じ形。

## 2. DNS
- **RDNSS を受ける**:
  - Wi-Fi の上流の RA の RDNSS（RFC 8106、option 25）から、DNS サーバを 2 つまでと、その寿命を覚える（`net.rdnss`）。
  - 寿命 0 の RDNSS が来たら忘れる。
- **自分の名前解決**:
  - smoltcp の DNS ソケットは、サーバを 1 つしか持たない（`dns-max-server-count` の既定は 1）。
  - DHCP（IPv4）のサーバがあればそれを使い、なければ RDNSS のものを使う（`dns_pick`）。前は DHCP のサーバがないと、名前を引けなかった。
- **DNS の中継**（doc/29）: 上流へ聞く先も `dns_pick` にした（IPv6 のサーバも可）。下流の IPv6 の問い合わせは、もとから受けていた（ポート 53 にアドレスを決めずに結ぶ）。
- **下流への広告**: NDP proxy の RA に、上流の RDNSS をそのまま載せる（寿命は残りと 1800 秒の短いほう）。
  - 下流の機器は、上流の /64 にいるので、上流の DNS サーバに転送で届く。
  - 自分（中継）を名乗る形にはしなかった。上流のサーバをそのまま渡すほうが、中継を通らずに単純なため（判断）。
- **実機の網**（iotap、2026-11-03）: `net.ra` に RA のフラグを足して見た。
  - 既定のルータの RA は flags=0x44（O と、RFC 4389 の proxy）で、RDNSS はなかった。
  - つまり、この網では IPv6 の DNS は DHCPv6（stateless、O フラグ）で配られる。RDNSS の部分は、この網では動かない（未確認）。
  - 下流の機器は、これまでどおり DHCPv4 と DNS の中継（IPv4）で名前を引ける。

## 3. 上流のプレフィックスが変わったとき
- 下流へ広告するプレフィックスが変わったら、前のプレフィックスも RA に載せる。2 つ目の PIO で、preferred 0、valid 0 にする。これを `PREFIX_VALID`（1 時間）の間続ける。
- 下流の機器は、古いアドレスを非推奨にし、新しい接続には新しいアドレスを使う。
- 古いアドレスは、残りの寿命（最大 2 時間）の間は残る（RFC 4862 §5.5.3 (e)。認証なしの RA では、valid を 2 時間より短くできない）。
- 上流の変化を起こせないので、実機でも t5emu でも確かめていない。

## 4. プライバシー拡張（一時アドレス、RFC 8981）
利用者の指示（2026-11-03）:「つづけて」。§5 の表で勧めたもの。

- **アドレス**（`net` の `EthLink::privacy`）:
  - SLAAC を使うリンク（Wi-Fi）で、SLAAC の /64 に、乱数の識別子のアドレスを 1 つ足す。
    - 識別子は 0 と、MAC から作る識別子と、RFC 5453 の予約（`fdff:ffff:ffff:ff80`〜`ff`）を避ける。
  - 寿命は RFC 8981 の既定どおり。推奨 1 日から、乱数で最大 4 割を引く（desync）。有効 2 日。推奨の時刻が来たら、新しいものを作る。
  - 前の一時アドレスは、それを使っている接続のために、有効の間は残す（最大 2 つ）。送り元には選ばない。
  - SLAAC の /64 がなくなったら、その一時アドレスも消す。
  - smoltcp の SLAAC は、自分が作った EUI-64 のアドレスだけを足し引きする。自分で足したアドレスは消されない（`sync_slaac_state`）。
  - 作るたびに `net.temp_addr`（アドレス、次に作るまでの時間）を出す。
  - アドレスの重複検出（DAD）はしない。64 ビットの乱数で重なることは、まずない（判断）。
- **送り元の選び方**（smoltcp の変更、`third_party/README.md`）:
  - 上流の smoltcp 0.14 は、RFC 6724 の規則 3（非推奨を避ける）と 7（一時アドレスを選ぶ）が TODO だった。同じ /64 に 2 つのアドレスがあると、先に足した（MAC から作った）ほうを使っていた。
  - `Interface::set_ipv6_source_preference(prefer, avoid)` を足し、選び方を規則 1、2、3、7、8 の順の比較に書き直した。`net` は、今の一時アドレスを選ぶアドレスに、前のものを避けるアドレスに渡す。
  - smoltcp の試験: 既存の 10 個と、新しい `get_source_address_temporary` が通る。新しい試験の中身:
    - 外への宛先と、同じ /64 の宛先では、一時アドレスを選ぶ。
    - 宛先が自分のアドレスなら、それを選ぶ（規則 1）。
    - リンクローカルの宛先には、リンクローカルを選ぶ。
    - 避けるアドレスは、ほかがあれば選ばない。
- **乱数**（カーネルのオブジェクト `random`、ABI 小版 18、`--permit random`）:
  - `read` で最大 64 バイトを返す。
  - ESP32-P4 では、RNG のレジスタ（`LP_SYSTEM_REG_RNG_DATA_REG`、0x5011_01A4）を、`esp_random` と同じく約 14 µs の間 XOR しながら読み、タイマーを混ぜる（`esp_hw_support/hw_random.c:49-80`）。
  - ESP-IDF によれば、このレジスタが真の乱数になるのは、エントロピー源（P4 では SAR ADC）が動いているときだけ。そうでなければ疑似乱数として扱う（`bootloader_random_esp32p4.c`）。
    - SAR ADC を動かすには、アナログの新しい設定が要る。この時はしていなかった。
    - このため ABI の説明では、一時アドレスなどの識別子には使ってよいが、鍵には使わない、とした。
    - その後、エントロピー源を動かした（doc/47）。今は鍵にも使える。
  - virt（QEMU、t5emu）では、タイマーを混ぜた値（乱数ではない）。t5emu は RNG のレジスタを xorshift で返す。
  - `t5_rt::random_fill`、`random_u64`。`net` は、smoltcp の乱数の種と一時アドレスに使う（前は時刻と MAC だけ）。
- **実機**（2026-11-03、iotap）:
  - 再起動の 26 秒後に、SLAAC のアドレス `2001:db8:0:1:e6b3:23ff:fe9a:1f24` と一緒に、一時アドレス `2001:db8:0:1:84e3:469f:94aa:2945`（22 時間後に作り直す）ができた。
  - 外へ出るときに一時アドレスが使われることは、実機では確かめられなかった。
    - one.one.one.one の `/cdn-cgi/trace`（見えた送り元を返す）は、HTTP を HTTPS へ転送した（301）。
    - PC は同じ /64 にいるが、Tab5 から PC へ IPv6 で送らせる手段がない。キーボードで打つか、`run` の引数（32 ビット）では足りない。
    - 選び方は、上の smoltcp の試験で確かめた。

## 5. まだ（利用者の判断が要るもの）
| 項目 | 内容 | 考え |
|---|---|---|
| DHCPv6（stateless） | Information-Request で IPv6 の DNS を得る。この網の O フラグに合う | 自分の名前解決は IPv4 の DNS で AAAA も引けるので、急がない。IPv6 だけの網で要る |
| DHCPv6（stateful）と PD | アドレスやプレフィックスを DHCPv6 で受ける | NDP proxy で足りている間は要らない |
| 乱数のエントロピー源 | SAR ADC を動かして、RNG のレジスタを真の乱数にする（§4） | 済み（doc/47） |
| DAD の中継（RFC 4389 の完全な形） | 下流の機器のアドレスの重複を上流で確かめる | EUI-64 なら重ならない。一時アドレスの機器が下流に来ると要る |
| NPTv6 | ホストリンク（fd55::/64）から IPv6 で外へ | PC は自分で IPv6 を持つので、要る場面が少ない |
