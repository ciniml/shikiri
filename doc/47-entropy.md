# 47. 乱数のエントロピー源（SAR ADC）

利用者の指示（2026-11-03）:「entropysourceよさそう。すすめて」（doc/46 §5 の表の「乱数のエントロピー源」）

## 1. 何のためか
- カーネルの `random`（doc/46 §4）は、RNG のレジスタ（`LP_SYSTEM_REG_RNG_DATA_REG`、0x5011_01A4）を読む。
- ESP-IDF によれば、このレジスタが真の乱数になるのは、エントロピー源が動いているときだけ。
  - ESP32-P4 では、エントロピー源は SAR ADC（`bootloader_random_esp32p4.c`）。
  - Wi-Fi の無線は C6 にあるので、P4 の側では無線の雑音を使えない。
- これまでは動かしていなかったので、`random` は鍵（TLS、SSH）に使わない、としていた。

## 2. 手順（`kernel/src/platform/esp32p4v1/entropy.rs`）
ESP-IDF 6.0 の `bootloader_random_enable` と同じ順に、同じ値を書く。

1. ADC をリセットし、クロックを入れる（`HP_SYS_CLKRST`）。
   - `HP_RST_EN2` の `rst_en_adc` を立てて下ろす。
   - `SOC_CLK_CTRL2` の `adc_apb_clk_en`、`PERI_CLK_CTRL23` の `adc_clk_en`。
   - クロック源は XTAL（`PERI_CLK_CTRL22` の `adc_clk_src_sel` = 0）、分周なし。
2. ADC のアナログのレジスタへの regi2c を使えるようにする（`PMU_RF_PWC`）。
   - `perif_i2c_rstb` を下ろし、`xpd_perif_i2c` を立て、`perif_i2c_rstb` を立てる。
   - アナログ I2C のマスタのクロック（`LPPERI_CLK_EN` の `ck_en_lp_i2cmst`）は、入れたままにする。ESP-IDF のアプリも、乱数のために入れたままにする。
3. regi2c（スレーブ 0x69、`ANA_CONF2` の bit 7）で、ADC のアナログの設定。
   - `DTEST_VDD_GRP1` = 0、`ENT_VDD_GRP1` = 1（`adc_ll_regi2c_init`）。
   - ADC1 の初期コード = 2166。
4. ADC1 のパターン表の 4 つに、channel 10、減衰 12 dB を入れ、長さを 1 にする。
5. ADC1 をデジタルの制御器につなぎ（`LP_ADC` の `sar1_dig_force` など）、電源を入れる（`xpd_sar1_force` = 3）。
6. ADC のクロックの分周 15、タイマーの間隔 100 で、タイマーで変換を続ける。

- ピンには触らない。
  - ADC1 の GPIO の channel は 0〜7（GPIO16〜23）。channel 10 はその外。
  - パッドの選択（`sar1_en_pad`）は 0 のまま。
- regi2c の関数は、PSRAM の MPLL で使っていたもの（`psram.rs`）を、スレーブを引数に取る形にして共用した。書き込みのマスク付きの版（`regi2c_write_mask`）を足した。
- 止める処理（`bootloader_random_disable`）は作っていない。このカーネルは ADC をほかに使わない。
- rev 3.0 以上の P4 にある `LP_TRNG` は、Tab5 の P4（v1.x）にはない。ESP-IDF でも rev 3.0 以上だけで動かす。

## 3. いつ動かすか
- `clock_init` の最初（PSRAM の後、PVT とクロックの前）。
  - PVT がないときの早い戻りより前に置いた。クロックがどうなっても動かすため。
  - アプリ（`net` など）が `random` を読むのは、これより後。
- 動かした後、20 µs おきに ADC1 の値（`SAR1_DATA_STATUS`）を 8 回読み、違う値の数を `rng.entropy`（`distinct`）に出す。変換が進んでいることの目安。
- 失敗（regi2c が busy のまま）なら `rng.no_entropy`。そのときも起動は続ける。

## 4. 結果
- 実機（2026-11-03）:
  - `rng.entropy source=sar_adc distinct=4`、再起動の後は `distinct=3`。ADC の値が揺れている。
  - 自己試験は pass。`net` は一時アドレス（`2001:db8:0:1:980c:300e:2c09:48ca`）を作った。ps で全プロセスが動いている。
- t5emu: ADC のレジスタの模型はない（読むと 0）。`distinct=1` で起動は通る。
- 出力の統計的な検定は §5。

## 5. 出力の検定
利用者の指示（2026-11-03）:「RNG 出力のテスト」

### 5.1 取り出し方
- ctl のコマンド `rngdump [raw [US]]`（`ctl::cmd::RNG_DUMP`）: 空いたスロットの 2 MiB（1 Mbit の列 16 本）を埋め、`rng.dump`（番地、かかった時間）を出す。
  - 引数なし: `random_u32`（アプリの `random` と同じもの）。
  - `raw US`: RNG のレジスタを US µs おきに 1 回だけ読んだ値（XOR しない）。0 なら続けて読む。
  - 4096 語ごとにウォッチドッグを叩き、表示の DMA の輪を補う。最後にキャッシュを書き戻す（プローブはキャッシュを通らずに読む）。
  - 56 µs おきだと 30 秒かかる。その間カーネルはほかのことをしない（試験用のコマンド）。65536 語ごとに `rng.dump_progress` を出す（`t5log --until-done` は 30 秒ログがないと止まる）。
- `t5log read --probe … ADDR LEN -o FILE`（新しいサブコマンド）: デバッグモジュールのシステムバスで読む。ハートは止めない（doc/36）。約 85 KB/s、2 MiB で 24 秒。
  - インストールされている probe-rs の CLI は古く、P4 を知らない。t5log が使う probe-rs のライブラリで読む。
- `tools/rngtest.py FILE...`: numpy と scipy だけで書いた検定（ホストに rng-tools、ent、dieharder がないため）。
  - `ent` に似た要約: バイトのエントロピー、カイ二乗、平均、系列相関、lzma で縮む割合、最頻値からの最小エントロピー（SP 800-90B §6.3.1 の MCV）。
  - FIPS 140-2 の 4 つ（20000 ビットのブロック、rngtest と同じ）。
  - NIST SP 800-22 の 8 つ（frequency、block frequency、cumulative sums、runs、longest run、DFT、serial m=16、approximate entropy m=10）。p ≥ 0.01 の列の割合が §4.2.1 の範囲（16 本で 0.915 以上）なら合格。
  - 確かめ: `/dev/urandom` の 2 MiB は全部合格。最下位ビットを 0 に固定した乱数は全部不合格。

### 5.2 結果（実機、2026-11-03）
| データ | エントロピー（ビット/バイト） | カイ二乗の p | FIPS 140-2 の失敗（838 ブロック） | SP 800-22 |
|---|---|---|---|---|
| `random_u32`（1 語 14 µs、前の版） | 7.99991 | 0.262 | 2 | 8 つとも合格 |
| `random_u32`（1 語 56 µs） | 7.99993 | 0.993 | 0 | 8 つとも合格 |
| レジスタ、続けて読む | 7.772 | 0.000 | 全部 | 8 つとも不合格 |
| レジスタ、14 µs おき | 7.772 | 0.000 | 全部 | 8 つとも不合格 |
| レジスタ、56 µs おき | 7.773 | 0.000 | 全部 | 8 つとも不合格 |

- **レジスタそのものは偏っている**。読む速さによらず、同じ形:
  - 32 ビットのうち 11 ビットは 1 になる確率が 0.75、1 ビットが 0.33、1 ビットが 0.65、残りは 0.5。
  - ビットごとの最小エントロピーを足すと、1 語で約 25.3 ビット。
  - 前の語との相関はビットごとに最大 0.013、ビットどうしの相関は最大 0.10。
  - つまり、このレジスタの値をそのまま鍵にしてはいけない。`esp_random` のように、何回も読んで混ぜる必要がある。
- **`random_u32` の出力は全部合格**。56 µs の間に約 200 回読んで XOR する。1 回あたり 25 ビット近くあれば、1 語 32 ビットには十分。
- **読む間隔を 14 µs から 56 µs に直した**（`RNG_WORD_US`）:
  - ESP-IDF の `esp_random` は、P4 で「CPU と APB の比（360/90 = 4）× 14 × 360 サイクル」= 56 µs を 1 語ごとに待つ。コメントには「約 75 kB/s で試験した」とある（1 語 56 µs で約 71 kB/s）。
  - 前の版（doc/46 §4）は「14 × 16 ティック」= 14 µs で、ESP-IDF の 4 倍の速さだった。検定はどちらも合格だが、Espressif が試験した速さに合わせた。
  - `random` の 64 バイトの読み出しは、約 0.9 ms になる。
- **限界**:
  - これらの検定は、悪い生成器を見つけるもの。決定的な生成器でも、よく混ぜてあれば合格する。合格は、エントロピーがあることの証明ではない。
  - エントロピー源を止めたときの出力と比べていない（止める処理は作っていない。§2）。
  - SP 800-22 の 15 の検定のうち 8 つ、列は 16 本だけ（p 値の一様性の検定はしていない）。SP 800-90B の完全な評価もしていない。

## 6. 残り
- エントロピー源を止めた状態との比較（`bootloader_random_disable` の手順。アナログの新しい書き込みになるので、するなら確認してから）。
- 長いデータ（数百 MB）での検定。今の取り出し方（プローブ、85 KB/s）では時間がかかる。
