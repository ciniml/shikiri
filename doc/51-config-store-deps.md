# 51. 設定の置き場所と暗号化、C6 の記憶、アプリの依存関係、権限（検討）

利用者の指示（2026-11-05）:「ファイアウォールの更新してよいです。SDの平文はcfgを暗号化対応することを考えましょう。cfgの設定を保持する領域としてNVSの対応も検討。C6がどうなっているかはesp-atファームウェアを確認してください。wifiとbleの依存関係については、アプリの依存関係設定などの仕組みを検討してください。そういえばアプリの権限管理はありますか？」

ファイアウォール: `run netctl 7` で `T5OS/NET.RUL` を守りの組（規則 6 つ）に書き直した。`netctl 0`（起動時と同じ読み込み）で rules=6、PC からの ping は届かず、smctl の toggle は通る。

## 1. C6 は渡された網を覚えているか
- C6 で動いているのは esp-at ではなく **esp_hosted 2.12.7** のスレーブ。INIT のイベントの版で確かめた（doc/22 §5）。
- そのソースを読んだ（github.com/espressif/esp-hosted-mcu、`feature/release_2_12_7` のマージ 8610f4f5。リポジトリには入れない）。
  - `wifi_init_config` の `nvs_enable` は、ホストの値がそのまま使われる（`slave/main/slave_wifi_std.c:189` の `USE_HOST_VALUE`）。
  - `wifi` は `nvs_enable` = 1 を送っている。ESP-IDF の Wi-Fi は、そのとき `esp_wifi_set_config` の STA の設定（SSID と passphrase）を C6 の NVS に書く。
  - **C6 のフラッシュには、最後に `wifi` が設定した網が passphrase ごと残る**（推測。ESP-IDF の `nvs_enable` の動き。C6 のフラッシュは読んでいない）。
  - スレーブが自分で `esp_wifi_set_storage(WIFI_STORAGE_FLASH)` を呼ぶのは、ネットワークを分ける構成（`CONFIG_ESP_HOSTED_NETWORK_SPLIT_ENABLED`）の `connect_sta` だけ（`esp_hosted_coprocessor.c:1099`）。M5Stack のビルドがこれを有効にしているかは分からない。Tab5 ではホストが接続を始めているので、無効と見てよい（推測）。
- **手当の案**（どれも C6 のファームウェアは書き換えない）:
  1. `WIFI_INIT` で `nvs_enable` = 0 を送る。スレーブは前と違う値なら Wi-Fi を止めて初期化し直す（`__wrap_esp_wifi_init`、`slave_wifi_std.c:352-387`）。以後、C6 は網を書かない。
  2. 残っている網を消す: `Req_WifiRestore`（291、`esp_wifi_restore`）。ESP-IDF の説明では、Wi-Fi の保存した設定を既定に戻す。C6 の NVS への書き込みになる。
  - 案 1 だけなら、既に書かれた分（今は `iotap`）は残る。消すなら、1 の前に 2。

## 2. `cfg` の置き場所と暗号化
### 2.1 今の弱いところ
- **SD の `T5OS/CONFIG.A/B` は、`svc:fs` の許可を持つアプリなら誰でも読める**。`fs` はクライアントを見分けず、パスの制限もない。今、`svc:fs` の許可は `matter`、`shell`、`netctl`、`init`、`mtbench`、`fstest`、`cfg` にある。`svc:cfgsec` で読める者を `wifi` に絞っても、ファイルを直に読まれる。
- SD を抜けば、PC でそのまま読める。

### 2.2 P4 のフラッシュに置く
- ESP-IDF の `nvs` の区画（0x9000、16 KiB）は**使わない**（判断）。
  - 中身を読んだ（読むだけ。キーの名前と型だけを見て、値は見ていない。読んだファイルは消した）: セクタ 0 に ESP-IDF の NVS のページが 1 つあり、前に入っていたファームウェアのデータが残っている。
    - Wi-Fi の `ssid`、`psk`、`ap_psk`。
    - Tailscale らしい `machine_priv`、`node_priv`、`disco_priv`。
    - `pin_hash`、`ssh_tofu`、`M5GFX` ほか。
  - 消すかどうかは利用者が決めること。
- **`userdata`（0xC20000、3.9 MiB、今は使っていない。doc/28）の先頭 64 KiB** を `cfg` に使う（案）。先頭の 256 KiB は消去された状態（全部 0xFF）だった。
  - 形は今のファイルと同じ表（`cfg::Table::image`、4 KiB）。セクタ A と B に交互に書く。セクタ 1 つ（4 KiB）に表が 1 つ入る。
  - カーネル: 新しいオブジェクト（例 `flash:cfg`）。そのセクタだけを読み、消し、書く。`flash.rs` の `writable` にその範囲を足す。許可は `cfg` だけ。
    - 消すと書くは、ストアのインストールと同じ道（割り込みを止めて 1 回 20 ms ほど）。設定の保存はたまにしか起きない。
    - 新しい区画への書き込みなので、利用者の承認が要る（tab5-hw-safety）。
  - 移行: 起動時にフラッシュの表がなく SD に `CONFIG.A/B` があれば読み込み、フラッシュに書き、SD のものを消す。
  - t5emu はストアのフラッシュを持っているので、同じ範囲を足せば試験できる（SD がなくても保存まで試せる）。
- フラッシュに置けば、SD を抜かれても、ほかのアプリが `svc:fs` で読んでも、設定は出ていかない。

### 2.3 暗号化
- 何から守るかで、要るものが変わる。
  1. **SD のファイルを読まれる**（§2.1）: 設定をフラッシュに移せば、この心配はなくなる。SD に置き続けるなら、秘密の値を暗号化する。鍵はフラッシュ（§2.2 の範囲）に置く。
  2. **本体を持ち去られ、フラッシュを読まれる**: 鍵が同じフラッシュにあれば、暗号化しても意味がない。
     - 防ぐには、鍵を eFuse に置く。P4 の HMAC の周辺機能は、ソフトから読めない eFuse の鍵（用途 `HMAC_UP`）で HMAC を計算できる（要確認: P4 の TRM の HMAC の章）。`cfg` の鍵は HMAC(eFuse の鍵, "t5os-cfg") で作る。
     - **eFuse は書いたら戻せない**。鍵のブロックを 1 つ使う。
     - USB-JTAG とダウンロードモードが開いていれば、フラッシュの暗号化がない限り、フラッシュはどのみち読める。今はプローブで開発しているので、この脅威はまだ防げない。
  3. **ほかのプロセス**: カーネルの許可で分けている（`svc:cfgsec` は `wifi` だけ）。
- **案**: `cfg` に、鍵の出どころを替えられる暗号の層を足す。
  - 秘密の値を AEAD（ChaCha20-Poly1305 か AES-GCM。RustCrypto、no_std）で包む。保存のたびに nonce を作り直し、キーの名前を関連データにする。
  - 鍵の出どころ: まずはフラッシュに置いた乱数 32 バイト（初回にカーネルの `random` から作る）。後で eFuse の HMAC に替える。
  - フラッシュに置いた表の暗号化は、2 の脅威に対しては見かけだけ。SD に書き出すとき（バックアップ）の意味が大きい。
- **勧める順**: (1) 設定をフラッシュ（`userdata` の先頭）へ移す。(2) 秘密の値の暗号化を、鍵はフラッシュから。(3) 量産に近づいたら、eFuse の鍵とフラッシュの暗号化（JTAG を閉じるかどうかも一緒に）。

## 3. アプリの依存関係
### 3.1 今
- `init` はリストの順に、待たずに起動を頼む。依存は各アプリの中の待ち合わせで手当てしている。
  - `init` と `netctl` と `cfg`: `fs` を 10 秒まで待つ。
  - `matter`: `net` を 10 秒まで待つ。
  - `wifi`: `cfg` を 3 秒まで待つ。
- **`ble` は、`wifi 1` が C6 の Bluetooth を起動するまで動けない**。待たずに先に起動すると CPU を使い切り（cpu_pm 996）、広告もしない。何が回っているか（HCI の Reset の答えがない間の再試行か、`bt:hci` の読みの誤りか）はまだ調べていない。

### 3.2 案
1. **依存を宣言する: T5A の新しい TLV `Needs`**（`elf2t5a --needs NAME`、Makefile の `NEEDS_<app>`。`--permit` と同じく署名の中）。
   - 名前は、サービス（`svc:NAME` に listener がある）か、準備の印（下の `ready:NAME`）。
   - カーネルは、`proc:spawn` でもコンソールの `run` でも、`Needs` が全部そろうまで起動を待たせる。`proc.waiting needs=…` を出し、10 秒でそろわなければ `proc.needs_timeout`。
   - 足りないものを起こすことはしない。何を起動するかは、今までどおり `START.CFG` が決める。
2. **準備の印 `ready:NAME`**: サービスでない条件のため。
   - 許可を持つプロセスが `open("ready:NAME")` で印を立て、プロセスが終われば消える。
   - 例: `wifi` は BT を起動したら `ready:bt` を立てる（`--permit ready:bt`）。`ble` は `--needs ready:bt`、`matter` は `--needs svc:net`、`wifi` は `--needs svc:cfg`。
   - 起動の順の問題が、アプリの中の待ち合わせなしに解ける。
3. **それでも各アプリは、相手がいなくても回り続けない**: `ble` は BT がないとき、待つかエラーで終わるように直す（`Needs` を使わずに `run ble` したときのため）。
- 代わりの案: `START.CFG` の行に `after=SERVICE` を書き、`init` だけが待つ。カーネルは変えずに済むが、`run` やシェルから起動したときは効かない。
- **勧める案**: 1〜3（宣言は署名した像の中、待つのはカーネル）。

## 4. アプリの権限（今あるもの）
- **ある**:
  - アプリの像は ed25519 で署名され、カーネルは検証してから動かす（doc/14）。
  - 署名の中の Permissions TLV に、`open` してよいオブジェクトの名前を並べる（`elf2t5a --permit`、Makefile の `PERMIT_<app>`）。ないものの `open` は `Denied` になり、`proc.denied` が出る（自己試験 `fault/open-denied`）。名前は次のとおり。
    - デバイス: `display`、`touch`、`kbd`、`sd`、`wlan:ctl`、`bt:hci`、`netdev:*`、`random`、`timer`。
    - サービス: 使う側は `svc:NAME`、提供する側は `listen:NAME`。
    - プロセスの操作: `proc:spawn`、`proc:list`、`proc:apps`、`proc:kill`。
    - その他: 共有メモリ `shm`、`chan:NAME`。
  - ハンドルには権利（読む、書く、待つ、ctl）があり、呼ぶたびに確かめる。
  - `proc:spawn` で起動したアプリは、起動した側の許可ではなく、自分の像の許可で動く。
  - プロセスは U モードで、PMP で互いのメモリとカーネルから隔てる。
- **ないもの・粗いところ**:
  - 許可はオブジェクトの名前の単位。サービスの中の細かい区別（どのキーを、どのファイルを）はできない。サーバはクライアントが誰かを知らない。それで `cfg` はサービスを 2 つに分けた。
  - `svc:fs` は SD 全体を開く（§2.1）。
  - `proc:kill` を持てば、どのプロセスも止められる。
  - 許可はビルド時に決まる。動いている間に取り上げたり、利用者に尋ねたりする仕組みはない。
  - 信頼の元は署名の鍵 1 つ。その鍵で署名した像は、どんな許可でも名乗れる。
  - 署名の鍵（`~/.config/tab5-os/dev-ed25519.key`）は開発用。
- 次に足すなら（案）:
  - クライアントの身元をサーバに渡す（`accept` が相手の像の名前か pid を返す）。それで `fs` はアプリごとのディレクトリに、`cfg` はキーごとの読み書きに絞れる。
  - `proc:kill` を、自分が起動したプロセスだけに絞れる形にする。
