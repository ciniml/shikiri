# 54. シリアルからの画面のキャプチャとタッチの入力（デバッグ）

利用者の指示（2026-11-05）:「画面と入力のプロセスにデバッグ機能として、画面をシリアル通信経由でキャプチャする機能と、シリアル通信経由でタッチ入力を行う機能を実装してください。」

## 1. 今の形
- 画面（`display`）とタッチ（`touch`）は、プロセスではなくカーネルの持ち物（`kernel/src/screen.rs`、doc/17 §6）。
  - 画面は、PSRAM のフレームバッファ（720 × 1280、RGB565）を 1 つのプロセスに貸す。
  - タッチは、`touch` を開いたプロセスがいる間、カーネルが 16 ms ごとにコントローラを読む。そして利用者の向きの座標にして渡す。
- シリアル（USB Serial/JTAG、PC からは `/dev/ttyACM3`）には、構造化ログのフレームが流れている（doc/12）。
  - PC からの受信は、ホストリンク（doc/21）が開いている間だけ読んでいた。
  - その中身は、IP のパケット（先頭 0xFF）だけだった。
- 制御コマンド（`run`、`kill` など、doc/14 §3）は、RTT の down チャネル（プローブ経由）だけで受けていた。

## 2. 方針
- **コマンドをシリアルでも受ける**: 形は RTT と同じ COBS フレーム（`u8 command | u32 request_id | 引数`）。
  - これで、プローブがなくても USB ケーブルだけで操作できる。
  - 答え（`ctl.done`/`ctl.failed`）とイベントは、今までどおりログに出る。ログはシリアルにも出ている。
  - カーネルは、ホストリンクが開いていなくても線を読む。
    - 先頭が 0xFF のフレームはパケットとして扱う。リンクが閉じていれば捨てる。
    - それ以外はコマンドとして扱う。
  - コマンドは 4 つまで待たせる。待っている間は線を読まない。PC の書き込みは USB の中で待つ（流量の制御、判断）。
  - USB に触れる人は JTAG でメモリも読み書きできる。そのため、シリアルで全部のコマンドを受けても、できることは増えない（判断）。
- **画面のキャプチャ `capture`**: フレームバッファを `t5_abi::capture` のフレームにしてシリアルへ送る。
  - フレームの種類は、ログと区別するため先頭を 0xFE にする。ログの記録の先頭はレベル（4 以下）、パケットは 0xFF。
  - START（id、幅、高さ、向き、形式）、DATA（最初の画素の番号と、ラン長で縮めた 512 画素）、END（画素の数、生の画素の CRC-32）。
  - 縮め方: 1 バイトの頭で、「次の画素を n 回」か「続く n 画素をそのまま」（n は 128 まで）。単色の背景が多い画面はよく縮む。
  - 送るのはスケジューラの回りごとに 1 ms ずつ。その間もプロセスは動く。送り終わるまで、カーネルは眠らない。
  - 画素は、その時のものを読む。写しは取らないので、送っている間に変わった画面は混ざる（判断: デバッグ用なのでメモリを使わない）。
  - 誰も線を読んでいなければ（FIFO が詰まれば）、やめて `capture.failed` を出す。
- **タッチの入力 `tap X Y [MS]`、`swipe X0 Y0 X1 Y1 [MS]`**: 利用者の向きの座標で、指を 1 本置く。
  - 置いている間は、コントローラの読みの代わりにこの点を渡す。
  - `swipe` は、16 ms ごとの読みのたびに、始点から終点へ線形に動かす。
  - 時間の既定は、`tap` が 100 ms、`swipe` が 300 ms。32 ms〜10 秒に丸める。
  - 指を離したら `touch.injected` を出す。
  - `touch` を開いているプロセスがいなければ断る（誰にも見えないため）。画面の外の点も断る。
- **PC の側 `t5log serial`**:
  - `--port /dev/ttyACM3`、`--cmd` を 1 つずつ送る。前のコマンドの答え（`capture` なら画面の最後）を待ってから次を送る。
  - ログを表示する。キャプチャは利用者の向きに回し、PNG に書く（`--capture-dir`）。
  - PNG は無圧縮の deflate なので、ライブラリは要らない。1280 × 720 で約 2.7 MB。

## 3. 使い方
```
tools/target/release/t5log serial --port /dev/ttyACM3 --elf build/t5-kernel-esp32p4v1.elf \
  --cmd "tap 200 300" --cmd "capture" --capture-dir . --until-done
```
- `--until-done` がなければ、標準入力の行もコマンドになる。
- `t5log rtt --cmd capture` でもキャプチャを始められる。ただし画面はシリアルに出るので、シリアルを読んでいる必要がある。
- `t5log hostlink` と `t5log decode` は、キャプチャのフレームを読み飛ばす。

## 4. 実装
- `abi/src/capture.rs`: フレームの形、ラン長の符号化と復号、CRC-32。
- `abi/src/ctl.rs`: コマンド 32 `capture` と 33 `touch_inject`（`tap`/`swipe` の行から作る）。
- カーネル:
  - `kernel/src/capture.rs`: スケジューラのループから `poll`、`pending` の間は眠らない。
  - `kernel/src/screen.rs`: `inject`。タッチの読みで、置いた指を優先する。
  - `kernel/src/hostlink.rs`: 線を常に読む。パケット以外はコマンドの待ち行列へ。
  - `kernel/src/main.rs`: `serve` で RTT とシリアルの両方からコマンドを受ける。
- `tools/t5log`:
  - `capture.rs`: 組み立て、向きの回転、PNG。
  - `Item::Capture`。
  - `t5log serial`。
- t5emu:
  - USJ のキャプチャのフレームをログから分ける。RTT との突き合わせは今までどおり。
  - `--ctl "serial COMMAND"` でシリアルから送る。
  - `--capture-out`、`--expect-pixel X,Y,RGB565`。
  - `capture` が終わるまで、走りを止めない。

## 5. 試験と結果
- 単体:
  - abi: ラン長の往復と、CRC-32 の検査値。
  - t5log: 組み立てと回転、欠けたフレームが誤りになること、Adler-32。
- t5emu（`make test-p4emu` に足した）:
  - `paint` を起動し、シリアルから `tap 600 400` と `capture` を送った。
  - 1280 × 720 の画面が 1802 フレームで届いた。
  - (600, 400) は `paint` の赤（0xFA8A）、左上の白い印は (20, 20)、背景は (300, 600)。
  - 模擬時間 13.4 秒の走り。
- 実機: §6。

## 6. 実機の記録
2026-11-05。カーネルを `good.t5k` の手順（`kupdate-test-kernels` → `kupdate`）で入れ直した。以後の操作は、プローブを使わずに、`t5log serial --port /dev/ttyACM3` だけで行った。
- `ps`: 9 つのプロセスの `proc.info` と `ctl.done` が、シリアルで返った。
- `capture`（シェルの画面）:
  - 114 ms で届いた。縮めた後は 47,682 バイト（生の 1,843,200 バイトの約 2.6 %）。
  - 1280 × 720 の PNG で、文字が正しい向きに写っていた。
- `mtpanel`:
  - シリアルから `kill`（`term`）と `run mtpanel 120` を送って起動した。
  - `tap 192 256`（タイルの中）で `mtpanel.touched on=true`、`mtpanel.state on=true`、`touch.injected` が出た。
  - 前後のキャプチャ（それぞれ 123 ms と 122 ms）で、タイルが OFF から ON に、一覧の `4 light` が 0 から 1 に変わった。
  - `tap 1300 100` は `outside the screen` で断られた。
- `paint`:
  - `swipe 200 200 1000 600 800` の後のキャプチャに、始点から終点まで四角の線が描かれていた（16 ms ごとの読みで約 50 点）。
- 終わりに、シリアルから `run term` を送って画面を戻した。
