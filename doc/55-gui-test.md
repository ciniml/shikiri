# 55. 画面の自動の試験（`mtpanel`）

利用者の指示（2026-11-06）:「これらの機能を使えばGUIの自動動作確認ができるはずです。試しにMatter用のGUIの動作確認を行ってみてください」。続けて「実施してください。」

doc/54 §6 では、`mtpanel` のキャプチャを人（Claude）が目で見て確かめた。ここでは、同じことをスクリプトが決まった手順で行い、合否を出す。

## 1. 方針
- **操作**: `t5log serial`（doc/54）を、対話の形（標準入力のコマンド、`--json` のイベント）で子のプロセスとして使う。操作はシリアルだけで、プローブは使わない。
- **画面の読み**: キャプチャの PNG を読み、`mtpanel` の `draw` が描くはずのものと比べる。
  - 色は画素で比べる。期待する色は、`t5_rt::rgb` の RGB565 を、`t5log` が PNG にするときと同じく 8 ビットに戻したもの。
  - 文字は、`mtpanel` と同じ Terminus（16 × 32）のグリフと、升目ごとに照らし合わせて読む。文字の色でも背景の色でもない画素があれば、その升目は `?` にする。OCR は要らない。描く位置と倍率がわかっていれば、正確に読める（判断）。
- **待ち**: `mtpanel` は描くのに時間がかかる。また、一覧は 3 秒ごとにしか読み直さない。そのため、期待する画面になるまで撮り直す（8 秒まで）。
- **イベント**: 切り替えは `mtpanel.touched`（触った）と `mtpanel.state`（`matter` から戻った状態）で確かめる。変わらないはずの操作では、1.5〜2 秒の間にこれらが出ないことと、`touch.injected` が出たことを見る。

## 2. 試験（`tools/guitest-mtpanel.py`）
```
tools/guitest-mtpanel.py --out DIR [--smctl "SMCTL --state-dir D"] [--node 1]
```
- 始めに `ps` で調べ、動いている `mtpanel` と `term` を止める。終わりに `mtpanel` を止め、`term` を起動し直す。タイルの状態も元に戻す。
- 画面の検査（`screen_errors`）:
  - 大きさが 1280 × 720 であること。
  - 帯の色と、題（`Matter  endpoint N`）。
  - 背景の色。
  - タイルの 4 隅と中の色、タイルのすぐ外が背景であること。
  - タイルの文字（`ON`/`OFF`、3 倍、色の組み合わせも）。
  - 下の案内（`touch to switch`）と、一覧の見出し（`endpoints`）。
  - 一覧に `N light 0/1` が 1 行だけあり、その値がタイルと合うこと。
- 項目:
  1. 起動の画面（`mtpanel.ready` のエンドポイントと、最初の `mtpanel.state`）。
  2. タイルの中央の `tap` で切り替わる。もう 1 度の `tap` で戻る。
  3. タイルの外（700, 600）の `tap` では変わらない。
  4. 端: 左上の隅（32, 96）と右下の隅（351, 415）では切り替わる。右に 1 画素外（352, 256）では変わらない。
  5. `swipe`: 外から入るものでは変わらない（指が下りたときだけ数える）。中から出るものでは 1 度だけ切り替わる。
  6. `--smctl` を渡すと: PC の smctl の `onoff toggle` で `mtpanel.state` が変わり（`mtpanel.touched` はなし）、画面が描き直される。2 回行って元に戻す。
- 出力: 項目ごとに `PASS`/`FAIL`、`DIR/guitest-mtpanel.log`（`t5log` の出力全部）、キャプチャの PNG。全部通れば終了コードは 0。

## 3. 見つけた不具合: 描いている途中のキャプチャで CRC が合わない
- 1 回目の実機の試験（8/12）では、4 つの項目が「15 秒キャプチャが届かない」で落ちた。
  - `t5log` は `capture 32: CRC 212cd066, expected 3b65f916` で、その画面を捨てていた。
  - どれも、`mtpanel` が 3 秒ごとの一覧の読み直しの後で、画面を描き直している間のキャプチャだった。
- 原因: `kernel/src/capture.rs` は、フレームバッファ（PSRAM）の同じ 512 画素を 2 回読んでいた。1 回は CRC-32 のため、もう 1 回はラン長で縮めるため。その間にプロセスが描くと、CRC と送った中身が別の画素になる。
- 直し: 512 画素を静的な場所に 1 度写し、CRC と縮めの両方をその写しから行う。
  - 画面が混ざること自体は、今までどおり起こりうる（doc/54 §2 の判断のまま）。
  - CRC は、送った画素について常に正しくなる。混ざった画面は検査で外れ、撮り直しになる。
- スクリプトの側: キャプチャが誤り（`t5log` の CRC の誤り、カーネルの `capture.failed`）になったら、すぐに撮り直す。

- カーネルを `good.t5k` の手順で入れ直した（slot 1、`valid`）。
- `tools/guitest-mtpanel.py --smctl …`（smctl はノード 1 の fabric）: **12/12 通った**。
  - 1 つの項目は 1.2〜4.3 秒、全体で約 30 秒。

## 5. 残り
- 検査は `mtpanel` の `draw` を Python で書き写したもの。`draw` を変えたら、スクリプトも合わせる。
- t5emu の `make test-p4emu` には入れていない。t5emu には `matter` のコントローラの相手（smctl）がない。タッチとキャプチャだけなら、t5emu でもできる（まだ）。
