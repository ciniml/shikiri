# 57. CPU の取り分の保証（パーティション）

利用者の指示（2026-11-06）:「CPU取り分の保証をいれましょう。」（doc/56 §6 の残り。QNX の adaptive partitioning に当たるもの）

## 1. 今の形と困ること
- スケジューラは、準備のできたプロセスを 2 つのコアで順に回すだけ（10 ms のスライス、doc/10、doc/33）。
- 回り続けるアプリが n 個あると、`net` や `term` も 1/(n+1) ずつしか CPU を得られない。
  - ルーターの目的（doc/58）では、パケットを運ぶ `net` と `wifi` の時間を、アプリの負荷から守りたい。
  - `net` は Wi-Fi の 9.9 Mbps で 1 コアの約 59% を使う（doc/33 §12）。

## 2. 方針（QNX の adaptive partitioning に倣う）
- **パーティション**は 3 つで、表はカーネルに固定（`t5_abi::cpu`）。

  | 名前 | 取り分（全コアの ‰） | 入るもの |
  |---|---|---|
  | `system` | 300 | システムの鍵の像（既定） |
  | `net` | 400 | `net`、`wifi`（`--permit cpu:net`） |
  | `apps` | 300 | アプリの鍵の像（既定） |

- **保証と貸し借り**: 選び方は次の順。
  1. 準備のできたプロセスのうち、パーティションが窓（100 ms）の中で取り分を使い切っていないものを先に選ぶ。
  2. そういうものがなければ、今までどおり順に回す。
  - 空いている時間は誰でも使える。どのパーティションが待っていても、コアは遊ばない（work-conserving）。
  - 取り合いのときだけ、取り分が効く。
- **入り方**: 署名した許可の `cpu:NAME` で決める。`cpu:` は強い許可（doc/52 §4）で、アプリの鍵の像は名乗れない。名乗らなければ、システムの鍵の像は `system`、アプリの鍵の像は `apps`。
- 数は 3 つに絞った（判断）:
  - 分ける理由がはっきりしているのは「ネットワークの通り道」「ほかのシステム」「アプリ」の 3 つだけ。
  - 表を設定で変えられるようにするのは、使い方が見えてから。
- QNX との違い:
  - 取り分を超えてでも動ける「critical」なスレッドはない。
  - 取り分の窓は 100 ms（QNX の既定と同じ）。
  - パーティションの中は今までどおり順番に回す（優先度はない）。

## 3. 実装
- `Process::partition`。ローダの結果（許可と、システムの鍵か）から `cpu::of` で決める。
- `sched::Usage`:
  - パーティションごとの時間を、10 ms の升 10 個で持つ。
  - スライスの時間は、終わった時刻の升に足す。
  - 窓の中の和が「窓 × コアの数 × 取り分」より少なければ、取り分の内とみなす。
- `Scheduler::pick`: 取り分の内のパーティションの準備のできたプロセスを、`next` から順に探す。なければ、どれでも。
  - 時刻を 1 回読む（SYSTIMER の読みは約 2 µs、doc/34）。
- 試すための制御コマンド:
  - `partitions on|off`: 取り分を守るのをやめると、今までの順番だけになる（比べるため）。
  - `partition PID system|net|apps`: 動いているプロセスを別のパーティションに移す（QNX の `aps join`）。ホストからだけ。
- `ps`:
  - `proc.info` に `partition` を足した。
  - パーティションごとに `kernel.partition`（前の `ps` からの使用、全コアの ‰、取り分）を出す。

## 4. 試験
- 自己試験 `selftest.partitions`（起動のたび）: 600 ms 回る `spin` を 5 つ動かす。1 つを `net`、4 つを `apps` に入れる。
  - 順番だけ（`partitions off` と同じ）と、取り分ありの 2 回、`net` の `spin` が自分の 600 ms の間に得た時間（1 コアの ‰）を比べる。
  - 合格は、取り分ありで 600‰ 以上、かつ順番だけより多いこと。
  - t5emu: 順番だけで 401‰（予想の 2/5 のとおり）、取り分ありで 762‰。
- 実機: §5。

## 5. 実機の記録（2026-11-06、Tab5、`matter-test`）
- カーネルを `good.t5k` の手順で入れ替えた。`net` と `wifi` は `cpu:net` を足した像を入れ直した。
- **自己試験**: `selftest.partitions round_robin_pm=400 partitions_pm=782`。`net` の `spin` は、順番だけでは 1 コアの 2/5、取り分ありでは約 0.78 コアを得た。
- **`ps`**:
  - `net` と `wifi` は `partition=net`、ほかの常駐は `system`。
  - 起動の後の窓では、`net` が全コアの 49‰、`system` が 21‰ を使った。
- **Wi-Fi の TCP の echo**（PC → `nettest 1`、2 MiB）:
  - `nettest` を `partition PID net` で `net` に移し、回り続ける `spin` を 2 つ（`apps`）動かした。
  - その上で、取り分のあり・なしを 3 回ずつ比べた。
  - 結果は、どちらも 2.3〜3.1 Mbps で、差は揺れの中。`spin` なしでも 2.8 Mbps だった。
  - その間、`net` は全コアの 11〜13% しか使っていない。この網（`matter-test` の AP と PC の USB の Wi-Fi）では、無線の側が遅さを決めていて、CPU の取り合いが起きていない。
  - **この場では取り分の効き目は測れない**（判断: 同じ測り方を続けない）。CPU が足りなくなる転送の試験は、Ethernet のある EVB（doc/58 R5、100 Mbps の有線）で行う。
- 試験の後片付け:
  - 1 回目の試験のスクリプトは、途中の誤り（プロセスのスロットが 12 で足りず、`spin` が 2 つしか起動できなかった）で後片付けを飛ばした。
  - そのため、フィルタの規則が空（`netctl 3`）のまま残った。気づいてすぐ `netctl 2`（`rules=6`）に戻した。
  - 2 回目は、後片付けを `finally` で必ず通す形にした。

## 6. 残り
- **スライスの長さ**: 待っていたプロセスが起きても、両コアが回り続けるアプリを動かしていると、スライスの終わり（最大 10 ms）まで待つ。取り分は時間の割合を守るだけで、待ち時間は守らない。ルーターで遅れを詰めるなら、`net` が起きたときに、取り分を超えているパーティションのコアを横取りすることを考える。
- **カーネルの時間**: スケジューラのループの中の仕事（`wlan::poll`、`hostlink::poll`）は、どのパーティションにも数えない。
- **表を変える方法**: 取り分の表を設定（`cfg`）から変える方法はない。
