# 59. エミュレータの高速化と、試験の並列実行

利用者の指示（2026-11-06）:「p4emu結構時間かかってますが、パフォーマンスに問題がありますか？」、「エミュレータ自体の高速化は可能ですか？」、「高速化すすめて。テストの並列実行も。」

## 1. 遅かった理由
- `make test-p4emu` は t5emu を 26 回起動していた。どれもカーネルを起動して自己試験を通してから、その試験の場面を動かす。
- t5emu は命令を 1 つずつ解釈する（40 MHz を模す）。毎秒約 800 万命令で、実機（2 コア × 360 MHz）よりずっと遅い。
- doc/56、doc/57 で試験が増え、26 回の合計は 8.8 G 命令から 13.4 G 命令になった（模した時間は 510 秒 → 620 秒）。
  - doc/56: 起動し直しの試験。
  - doc/57: 自己試験の `selftest.partitions`。600 ms の spin を 5 つ、2 回。
- 逐次に流すと約 40 分かかっていた。
- OS（実機）の速さの問題ではない。

## 2. エミュレータの手直し（動きは変えない）
- **測り方**:
  - `perf` は使えなかった（カーネルの道具がなく、`perf_event_paranoid` が 4）。
  - gdb の子として t5emu を動かし、0.1〜0.3 秒ごとに SIGINT で止めてスタックを数えた。
- **時間の内訳**: 毎命令の付けたしが、時間の半分ほどだった。

  | 割合 | 場所 | 直し |
  |---|---|---|
  | 約 30% | 割り込みの道筋（`route_interrupts`）が毎命令、DMA2D のレジスタ 2 つを `HashMap`（SipHash）で引いていた。DSI の DMA の割り込みも同じ | アドレス用の軽いハッシュ（`regmap.rs`）にした。2 つの割り込みの状態は、書き込みのときにだけ計算し直して持つ |
  | 約 15〜20% | 毎命令、48 本の CLIC の線を作り直し、比べ、全部を見て選んでいた | 線を 64 ビットのビット列で作り、変わらなければ何もしない。保留がなければ選ばない（`maybe_pending`） |
  | 約 8% | `Bus::ticks` の 128 ビットの割り算 | 積が 64 ビットに収まる間（数時間の模擬時間）は 64 ビットで計算する |
  | 約 7% | PMP の検査が毎回、16 個の項目の範囲（TOR、NAPOT）を解いていた | CSR に書いたときに、使っている項目の範囲だけを解いて持つ |

- **動きが同じことの確かめ**: t5emu は決定的なので、命令の数と模した時間が同じなら動きは同じとみなした。
  - 4 秒の起動: 153,654,887 命令で同じ。18.6 秒 → 8.6 秒。
  - 自己試験の起動: 483,832,115 命令で同じ。64.5 秒 → 28.1 秒（2.3 倍）。
  - 26 回の全部で、前の逐次の版と命令の数が同じ（並べて比べた）。
- `cargo test`（t5emu の単体の試験）も通った。

## 3. 試験の並列実行
- `test-p4emu` の 26 回を、それぞれ別のターゲット `p4emu-run-01`〜`p4emu-run-26` に分けた。
  - 前に付いていた説明は、それぞれのターゲットに残した。
  - 準備（`p4emu-prep`: emu、schemas、kupdate の試験用カーネル、EVB のカーネル）は 1 回だけ。
- `test-p4emu` は、`$(MAKE) --output-sync=target -j$(P4EMU_JOBS)` で走らせる。
  - 既定は 12。PC のコアは 24。
  - 出力は回ごとにまとまる。どれかが落ちれば `make` も落ちる。
- 26 回は互いに頼らない。同じ像から別々の t5emu を起動し、書き出すファイル（`emu-capture.png` など）も回ごとに別。
- **結果**: `make test-p4emu` は約 40 分 → **157〜165 秒**（約 15 倍）。

## 4. 残り
- 解読した命令を PC ごとに覚えておく仕組み（自己書き換えには、キャッシュのモデルの `I_STALE` と同じ扱いが要る）で、さらに 1.5〜2 倍ほど見込める。今は要らない。
- 自己試験の重い項目を、最初の回だけにする案もある。今の速さでは要らない。
