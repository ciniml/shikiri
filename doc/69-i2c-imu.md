# 69. アプリから I²C のデバイス（IMU）を使う

利用者の指示（2026-11-09）: doc/68 の次として「すすめて」。kumiki のドライバ（`kumiki-bmi270`）を、そのまま tab5-os のアプリで動かす。

## 1. 方針（doc/68 の続き）
- アプリは I²C のコントローラに触れない（MMIO）。カーネルが「内部バスの 1 つのデバイス」をオブジェクトとして出し、`t5_rt` 側（`kumiki-t5os`）が embedded-hal の `I2c` をその上に実装する。kumiki のドライバは変えない。
- 内部バスには、電源を切り替える IO エクスパンダ（0x43、0x44）、タッチ（GT911）、RTC、INA226 なども載っている。どのデバイスに触れるかを許可で絞る。

## 2. ABI（小版 26）
- オブジェクト `i2c:int/0xNN`（`t5_abi::i2c`）: 内部バスのアドレス 0xNN の 1 台。`write` が 1 回の転送で `[読む長さ, 送るバイト...]`（それぞれ 64 バイトまで、`MAX`）。送った後、繰り返しスタートで読む。`read` で読んだものを返す。応答がなければ `NoAck`、ほかは `Fail`。
- 許可: デバイスを名指し（`i2c:int/0x68`）するか、バス全体（`i2c:int`）。**`i2c:` で始まる許可は強い許可**（システムの鍵だけ）。例外は `APP_DEVICES`（IMU の 0x68、0x69）だけで、アプリの鍵の像も名乗れる（`t5a::strong`、単体試験 `i2c_permits`）。
- 読み書きはシステムコールの中で行う（カーネルの鍵を持ったまま、100 kHz で 33 バイトなら約 3 ms）。カーネル自身の I²C（タッチ、エクスパンダ）とは鍵で順番になる。

## 3. カーネル
- `Platform::i2c_transfer`（既定はなし）。ESP32-P4 は Tab5 だけ（`board::INTERNAL_I2C`、EVB は内部バスを起こしていないので断る）。
- **FIFO より長い書き込み**: コントローラの FIFO は 32 バイト（アドレスを含む）で、これまでの `i2c::transfer` は書き込み 30 バイトまでだった。`kumiki-bmi270` は設定の転送で 33 バイト（レジスタ＋32 バイト）を書く。ESP-IDF のドライバと同じく、コマンドの列を `END` で区切る形を足した（`long_write`）: アドレスと最初の 31 バイト、`END`（コントローラが SCL を low に保ったまま止まる、`END_DETECT`）、残りと `STOP`。読みのない 64 バイトまでの書き込みだけがこの道を通る。それより短い転送（タッチ、エクスパンダ）は今までの道のまま。
- `I2cDev`（`handle.rs`）。

## 4. アプリの側
- `kumiki_t5os::I2cDevice`: embedded-hal の `I2c`。`transaction` は、書き込みとその直後の読み出しを 1 回の転送に（`write_read` の繰り返しスタート）、それ以外は操作ごとに 1 回。開いたアドレス以外へは `Denied`。`NoAck` は embedded-hal の `NoAcknowledge`。
- `kumiki_t5os::Delay`: embedded-hal の `DelayNs`。ミリ秒の単位は眠り、残りは回って待つ。
- `imu`（`--permit i2c:int/0x68 --permit i2c:int/0x69`、アプリの鍵でよい）: 0x68、だめなら 0x69 で `kumiki_bmi270::Bmi270` を作り、`init`（設定 8 KiB の転送）、サンプルを N 回（加速度は mg、角速度は生の値）。

## 5. エミュレータ
- I²C の `END` コマンド（止まって `END_DETECT`、相手のデバイスを覚えたまま次の `TRANS_START` で続く）。
- BMI270（0x68）: CHIP_ID 0x24、ソフトリセット、設定の転送（INIT_DATA はレジスタの位置を進めない）、INIT_CTRL = 1 で INTERNAL_STATUS = 1、固定のサンプル（Z に 1 g = 4096 LSB、角速度 10、-20、30）。

## 6. 試験
- p4emu-run-42: `run imu 3` で `imu.found addr=104 chip_id=36`、`imu.ready`（設定の転送は 33 バイトの書き込みで `END` の道）、`imu.sample n=0 ax_mg=0 ay_mg=0 az_mg=1000 gx=10 gy=-20 gz=30`。
- `abi` の単体試験 `i2c_permits`。

## 7. 実機（Tab5、2026-11-09）
- `run imu 5`: `imu.found addr=104 chip_id=36`、設定の転送（33 バイトの書き込み 256 回、`long_write` の `END` の道）を経て約 0.94 秒で `imu.ready`。サンプルは `az_mg` が −994〜−996（平らに置いて 1 g）、`ax_mg`、`ay_mg` は −9〜−11 と −36〜−37、角速度はほぼ 0。最初の 1 回は 0（データの用意の前に読んだ）。
- 試す前に Tab5 には kumiki のファームウェアが入っていた（kumiki のセッションが書いた）。tab5-os のツールの返事がないのを tab5-os の不具合と取り違え、probe のリセットや USB シリアルを開くこと（ダウンロード・モードに入った）をしてしまった。利用者が電源を入れ直し、利用者の許可で `make flash-p4`（ブートローダ、パーティション・テーブル、カーネル）で書き戻した。アプリのストアは残っていた。

## 8. まだ
- I²C の転送をシステムコールの中で行うので、長い転送の間カーネルの鍵を持つ。多くなれば、サービスのループに回す（`update` のように）。
